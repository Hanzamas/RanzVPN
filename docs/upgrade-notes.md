# Upgrade notes

What an existing server shows after an upgrade. Newest first.

## AUD1-DT-18-R1 (#554): `ranz install` works on the data directory through a handle

The data directory of a Controller that is installed is not touched by the upgrade, and the service starts in it as before. What changes is how the install and the service make a new data directory, and how the install takes over one that is there:

- **A folder put in the place of the data directory while the install runs gets nothing.** The install and the service make a new data directory with one call that also opens it, and set its owner and its access list through that handle. The install opens a data directory that is there as itself, looks at what it holds, sets its owner and its list, and looks again, all through that handle. A user that may change the folder above, one that made `C:\ProgramData\Ranz` before the install, or any user under a folder in the root of a volume such as `D:\RanzData`, can still rename the data directory away in that moment and put a folder of its own or a junction in its place. The install and the service then stop with a message that says that the data directory was replaced, and what the user put there keeps its owner and its list: before, it got the Administrators as its owner and the protected list. Look at what is there, remove it, and run the install again, or start the service again.
- **A hard link in a kept data directory is refused.** A file in it with more than one name is refused before anything is changed, and the refusal names it. Its other names may be outside the data directory, and the list that the install passes down would reach the file under every name. Remove the name in the data directory with `del`, which leaves the file under its other names, and run the install again. Do not give it to the Administrators: they would own the file under every name. The Controller and its rqlite member make no hard link.
- **Names that Windows reads as other ones.** A file or a folder whose name ends in a period or a space, or is the name of a device such as `NUL` or `CON`, is looked at as itself, and one that a user owns is refused like any other. The refusal names it in quotes and says to put `\\?\` before its full path in the commands that remove it, as in `rmdir /S "\\?\C:\ProgramData\Ranz\controller\NUL"`.
- **The install looks twice.** Once the owner and the list are set, the install looks at what the data directory holds again and refuses what a user added while it looked, which a data directory whose list lets the Users group add files and folders allows, as one that an administrator made by hand in `C:\ProgramData\Ranz` has. The data directory keeps the owner and the list that the install gave it, and the service is not registered: remove what the user added, and run the install again.
- **The messages.** The refusal of a file or a folder of a kept data directory names it in quotes, so that a period or a space at its end shows.

## AUD1-DT-18 (#503): the data directory has no gap at its creation, and `ranz install` looks at what a kept data directory holds

The data directory of a Controller that is installed is not touched by the upgrade, and the service starts in it as before. What changes is how a new one is made, and which existing ones the install takes over:

- **A new data directory has its owner and its access list from the moment it exists.** The install on a new host, or after the folder was removed, makes `C:\ProgramData\Ranz\controller` with the Administrators as its owner and the protected list in one call, and so does the service when the folder is missing. Before, the folder had the list of `C:\ProgramData`, which lets the Users group add files and folders, for the moment that the install took to set its own. Nothing to do.
- **A `-data` that ends in a period or a space is refused.** Windows takes trailing periods and spaces off the end of a path, so `-data "D:\RanzData\ "` names `D:\RanzData`, and the files of the Controller, which are joined to the text, would not lie in the folder that was looked at. The install, the service at its start, `reset-admin`, `backup` and `restore` refuse such a path and say so, and the install and the service make nothing. A Controller that was registered with such a `-data` does not start after the upgrade, and its Application log says why: run `ranz controller uninstall`, which keeps the data directory, and `ranz controller install` again with the folder named without the period or the space. A trailing backslash or slash is fine: it is taken off before the folder is made.
- **`ranz install` refuses a kept data directory that holds what another account owns.** A data directory that SYSTEM, the Administrators, `NT SERVICE\ranz-controller` or the account that runs the install owns is kept with what it holds, as before, when what it holds is theirs too. When a file or a folder in it, at any depth, is owned by another account, or is a reparse point (a junction or a symbolic link, for example), the install does not take the directory over: it names the file or the folder and why, and changes nothing. Look at it, remove it, and run the install again. Do not give what a user made to the Administrators: `takeown` changes only the owner, so an entry that the user put on its access list stays, and so does a handle that the user holds open. Files that another administrator made, on a machine whose policy makes the creator the owner of what it makes, are refused the same way. Give those to the Administrators and reset their access lists, with `takeown /F "<the file or folder>" /A /R /D Y` and then `icacls "<the file or folder>" /reset /T`, and run the install again. Remove a link itself, with `rmdir` for a junction or a link to a folder and `del` for a link to a file, which leaves what it points at. Do not give a link to the Administrators: it stays a link.
- **The refusal of a data directory that another account owns gives the same advice.** The install, the service at its start, `reset-admin`, `backup` and `restore` refuse a data directory that an account other than those owns, as before (the note of AUD1-DT-10 below). Their messages offered `takeown` for the whole directory with no reset of its access lists, which keeps an entry that a user put on the list of a folder in it, such as `payload\`, and the next install, which looks at owners only, would then have taken the directory. Now they say: look at what it holds, remove it, and run the install again, or start again. Only when an administrator made the directory and all that it holds, give it to the Administrators and reset its lists (`takeown /F "<the data directory>" /A /R /D Y`, then `icacls "<the data directory>" /reset /T`). After the refusal of the service, register the service again over the directory before it starts (`ranz controller uninstall`, then `ranz controller install` with the flags of the service): the reset leaves the directory the list of the folder above it, which under `C:\ProgramData` lets the Users group read it, and only the install sets the list of a directory that is there.
- **A Controller that is installed already is not looked at again.** `ranz install` only starts a service that is registered, and the service does not look at what its directory holds at its start. The install looks when it registers the service over a directory that is there, one that `ranz uninstall` left or that an administrator made. A data directory of an earlier release, in which a user made a folder while the directory had the list of its parent, stays as it is until the service is registered again over it.
- **What the look does not catch yet.** The install reads each file and folder of a kept data directory by its name, one call after the other, and changes the directory by its name after the look. A user that owns a folder in it can switch that folder between a plain folder and a junction while the install looks, and so pass the look. A file or a folder whose name ends in a period or a space, which a user that may add to the directory can make, is looked at by the name without the period or the space, so a junction or a folder of a user named `admin.token ` passes as the file `admin.token` next to it. A user that owns `C:\ProgramData\Ranz` can put a folder of its own, or a junction, in the place of the kept directory between the look and the change, and in the place of a new one between the call that makes it and the change of its list. The look does not see a hard link either. AUD1-DT-18-R1 (#554), the note above, makes the install look and change through a handle.

## CORE-S8-1-R1 (#575): a machine with a hand-installed vpnserver moves to the Node by hand, and nothing does it for you

`vpnserver.exe` is retired (CORE-S8-1, #84): no build holds it, and the Node, `ranz-node.exe`, is the one server program. No Ranz release ever shipped `vpnserver` (the only release, `oracle-8e6504d5`, is the upstream build, and the MSI carries `ranz.exe` only), so the upgrade of a release never meets it. A machine that was set up by hand does: someone copied the build output into a folder and ran `vpnserver.exe /install`, which registered the service `sevpnserverdev` (display name "Ranz VPN Server", ADR-0020), added the inbound firewall rule "Ranz VPN Server" for that `vpnserver.exe`, and left the data next to the program: `ranz_server.config`, its backups and its logs.

Nothing removes that service. Decision 4 of ADR-0020 had the MSI stop and delete `sevpnserverdev`, but the MSI is a thin wrapper that runs `ranz install` now, and `ranz install` registers the services `ranzvpnserver` and, with `--controller`, `ranz-controller`, and no other. The old service keeps running the old program, which holds TCP 443, TCP 5555 or both (the listener list of an existing server keeps what it had, ADR-0020 decision 6). The Node needs TCP 443 and UDP 443 for its front door, and the Controller needs TCP 443, or 5555 when 443 is taken, so with the old server still there they cannot take their ports. Move the machine by hand, from a PowerShell that runs as an Administrator, before `ranz install`:

1. **Read what the service is.** The name `sevpnserverdev` is also the name of the service of an upstream SoftEther VPN Developer Edition server (ADR-0020), so look at the program before you delete anything:

   ```powershell
   Get-CimInstance Win32_Service -Filter "Name='sevpnserverdev'" | Format-List Name, State, PathName
   ```

   `PathName` is the path of `vpnserver.exe`, with `/service` after it. The folder of that file holds `ranz_server.config`: note where it is. A program that is not a Ranz build is an upstream server, which this note does not cover: leave it where it is, and move its listeners off TCP 443 and 5555 before you install the Node.

2. **Stop the service and delete it.** TCP 443 and 5555 are free after that, and the last command prints nothing:

   ```powershell
   Stop-Service sevpnserverdev
   sc.exe delete sevpnserverdev
   Get-NetTCPConnection -LocalPort 443, 5555 -State Listen -ErrorAction SilentlyContinue
   ```

3. **Delete the firewall rule.** It names the old `vpnserver.exe` and lets every port and protocol in on it:

   ```powershell
   Remove-NetFirewallRule -DisplayName 'Ranz VPN Server'
   ```

   The command prints an error when there is no such rule, which is fine. A server that started before REL-2 (#47) ran a VBScript for the rule and wrote the registry key `HKLM\SOFTWARE\Hanzcodes\Ranz VPN\PacketiX VPN\FW ScriptHash`, which nothing reads any more: `Remove-Item -Recurse 'HKLM:\SOFTWARE\Hanzcodes\Ranz VPN\PacketiX VPN\FW ScriptHash'` removes it. Leave the keys above it, which the Node and `ranz install` use.

4. **Install the Node**, and the Controller where it runs on this machine: `ranz install` or `ranz install --controller` (`docs/first-test.md`, step 5, says what it does). The Node starts with an empty Configuration store, and makes its data directory `C:\ProgramData\Hanzcodes\Ranz VPN` for SYSTEM, the Administrators and its service account only.

5. **Put `ranz_server.config` into the data directory of the Node.** Stop the service first, so that the file never lies in a folder with another access list than the one the Node gave it, and start the service after:

   ```powershell
   Stop-Service ranzvpnserver
   Copy-Item '<the folder of vpnserver.exe>\ranz_server.config' 'C:\ProgramData\Hanzcodes\Ranz VPN\'
   Start-Service ranzvpnserver
   ```

   The Node imports the file once at its start, and renames it `ranz_server.config.imported`. It imports the Virtual Hubs as L2 Networks with their CAs, groups and users, the TCP listeners as TLS listeners, the server certificate with its chain, the administrators, and the access lists as rules of the policy. It leaves out the password hashes that are SHA-0 (ADR-0022: those users and administrators need a new password), the server key (it belongs in a key storage provider, not in the store), the cascades, and the items of the policies of users and groups other than their VLAN. The node log says what it carried and what it left out:

   ```powershell
   Select-String -Path 'C:\ProgramData\Hanzcodes\Ranz VPN\node_log\*.log' -Pattern 'Fork configuration'
   ```

   The import needs a store that holds no Network, Listener, certificate or administrator and has imported nothing before. When a Controller has put a Network or a Listener there already, the log says `not imported` with `the configuration store is not empty`, the file stays where it is, and nothing was changed.

6. **Clean up.** `ranz_server.config.imported` and the old folder hold the server key and the password hashes of the old server. Delete the renamed file once the import is checked, and the old folder with its backups and logs when you do not need them: ADR-0020 decision 3 keeps them on uninstall, and nothing deletes them.

Nothing warns you either: the Node, `ranz install` and `ranz doctor` do not look for `sevpnserverdev`. And there is no way back to `vpnserver`: no build holds it any more.

## AUD1-DT-17 (#502): what holds for a secret that the upgrade sealed, the URL of a target is not sealed, and a secret opens for its URL only

The note of AUD1-DT-10 (#458, below) says that the Controller seals the secrets of the export and audit targets, and the threat model said that the table, the data of `rqlited`, a snapshot and a backup then hold none in clear. That holds for a secret that is put after the upgrade. For a secret that the earlier release kept in clear and that the upgrade sealed it holds in part, and the text now says which part:

- **The old text of a migrated secret is still in the data of `rqlited`.** The upgrade seals such a secret by changing its row. The table, and every backup that this release makes, hold it sealed only: the backup is vacuumed (`GET /db/backup?vacuum`), so it holds none of the free space where SQLite leaves the old text of a changed row, which a plain copy of the file would carry. But rqlite keeps the first write of the secret in its Raft log until a snapshot truncates the log (on a quiet Controller that can be a long time), in its older snapshots until newer ones replace them, and in the free space of its SQLite file until the file is vacuumed. Whoever can read the data directory of `rqlited` (ST-3 of the threat model), or a copy of the disk or of a snapshot of the host, can read the old secret there. In a cluster, every member holds it in its own rqlite. **After the upgrade, put each target that has a secret again with a new secret, and change the secret at the receiver** (the HMAC key of a webhook, the bearer token of an OTLP endpoint): `PUT /api/v1/targets/{name}` and `PUT /api/v1/audit/targets/{name}`. A secret that is put after the upgrade is sealed before it is written, so no byte of its clear text is in any of these places.
- **A backup that the earlier release made holds the secrets in clear**, and its file keeps them so after a restore: delete it, or keep it as safe as the data directory. The restore of it under the running service puts them back into the store in clear for a moment: the Controller looks for secrets in clear every minute, as a member of a cluster does, and seals them without a restart. A Controller that is stopped seals them at its next start. The text that `ranz controller restore` prints says so.
- **The URL of a target is not sealed.** The path and the query of a webhook URL are often its token, and the URL is in the table, in the data of `rqlited` and in every backup as it was put; the API shows of it the scheme, the host and the port only. The Controller must know where a target goes without the key, so that a store whose key is lost still names where each target sends. Put a token in the secret field where the receiver takes it there (the HMAC key of a webhook, the bearer token of an OTLP endpoint). A token that the receiver wants in the URL is as safe as the backups and the data directory: keep them so, and change the token at the receiver when a backup is lost. The text of `ranz controller backup` says so.
- **A secret opens for the URL it was sealed with.** Whoever can write a row of the store, or change a backup that an administrator restores, could point a target at a URL of its own, and the Controller sent the unsealed secret there. The sealed box now holds the URL of its target, so a row whose URL was changed has a secret that does not open: the target comes back with its new URL and none, the log names it (`the secret of a target cannot be opened ... or the URL of the target was changed after the secret was sealed`), and the Controller sends to the new URL without a secret, a webhook unsigned and an OTLP endpoint without its bearer token. A change of the URL through the API replaces the target with its secret, which seals it for the new URL, so an operator sees no difference. A store that a build of `integration` sealed before this change, between the note of AUD1-DT-10 and this one, holds secrets that no longer open: the log names each target at the start, and each is put again.
- **A rollback to the earlier release** cannot open a sealed secret. It takes `ranz-sealed:1:` and the text after it for the secret itself: it signs each webhook with that text as the HMAC key, so a receiver that checks the signature refuses it and the Controller sends again later, and it calls an OTLP endpoint with that text as the bearer token, which the endpoint refuses. `GET /api/v1/targets` still shows `hasSecret` true. After the rollback, put each target again with its secret, through the earlier release, which keeps it in clear as it did; the next upgrade seals it again. The rollback of a cluster is in the note of AUD1-DT-16, below.
- **Two Controllers on one store are not told for a cluster.** A cluster is the Controllers that start with `-rqlite-join`, each with a rqlite member of its own; they seal with the Cluster key. Two Controllers that use one store through `-rqlite-external`, or through an rqlite that another process runs, seal with the key of their own hosts and cannot open what the other sealed: the log of each names the secrets that it cannot open, and the targets of the other are sent without them. Use `-rqlite-join` for two Controllers on one store.

## AUD1-DT-16 (#501): a cluster of Controllers seals the secrets of its targets and the PresharedKeys of its Devices with a Cluster key

A cluster of Controllers, whose members run with `-rqlite-join`, kept the secrets of its export and audit targets in clear, and made no WireGuard Device with a PresharedKey, since its members have no key in common. It seals them now with a Cluster key: one key of the cluster, which each member holds in memory and the store holds only as a copy for each member, sealed to the key of that member's host. At the first start of a member of this release:

- **The cluster gets its Cluster key, and the secrets are sealed.** The first member of this release that starts makes the Cluster key, logs `this member holds the Cluster key: it made it`, seals the secrets that the store holds in clear, and logs `sealed the secrets of the targets that were in clear, with the Cluster key` with how many. Each member that starts after it publishes the public half of the key of its host in the store, gets a copy of the Cluster key from a member that holds it within seconds, and logs `this member holds the Cluster key: its copy opens`. The targets send as before, and the API still never shows a secret.
- **During the rolling upgrade** a member of the earlier release cannot open a sealed secret. While one leads, the targets are sent without their secrets (a webhook unsigned, which a receiver that checks the signature refuses and the Controller sends again later; an OTLP endpoint without its bearer token), and its log says `the secret of a target cannot be opened`; a Device that a member of this release made with a PresharedKey goes to its gateway without it. Upgrade the members one after the other, without a pause: once a member of this release leads, the targets are sent with their secrets again. A target that a member of the earlier release puts meanwhile is in clear until a member of this release seals it, within a minute.
- **A Device can be made with a PresharedKey in a cluster.** `ranz device create`, the form Make a Device and `POST /api/v1/devices` seal the PresharedKey with the Cluster key, in the table `device_keys`, as a single Controller seals it with the key of its host, and the member that leads opens it for the gateway of the Device alone. The Devices that the cluster made before, with `-no-preshared-key`, have none: to give one a PresharedKey, make a new Device and delete the old one.
- **A member that holds no Cluster key yet** refuses a target with a secret and a Device with a PresharedKey, says `this member does not hold the Cluster key yet` in its log, and sends to the targets without their secrets, and the Devices to their gateways without their PresharedKeys, until it gets its copy, which a member that holds the key gives it within seconds.
- **A backup of a cluster holds the secrets and the PresharedKeys sealed**, and the Cluster key only as copies that the key of each member opens. A restore keeps the Cluster key of the cluster that it restores into: a backup of the same cluster opens as it was, and a backup of another cluster, or one restored on a single Controller, brings its targets back with their names, URLs and types and with no secret, and its Devices with a PresharedKey that does not open, as a backup restored on another host does. Put each target again with its secret, and make each of those Devices again. A backup that the cluster made before the upgrade holds the secrets in clear: make a new one and delete the old one.
- **When every member loses the key of its host at once**, for instance when every member that ran in the foreground runs as the service, whose account has another key set, no member can open its copy. A minute later a member makes a new Cluster key and logs `the Cluster key was lost`, and the targets are sent without their secrets until each is put again, and the Devices without their PresharedKeys until each is made again. Change the members one after the other instead, and the members that still hold the key give the others a copy.
- **A rollback** to the earlier release: its members cannot open a sealed secret or a PresharedKey, and send to the targets without their secrets, and the Devices to their gateways without their PresharedKeys, until each is put or made again.
- A single Controller that becomes a member of a cluster keeps the secrets and the PresharedKeys that the key of its host sealed, which the other members cannot open: put each target again, and make each Device that has a PresharedKey again, once the cluster has formed.

## SDN-82-R2 (#565): a gateway that the earlier release left without a key, and two key files that others could read

The read-only review of SDN-82-R1 (#548, below) found three edge cases. After the upgrade:

- **A gateway that the earlier release left without the key of a Device does not get it from this release. Restart it once.** When the PresharedKey of a Device did not open, the release before SDN-82-R1 sent the Device to its gateway without the key, but stored the Ack of the gateway, the state that it acknowledged last, with the sealed key. This release trusts the Ack that the store holds. It takes such a gateway for one that has the key, and sends it nothing: not when the key opens, and not after a restart of the Controller. The gateway keeps the Device without its key, and a client that holds the PresharedKey completes no handshake. Restart the Node service of that gateway (`Restart-Service ranzvpnserver`). It then holds nothing, and the Controller sends it each Device whose key opens, with its key, as it does for a new gateway. The log of the earlier release names the Device of such a gateway (`the PresharedKey of a Device is not sent`), and `ranz get devices` shows the `gateway` of each Device. Without that log, restart the gateway of each Device whose `presharedKey` is true. This is only for what the earlier release stored: a gateway that this release sent a Device without its key gets the key without a restart, as SDN-82-R1 says.
- **`ranz device create` makes no file on a volume that keeps no access lists.** On a FAT32 or exFAT volume, a USB stick for instance, `-o` and `-qr-file` made the file and printed a note that every account of the computer may read the keys in it. The file of a key is for its owner, SYSTEM and the Administrators only, so `ranz` now makes no file there. `-o` prints the configuration instead, as it does for a file that cannot be written, and `-qr-file` fails with a message after the configuration is printed. Name a file on an NTFS volume.
- **`ranz device create` refuses a name with a colon on Windows.** `-o C:\temp\notes.txt:phone.conf` put the keys in a stream of the file `notes.txt` when that file existed, and a stream has the access list of its file, which other accounts may read. `ranz` now refuses a name with a colon in its last element before it makes the Device, and says that nothing is made. Off Windows a colon is an ordinary character, and the names are not changed.

## SDN-82-R1 (#529): the keys of the Devices after the review of SDN-82

The read-only review of SDN-82 (#377, below) found faults in the keys of the Devices and in `ranz device create`. After the upgrade:

- **`ranz device create` writes its files only as new files.** The files of `-o` and `-qr-file` hold the private key and the PresharedKey of the Device. `ranz` makes each of them itself, so that it never takes the access list of its folder: on Windows `CreateFile` gets the protected list of the owner, SYSTEM and the Administrators with the call, and elsewhere the mode is 0600. A file that exists, a link, or one name for both flags is refused before the Device is made, with a message that says so, and nothing is made. A script that wrote the configuration to the same file at each run deletes the file first, or names a new one.
- **`-qr` on a Windows console.** `ranz` turns on the colour codes of the console for the QR code, and gives the console its mode back after. A console that refuses the mode gets the code without colour codes. `-qr-file` writes the PNG file for a scanner that does not read the code on the terminal.
- **A PresharedKey that does not open is shown.** The Controller opens each sealed PresharedKey when it starts. `GET /api/v1/devices` and `ranz get devices` have `presharedKeyDoesNotOpen` for a Device whose key does not open, as after a restore on another host, the Devices page says `does not open` in its column PresharedKey, and the configuration that `ranz get device-config` prints has a comment that says so. The log names each of those Devices once, when the Controller starts, and not at each Update as it did.
- **A PresharedKey that opens late reaches its gateway.** A key that did not open because its key storage provider did not answer, or because a member of a cluster did not hold the Cluster key yet, is tried again every 10 seconds, and the gateway gets the Device with its key once it opens: the gateway does not start again, and the Device does not change. A gateway that this release sent a Device without its key, since the key did not open when the Device was sent, gets the key too after a restart of the Controller with the key that sealed it. A gateway that the earlier release left so does not: see SDN-82-R2, above. A key that another key sealed never opens with this one: make the Device again.
- **A refusal of a PresharedKey is a 409.** `POST /api/v1/devices` answers 409, with the message that says what to do (make the Device without a PresharedKey, or try again), when the Controller has no sealing key, a member of a cluster does not hold the Cluster key yet, or the sealing key does not open what it sealed. It answered 500. A client of the API that took the 500 for this refusal takes the 409.
- **A delete that failed leaves no key for a new Device.** A Device that a change adds, through `ranz device create`, an apply, an import or a rollback, takes the PresharedKey of no earlier Device of its name: the Controller deletes the row of `device_keys` that the store may still hold of that name before it stores the change, and refuses the change when it cannot delete it.

## SDN-82 (#377): the Controller makes the keys of a WireGuard Device

The Devices of SDN-80 (#375) had the public key that an administrator gave in the Intent, and no PresharedKey. After the upgrade:

- **A Device can be made with its keys.** `ranz device create`, the form Make a Device on the Devices page and `POST /api/v1/devices` have the Controller make the key pair and a PresharedKey of the Device, add the Device to the Intent, and answer once with its finished configuration and the QR code of it. The private key is in no place that the Controller keeps; the PresharedKey is in the new table `device_keys` of the store, sealed to the sealing key of the host, the one that seals the secrets of the targets. The table is made at the first start, and is empty. The guide `docs/clients.md` has the setup of each client.
- **The Devices that exist have no PresharedKey, and the Controller adds none.** A key is never changed in place. To give a Device a PresharedKey, make a new Device and delete the old one, and set the new configuration up on the client. An `apply` of a Device resource, as before, never makes one.
- **A Device can have an owner.** The field `owner` of a Device names a User: the Device carries the groups of the User as tags, and counts against the maximum devices of the User. A User that owns a Device cannot be deleted.
- **A Controller with `-rqlite-join`, a member of a cluster,** had no sealing key in common with the other members, so it refused to make a Device that has a PresharedKey. Since AUD1-DT-16 (#501, above) it seals the PresharedKey with the Cluster key of the cluster.
- **A backup holds the PresharedKeys sealed, and a restore on another host does not open them.** The Controller there logs `the PresharedKey of a Device is not sent` for each of those Devices, and its gateway terminates them without a PresharedKey, so a client that has one completes no handshake. Make each of those Devices again.

## AUD1-DT-10 (#458): the secrets of the targets are sealed, a backup is for the Administrators, the data directory has an owner

The Controller's files on its host changed in three ways. At the first start after the upgrade:

- **The secrets of the export and audit targets are sealed.** The HMAC key of a webhook and the bearer token of an OTLP endpoint were in the store in clear. The Controller now seals each one with a key of its host (an X25519 key of the Microsoft Software Key Storage Provider, named after the data directory, in the key set of the account of the service) and logs `sealed the secrets of the targets that an earlier release kept in clear` with how many. The targets send as before, and the API still never shows a secret. A Controller with `-rqlite-join`, a member of a cluster, keeps the secrets in clear, since the members have no key in common, and says so in its log at each start.
- **A backup holds them sealed, and has an access list of its own.** A backup that `ranz controller backup` writes is readable by SYSTEM and the Administrators only, whatever the access list of its folder says, and its text names everything that it holds (the Intent, the audit log, the hashes of the tokens and of the passwords, the licence key and the secrets of the targets). A backup made before the upgrade holds the secrets in clear and has the access list of its folder: make a new one and delete the old one, or keep the old one as safe as the data directory.
- **The service does not start in a data directory that another account owns.** The data directory must be owned by SYSTEM, the Administrators or `NT SERVICE\ranz-controller`. One that `ranz install` made, or that the service made, is. One that a user made and put in the place of the real one is not: the service does not start, writes a failure (event ID 3) to the Application log that names the owner, and `ranz controller reset-admin`, `backup` and `restore` refuse the directory too. Look at what it holds, then remove it, and start the service again. (This note offered `takeown` alone for a directory that is yours. That keeps an entry that a user put on a list in it: give a directory to the Administrators only when an administrator made it and all that it holds, with a reset of its lists, as the note of AUD1-DT-18 above says.) A data directory that is a link (a junction or a symbolic link) is refused the same way: name the folder itself with `-data`. `ranz install --controller` takes over a data directory that another account made only when it is empty (it makes it again), and refuses one that holds files, with a message.

What a restore does with the secrets: they open only with the key of the host that sealed them. After `ranz controller restore` on **another host**, on a host whose key storage was rebuilt, or with the data directory at another path, the targets come back with their names, their URLs and their types and with no secret. The Controller sends to them with none (a webhook unsigned, an OTLP endpoint with no bearer token), logs at its start `the secret of a target cannot be opened with the sealing key of this host` for each one, and `GET /api/v1/targets` shows `hasSecret` false. Put each target again with its secret (`PUT /api/v1/targets/{name}`, and `/api/v1/audit/targets/{name}` for an audit target). A restore on the same host keeps them working.

## SDN-54 (#247): old log files go at the first start

The log of the Controller service (`controller.log` in its data directory), the log of a Node (`node_log` in its data directory) and the log of the BGP sidecar of the Node (`ranz-bgp.log` in the same folder) now keep within an age limit of 30 days and a disk limit of 256 MB. At the first start after the upgrade, the files of these logs whose last record is older than 30 days are deleted, and so are the oldest files beyond 256 MB together, with the log file that is open counted at the size it may grow to (a quarter of the limit). A file that another program holds open stays and is tried again every hour.

To keep more, start the Controller with `-log-days` and `-log-mb`, or set the settings `LogDays` and `LogMB` in the Configuration store of the Node; 0 is no limit. The Controller logs to its standard error, and so keeps no file, when it runs in the foreground or on Linux.

## FIX-5 (#101): the virtual hub MAC address and address change once

The machine identity of a server now comes from the MachineGuid of Windows (`HKLM\SOFTWARE\Microsoft\Cryptography\MachineGuid`) and a random 32-byte salt that the config file keeps as the `byte MachineIdSalt` item of `ServerConfiguration`. It used to come from the host name, the host IP addresses and the OS version.

On the first start after the upgrade:

- The config file has no `MachineIdSalt` yet. The server draws one and saves it at start-up.
- Every virtual hub gets a new MAC address (`00:AE:xx:xx:xx:xx`), a new hub address (`172.31.x.x`) and, from the new MAC address, a new IPv6 link-local address. Hosts on the hub segment learn the new MAC address from the next ARP or neighbour exchange. Static ARP entries, MAC filters or access lists that name the old hub MAC address need the new one.
- The `unique_id` that a Cascade sends when it logs in to another server changes.

After that, the identity stays the same across restarts, host renames, IP address changes and OS updates.

Other cases:

- Two servers cloned from one image share the MachineGuid. They get separate identities only if each has its own config file: an image made before the server first started has none, so each clone draws its own salt. An image that already holds the config file gives every clone the same salt, and with it the same hub MAC address and address. On each such clone, stop the server, delete the `byte MachineIdSalt` line from the `ServerConfiguration` folder of the config file, and start it again; it draws and saves a new salt.
- A config file restored on the same machine keeps the identity. Restored on a different machine, it gives a new identity, because the MachineGuid differs. A new config file, or one without `MachineIdSalt`, gives a new identity.
- Two server instances on one machine no longer share the identity. A Cascade between them still counts as a local-host session, because the server also checks whether the peer address is one of its own.
