# ADR-0030: Telemetry from counters, ETW and controller export, events by webhook

**Status:** Accepted (2026-10-20, from the SDN spec #176 that Hilmi filed; recorded by SDN-1, #177). Follows the ETW and Prometheus rows of ADR-0008.

## Context

The new core has no telemetry. Operators of an SDN need to see who sends what and which rules hit, Windows administrators expect local events in their usual tools, existing monitoring (Prometheus, OpenTelemetry) should pick Ranz up without adapters, and alerts must arrive without polling. The slim fork's web admin plans a Prometheus `/metrics` endpoint on its admin listener (ADR-0021); in the new core the controller is the place where fleet-wide numbers come together (ADR-0026).

## Decision

1. **Counters in the node per peer, per VRF and per policy rule.**
2. **Local node events go to ETW**, so Windows administrators read them with the tools they already use.
3. **Nodes push summaries to the controller** over the control stream (ADR-0027). **The controller exports Prometheus and OTLP.**
4. **IPFIX flow records** are the last telemetry step of v1, for traffic analysis per flow.
5. **Events by webhook:** node down, gateway failover, IPAM pool near exhaustion (ADR-0028) and an automatic rollback (ADR-0031). The same conditions are exported as metrics.

## Consequences

- The controller conformance seam (ADR-0026) checks events and metrics as external behaviour: a scenario that takes a node down or exhausts a pool produces the webhook call and the metric.
- The delivery order of #176 puts telemetry after IPAM and DNS and before the intent API; IPFIX comes last inside telemetry.
- The unified-management spec #224 adds an audit log (SDN-49, #242) and usage reports per user, group and network built from traffic counters (SDN-51, #244).
- Tickets: SDN-16 (#192).

## Amendment 2026-10-23: the audit log (SDN-49)

Recorded by SDN-49 (#242), the audit log that the unified-management spec #224 adds to the telemetry of this ADR (user story 55).

- **An Audit record is not an Event.** The controller keeps an audit log beside the Events of decision 5: one Audit record for each login, logout, failed authentication, enrolment, change of the intent and operation, with its actor, its time, its source, its outcome and, for a change of the intent, the revision that it made. An Event is a condition that operators are told about; an Audit record is the controller's account of who did what. The two have their own tables, their own API and their own targets, so a webhook of events never receives an Audit record.
- **What each kind records today.** `intent-change`: every revision (apply, delete, rollback, import, the first start and the automatic rollback), written by the controller with the revision, under the API token that asked for it or the system; an apply, delete, rollback or import that an API call asked for and that failed is a record with outcome failure, the reason and no revision. `operation`: every other call of the API that changes something (a licence key, an export or audit target, an API token, the retention), with the call as its action, so the live operations of SDN-50 (#243) are audited from the day they exist. `auth-failed`: a call of the API whose bearer token is missing or unknown, a request that the admin source allowlist of SDN-39 refused, and a node whose static key no Node resource holds (its actor is the key, so an operator can write the resource). `enrolment`: the first Hello of a static key, and with the outcome failure a node that a Network refused to enrol because of its source address (`enrolSources`, SDN-39); both refusals are Events as well, and are recorded here as often as the Event is. `login` and `logout`: a control stream of a node that was accepted and that ended; the logins of users and administrators (SDN-32, #226) record themselves as the same kinds through `Controller.RecordAudit`. A controller that closes ends every stream and records no logout for them. A source that fails to authenticate again within 10 seconds is not recorded again, so a caller that guesses tokens cannot fill the store.
- **Export.** An audit target is an export target of its own kind, kept in its own table and managed under `/api/v1/audit/targets`: a `webhook` receives each record as a JSON POST signed with the secret of the target (`X-Ranz-Signature`, the form of the webhook of events), and a `syslog` receiver each record as an RFC 5424 message over UDP, TCP or TLS (the facility is log audit, the severity warning for a failure; over TCP and TLS each message has its length in front of it, RFC 6587 and RFC 5425). A target may name the kinds it wants. The leader sends each target the records in the order they were made and the store keeps the last record each target was sent, so a controller that restarts, or the next leader, goes on where the last one stopped; a target that fails is tried again with a growing wait, and no record is skipped for it. A new target starts at the latest record.
- **Retention.** The leader removes the records older than the retention policy, and the oldest beyond its maximum number, every hour. The policy is `{"days": 365, "maxRecords": 2000000}` until an operator sets another through `/api/v1/audit/retention`; the maximum number is what keeps a flood of failed authentications from filling the disk. The id of a record is never used twice, also after every record was removed, so the record of what a target was sent stays valid.
- **Reading.** `GET /api/v1/audit` lists the records oldest first, with `kind`, `actor`, `since`, `until`, `after` and `limit`. It needs the role viewer, since the API gives every read that role; keeping the audit log from viewers needs a rule in the Guard (`api.Needs`), which is not part of this change. The source of a call that a standby forwarded to the leader is the address of the standby.
- **ETW on the nodes** stays with the node (decision 2): the control message that tells a node what to log, and the C code that writes the events, are not part of this change.

## Amendment 2026-10-24: log retention and the diagnostics bundle (SDN-54)

Recorded by SDN-54 (#247), the retention of logs and the support bundle that the unified-management spec #224 adds (user stories 57 and 58).

- **Log limits.** The log of the Controller service and the log of a Node keep within an age limit and a disk limit, 30 days and 256 MB unless an operator sets others, and 0 is no limit. The Controller takes them from `-log-days` and `-log-mb`; a Node from the settings `LogDays` and `LogMB` of its Configuration store. The writer starts a new file when the current one is full and when a day ends (the Controller's writer moves the file aside under a name with the time, the Node's writer names its files by date and number, as it always did), and the files that it is done with are deleted when their last record is older than the age limit and, oldest first, when they would take the room that the disk limit leaves the file that is open. That file counts as much as its maximum size lets it grow to, and a disk limit makes the maximum size a quarter of it, so a log never takes more than its limit, also not between two files. The limits are applied when the program starts, so limits that are lower than the ones of the last run take effect at once, and every hour while it runs. A file that cannot be deleted, because another program holds it open, stays and is tried again; the file that is open is never deleted. The Controller log is written by `controller/internal/logfile` (the Windows service writes `controller.log` through it; run in the foreground, the Controller logs to its standard error and keeps no file); the Node log by `SetLogLimits` of the log writer (`LogWriter.c`), whose writer thread deletes the files and writes a line of the log for each. The log of the BGP sidecar of a Node (`ranz-bgp.log` in the node log directory) keeps within the same limits: the Node starts the sidecar with `-log-days` and `-log-mb`, and the sidecar of the `ranz` executable writes its log through `controller/internal/logfile` (`ranz-bgp` is not under `controller/`, so it takes the writer through `bgpcmd.OpenLog`, which `controller/cmd/ranz` sets).
- **The diagnostics bundle** is one ZIP archive with the logs, the configuration and the status of a Controller or of a host, and a manifest (`manifest.json`) that lists every part with its size, its hash and the number of secrets that were replaced in it, and names what could not be collected. It is built from sources that each name the parts they give (`controller/internal/bundle`), so that what no source names, the keys, the token file and the stores, is not in it. Every part goes through the redaction: the value of a field whose name holds a secret (password, token, key, hash, salt and the like) in JSON and in text, a secret that has a form of its own (a bearer token, a token of the API, a private key in PEM, a password hash, a password in a URL, a web token) and a JSON document that a line holds as an escaped string, are replaced by `[redacted]`. A part is at most 16 MB and a bundle 48 MB; of the log files, the newest records go in.
- **The bundle of a Controller** is the answer of `POST /api/v1/diagnostics/bundle`: the host and its services, the status, the nodes with their Capabilities, the intent, the revisions, the events, the licence in force, the address pools, and the files of the Controller log with a report of what they take against their limits. It is a POST, since it makes a file at this moment, and so it needs the role operator and is an `operation` in the audit log, under the token that asked; keeping the logs from operators needs a rule in the Guard (`api.Needs`), which is not part of this change. The web UI offers it on the Diagnostics page (the UI action `diagnosticsBundle`), to the roles that may. In a cluster a standby forwards the call, so the bundle is the one of the leader.
- **The bundle of a host** is `ranz doctor --bundle`: the report of the checks, the host and its services, the log files of the Node and of the Controller that run there, and the text dump of the Node's Configuration store (`node_config.txt`, which the Node writes into its data directory at its start; the dump has no password hash and no key). It writes the file given with `-o`, which must not exist yet, or `ranz-host-NAME-TIME.zip` in the current directory.

## Amendment 2026-10-27: the live operations are audited by the Controller (SDN-50)

Recorded by SDN-50 (#243). The `operation` records of the amendment of 2026-10-23 said that the live operations would be audited from the day they exist. They are, and the Controller makes the records itself, with `RecordAudit`.

- **Every call is a record, the reads too.** A list of the sessions or of the bans, a read of a MAC table or of an IP table, a disconnect, a ban, an unban and a clear are `operation` records, with the action `session-list`, `session-disconnect`, `user-disconnect`, `ban-list`, `user-ban`, `user-unban`, `mac-table`, `mac-table-clear`, `ip-table` or `ip-table-clear`. The rest of the API stays as it was: a read is not audited. These reads are, because they show who is connected from where and what a node learnt of its members, and the spec asks that every operation is written to the audit log (#224).
- **The Controller makes them because it knows more than the call does.** The subject is what the call was done to (a session, a user, a Network with the node and the entry), the message says what came of it (the sessions that were ended, the status of each node that was asked, the reason of a ban), and the outcome is a failure when the call failed, and when a node that a table call asked did not do what was asked. `AuditCalls` does not record the paths under `/api/v1/operations` a second time (`selfAudited` of the API).
- **A stream that is refused for a banned user** is an `auth-failed` record of the node, throttled as the others are.

## Amendment 2026-10-27: the session flap (AUD1-DT-11)

Recorded by AUD1-DT-11 (#459), the detection that rows NS-12 and G-30 of `docs/threat-model.md` ask for. It adds a fifth Event to decision 5, `session-flap`, that a Node raises.

- **The condition.** A new handshake of a static key closes the session that a Node holds for it (`NodeOverlayReplace`), because that is how a Node that roamed or woke from sleep takes its place again (CORE-S3-1). A thief of the key and the real Node can use it to keep each other off by taking turns: each dials again as soon as the other closed its session. The replacement stays as it was. It is counted now.
- **What the Node counts.** The overlay counts, for each peer, the replacements of its session in a window. Above the limit it raises one event of the type `session-flap` and writes a line of the node log; a peer that is reported is not reported again before another window has passed, so a flap that goes on makes one Event for each window. The defaults are more than 5 replacements in 60 s (`NODE_FLAP_LIMIT`, `NODE_FLAP_WINDOW`): a Node that roams once replaces one session and raises nothing, and two holders that dial again a second after their session was closed are above them within 10 s. The limit and the window are fields of the overlay configuration (`FlapLimit`, `FlapWindow`, 0 for the default) that only the code and the vpntest harness set, as the number of handshakes in flight is; no setting of the Configuration store or of the Intent carries them yet. The count is in memory: a Node that restarts starts to count again.
- **What the Event says.** The subject is the name of the peer, and the message says how often its session was replaced in the window and from which addresses the sessions came, for example `the session of peer branch-2 was replaced 6 times in 60 s, by sessions from 198.51.100.4 and 203.0.113.9`. The addresses are the hosts of the sessions that replaced each other, at most four, without a port, which changes with each connection. Two addresses show two holders of the key. One address shows one host that dials again and again, which is a bad link of that host, or two holders behind one address. The Node asks its transport for the address of the other end of each stream (`TransportRemote`): the peer of the TCP connection under TLS, the remote address that msquic reports under QUIC. A transport that tells none leaves the addresses out of the message.
- **What reaches the Controller.** The Node queues its events, 64 at most with the oldest dropping first, and writes them as the events of a Telemetry message after its Hello and whenever they wait. An event leaves the queue once its write succeeded, so a Node that was cut off from its Controller reports what it saw once it is back, and the Controller stamps the Event with the time it took it. The Controller raises the Event `session-flap` with the node that reported it as `node`, the peer as `subject` and the message of the Node cut to the limits of the Telemetry (63 and 255 bytes). `ranz get events`, the Events page of the web UI (with the columns Node and Subject), a webhook target that names the type or none, and the metric `ranz_events_total{type="session-flap"}` (0 from the start) have it as they have any Event. The control protocol gets `NODE_EVENT_TYPE_SESSION_FLAP`. No schema version changes: a Controller of an older release skips an event of a type that it does not know.
- **What the operator does.** The key is no secret of one Node any more, so no change of the session settles who the real Node is: the operator takes the key away. Delete the Node resource of the peer (`ranz delete Node NAME`, with the kind spelled `Node` as in the Intent): its key leaves the Peer objects of the next Generation of every Node that can reach the Controller, and its control stream is refused at once (NS-11, CS-5). A Node that cannot reach the Controller keeps the list it has until it can (CS-10). Then make a new key for the real Node, on a host that the thief no longer reaches. The Node makes its static key at its first need and keeps it in the Microsoft Software Key Storage Provider under the name of its `IdentityKey` setting, `Ranz Node` unless the setting names another. Stop the Node service, delete that key from the key storage (for example `certutil -csp "Microsoft Software Key Storage Provider" -delkey "Ranz Node"` in an elevated window, which is the machine key set that a service with the rights of an administrator uses) and start the Node service again: `ranz node key` then prints the public half of the new key. Apply a Node resource with it as `publicKey`. The new key is a Node that the thief has no key for. If the thief is on the host of the Node (NS-13), a new key on that host does not stop it: that is what ADR-0041 designs for.
- **What is not part of this change.** The replacement itself is not refused: a Node that took the place of a session cannot know which of the two holders is the real one. A Node that the Controller cannot reach reports nothing until it can. The limit and the window of a Node are not set from the Intent, and the Event is not an alert by itself: an operator who wants one gives a webhook target the type `session-flap`.

## Amendment 2026-10-27: a read of the tokens, the audit log or the licence is an access (AUD1-DT-13)

Recorded by AUD1-DT-13 (#461), which closes the audit of reads of gap G-17 of the threat model (AP-8). The audit log recorded every call that changes something and no read, so the log could not say who looked at the API tokens, at the log itself or at the licence.

- **A new kind, `access`.** A read of `GET /api/v1/tokens`, `GET /api/v1/tokens/users` (the API roles of users, which SDN-32 keeps under the tokens, since who holds which role is what the tokens say too), `GET /api/v1/audit` or `GET /api/v1/licence` (a `HEAD` of them too) that the API answers with a success is a record of the kind `access`, under the API token that read it (`token:NAME`), or the User of the user token that read it (`user:NAME`, SDN-32), from the address that the call came from, with the call as its action, for example `GET /api/v1/audit`. The query of the call is not in the record. It is written when the call ends, by the same wrapper that records the calls that change something (`api.AuditCalls`), so a read of the audit log does not list its own record. The kind is in `audit.Kinds`: `ranz get audit -kind access` lists the records, and an audit target may name it in its `types`.
- **Only those reads.** Any other read stays unrecorded: the status, `whoami`, the Intent, the nodes, the events, the audit retention and the audit targets. A read that the Guard refuses (a viewer that reads the tokens gets 403) and a read that fails is no access: nothing was shown. They are the list `auditedReads` of `controller/internal/api/accessaudit.go`; a later ticket that audits another read adds a path to it.
- **At most one record a minute for each token and each read.** A read changes nothing and a caller can repeat it as often as it likes, as a page that refreshes itself or a script does. A record for each read would let a viewer fill the log and push the records of changes out of it by the maximum number of records of the retention, which is what the throttle of the failed authentications keeps from happening too. So the Log (`audit.Log`) records the first read of a token of each of the three, and the reads of the same token of the same thing in the minute after it are dropped without an error; the log then says that the token read it and when it began. The Log remembers at most 4096 such pairs, and a read of a new pair is not recorded while the memory is full of reads that are less than a minute old. A read is a path and not a method: a `HEAD` is the same read as a `GET`, so of the two the first in a minute is recorded and the other is dropped (AUD1-DT-19, #506). A viewer can read two of the audited reads, the audit log and the licence, and one that polls both with both methods leaves two records a minute, 1,051,200 a year, under the 2,000,000 of the default retention; with the method in the key it left four, 2,102,400, over it (`TestOneViewerThatPollsLeavesTwoRecordsAMinute`, `TestAViewerThatReadsWithGetAndHeadLeavesOneAccessRecordForEachRead`).

## Amendment 2026-10-29: the life of a node key is announced (SDN-56-R1)

Recorded by SDN-56-R1 (#515), which follows the read-only review of SDN-56 (#249, the key expiry of Nodes, the amendment of ADR-0031 of 2026-10-28). The review found that a key ends in silence: every Node that exists when a Controller first starts with key life gets the same end, 90 days later, to the millisecond, and a Node that nobody marks `nonExpiring` leaves the overlay on that day with no warning. The Controller now says what comes before it does. It adds three Events to decision 5.

- **Three Events.** `node-key-expiring`: the key of a Node ends within 14 days. `node-key-ended`: the key of a Node ended, and the Node is held back (its stream is refused, and the others have no Peer for it) until its User logs in again or an operator refreshes the key. `node-waiting`: a Network whose approval is `manual` holds a new Node until an operator approves it. For each, `node` is the Node resource, `subject` is the User that owns it (left out for a Node that has none), and the message says what is the matter and who ends it, for example `the key of Node "alice-laptop" of User "alice" ends at 2026-01-31T10:00:00Z, in 14 days: its user logs in again to refresh it`, and for a Node that has no owner `the key of Node "files" ends at 2026-01-31T10:00:00Z, in 14 days: an operator refreshes it, or marks the Node nonExpiring`. They are in `event.Types`, so `ranz get events`, the Events page of the web UI, a webhook target that names the type (or none) and the metric `ranz_events_total{type="node-key-expiring"}` (0 from the start) have them as they have any Event.
- **14 days and 3 days.** The Controller raises `node-key-expiring` when a key enters the span of 14 days before its end and again when 3 days are left, and the message gives the days that are left counted up (`in 14 days`, `in 3 days`). Fourteen days are two working weeks, to mark servers `nonExpiring` or to ask users to log in again, and 3 days are the last call before a weekend. A key with no end, the key of a Node marked `nonExpiring`, raises none. The first period is not changed: SDN-56 sets 90 days for every Node and the maintainer approved it, and the harm was the silent end, not the length. A key whose whole period is shorter than the span, in a Network with a `keyLifetimeDays` of 10, is announced when it begins.
- **Once for each key and state.** The mark of what was announced of a key is the column `announced` of its row in `node_keys` (one bit each for the wait, the first and the last warning and the end), written in the same transaction as the Event (`PutNodeKeys` takes the Events beside the lives), so that a restart of the Controller and the next leader of a cluster raise none twice and lose none. A state that ends takes its mark away. The refresh of a key (the login of its User, or an operator) and the approval of a Node begin a period, so the end of the next one is announced again; a Node that its Network no longer holds is no longer waiting; and a Node that is deleted and made again with its key, which the Network holds again, is announced again, since the row of a key that no Node holds loses the mark of the wait together with the approval. The column is in the statement that makes the table: `node_keys` was in no release, and nothing in the store alters a table that exists. A look that finds a key past some of the states of its life announces the one that it is in and not the ones that it missed: a Controller that was down while the span passed announces `node-key-ended`, and one that first looks at a key with 2 days left announces it once. A Node that waits has no life yet, so it raises `node-waiting` once and nothing of its key until it is approved.
- **The first start.** The first start with key life gives each Node a period from that moment, so every Node is announced at the same look, 14 days before the shared end, in the list of Events and in the audit log. One look raises at most 200 Events, ordered by the name of the Node, and the next look goes on with the others, so that a Controller with thousands of Nodes does not hold its lock for all their writes at once.
- **The audit log.** Each Event is also an `operation` record of the audit log under the actor `system`, from `local`, with the type of the Event as its action (`node-key-expiring`, `node-key-ended`, `node-waiting`), `node NAME` as its subject and the message of the Event, a success. It is no call of the API, and the system is the actor that the amendment of 2026-10-23 names for what the Controller does itself. The Event is the condition that operators are told about, and the record is the account of the Controller that it told them. The audit record is written after the Event, and one that cannot be stored is logged and not made again.
- **`ranz node-key list`.** The answer has `daysLeft` beside `expires`: the days that a valid key has left, counted up, left out for a key that has no end, one that ended and one that waits. `-o table` prints one line for each Node (NODE, OWNER, STATE, ENDS, DAYS LEFT).
- **Not here.** A page of the web UI for the keys and approvals. A channel of its own for the warning to the User, such as an email or a message of the tray: the Event is what a webhook target takes today. The keys of Devices (SDN-80), which are not static keys of Nodes.
- **CI.** `controller/internal/controller/nodekeys_events_test.go` runs the controller conformance on a clock that it moves: both warnings and a key with no end that raises none (`TestTheEndOfAKeyIsAnnouncedBeforeItComes`), the end and the wait announced once, across restarts, and again after a refresh and after a new wait (`TestAnEndedKeyAndAWaitingNodeAreAnnouncedOnce`), the first start on a store with Nodes and no lives, in the list of Events and in the audit log (`TestTheFirstStartWithKeyLifeAnnouncesTheSharedDeadline`). `keyevents_internal_test.go` walks the states of one key through `announce`, `store/nodekeys_test.go` the marks and the Events written together, `export/target_test.go` the types of a webhook, and `cmd/ranz/nodekeys_test.go` the list with the days that are left.

## Amendment 2026-10-31: the audit log names the API tokens, and a viewer reads the names (AUD1-DT-15-R1)

Recorded by AUD1-DT-15-R1 (#561), from the review of PR 551 (AUD1-DT-15, #497). The audit log names the API tokens that acted, and a viewer reads the log, so a viewer reads those names.

- **What the log names.** A call that changes something, and each read of the tokens, the audit log or the licence, is recorded under `token:NAME` (`user:NAME` for a user token). Since AUD1-DT-15 a call with the secret of a token after its expiry is an `auth-failed` record under the name of that token, which says when the token ended and where the call came from, so that a leaked token that is tried late shows up as that token and not as an unknown one.
- **What a viewer reads.** `GET /api/v1/audit` needs the role viewer (the amendment of 2026-10-23), so a viewer reads the name of every token that acted or whose secret was tried after its end, and can filter the log by it (`actor=token:NAME`). `GET /api/v1/tokens` is the admin's and refuses a viewer with 403, so a viewer reads names that it cannot list. A name is no secret, and no secret of a token comes into the log.
- **Said, not hidden.** Keeping the names from a viewer is a rule in the Guard (`api.Needs`) that no ADR has. It would have to hide the actor of every record, since a viewer reads `token:NAME` under every change, which is a redesign of the log, and it would take the name out of the record that criterion 2 of #497 asks for, an audit record with the name of the token and the word `expired`. The rows AP-5 and AP-8 of the threat model say what is written here.
