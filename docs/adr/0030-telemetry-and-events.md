# ADR-0030: Telemetry from counters, ETW and controller export, events by webhook

**Status:** Accepted (2026-10-20, from the SDN spec #176 that Hilmi filed; recorded by SDN-1, #177). Follows the ETW and Prometheus rows of ADR-0008.

## Context

The new core has no telemetry. Operators of an SDN need to see who sends what and which rules hit, Windows administrators expect local events in their usual tools, existing monitoring (Prometheus, OpenTelemetry) should pick Ranz up without adapters, and alerts must arrive without polling. The slim fork's web admin plans a Prometheus `/metrics` endpoint on its admin listener (ADR-0021); in the new core the controller is the place where fleet-wide numbers come together (ADR-0026).

## Decision

1. **Counters in the node per peer, per VRF and per policy rule.**
2. **Local node events go to ETW**, so Windows administrators read them with the tools they already use.
3. **Nodes push summaries to the controller** over the control stream (ADR-0027). **The controller exports Prometheus and OTLP.**
4. **IPFIX flow records** are the last telemetry step of v1, for traffic analysis per flow.
5. **Events by webhook:** node down, gateway failover, IPAM pool near exhaustion (ADR-0028) and an automatic rollback (ADR-0031). The same conditions are exported as metrics.

## Consequences

- The controller conformance seam (ADR-0026) checks events and metrics as external behaviour: a scenario that takes a node down or exhausts a pool produces the webhook call and the metric.
- The delivery order of #176 puts telemetry after IPAM and DNS and before the intent API; IPFIX comes last inside telemetry.
- The unified-management spec #224 adds an audit log (SDN-49, #242) and usage reports per user, group and network built from traffic counters (SDN-51, #244).
- Tickets: SDN-16 (#192).

## Amendment 2026-10-23: the audit log (SDN-49)

Recorded by SDN-49 (#242), the audit log that the unified-management spec #224 adds to the telemetry of this ADR (user story 55).

- **An Audit record is not an Event.** The controller keeps an audit log beside the Events of decision 5: one Audit record for each login, logout, failed authentication, enrolment, change of the intent and operation, with its actor, its time, its source, its outcome and, for a change of the intent, the revision that it made. An Event is a condition that operators are told about; an Audit record is the controller's account of who did what. The two have their own tables, their own API and their own targets, so a webhook of events never receives an Audit record.
- **What each kind records today.** `intent-change`: every revision (apply, delete, rollback, import, the first start and the automatic rollback), written by the controller with the revision, under the API token that asked for it or the system; an apply, delete, rollback or import that an API call asked for and that failed is a record with outcome failure, the reason and no revision. `operation`: every other call of the API that changes something (a licence key, an export or audit target, an API token, the retention), with the call as its action, so the live operations of SDN-50 (#243) are audited from the day they exist. `auth-failed`: a call of the API whose bearer token is missing or unknown, a request that the admin source allowlist of SDN-39 refused, and a node whose static key no Node resource holds (its actor is the key, so an operator can write the resource). `enrolment`: the first Hello of a static key, and with the outcome failure a node that a Network refused to enrol because of its source address (`enrolSources`, SDN-39); both refusals are Events as well, and are recorded here as often as the Event is. `login` and `logout`: a control stream of a node that was accepted and that ended; the logins of users and administrators (SDN-32, #226) record themselves as the same kinds through `Controller.RecordAudit`. A controller that closes ends every stream and records no logout for them. A source that fails to authenticate again within 10 seconds is not recorded again, so a caller that guesses tokens cannot fill the store.
- **Export.** An audit target is an export target of its own kind, kept in its own table and managed under `/api/v1/audit/targets`: a `webhook` receives each record as a JSON POST signed with the secret of the target (`X-Ranz-Signature`, the form of the webhook of events), and a `syslog` receiver each record as an RFC 5424 message over UDP, TCP or TLS (the facility is log audit, the severity warning for a failure; over TCP and TLS each message has its length in front of it, RFC 6587 and RFC 5425). A target may name the kinds it wants. The leader sends each target the records in the order they were made and the store keeps the last record each target was sent, so a controller that restarts, or the next leader, goes on where the last one stopped; a target that fails is tried again with a growing wait, and no record is skipped for it. A new target starts at the latest record.
- **Retention.** The leader removes the records older than the retention policy, and the oldest beyond its maximum number, every hour. The policy is `{"days": 365, "maxRecords": 2000000}` until an operator sets another through `/api/v1/audit/retention`; the maximum number is what keeps a flood of failed authentications from filling the disk. The id of a record is never used twice, also after every record was removed, so the record of what a target was sent stays valid.
- **Reading.** `GET /api/v1/audit` lists the records oldest first, with `kind`, `actor`, `since`, `until`, `after` and `limit`. It needs the role viewer, since the API gives every read that role; keeping the audit log from viewers needs a rule in the Guard (`api.Needs`), which is not part of this change. The source of a call that a standby forwarded to the leader is the address of the standby.
- **ETW on the nodes** stays with the node (decision 2): the control message that tells a node what to log, and the C code that writes the events, are not part of this change.

## Amendment 2026-10-24: log retention and the diagnostics bundle (SDN-54)

Recorded by SDN-54 (#247), the retention of logs and the support bundle that the unified-management spec #224 adds (user stories 57 and 58).

- **Log limits.** The log of the Controller service and the log of a Node keep within an age limit and a disk limit, 30 days and 256 MB unless an operator sets others, and 0 is no limit. The Controller takes them from `-log-days` and `-log-mb`; a Node from the settings `LogDays` and `LogMB` of its Configuration store. The writer starts a new file when the current one is full and when a day ends (the Controller's writer moves the file aside under a name with the time, the Node's writer names its files by date and number, as it always did), and the files that it is done with are deleted when their last record is older than the age limit and, oldest first, when they would take the room that the disk limit leaves the file that is open. That file counts as much as its maximum size lets it grow to, and a disk limit makes the maximum size a quarter of it, so a log never takes more than its limit, also not between two files. The limits are applied when the program starts, so limits that are lower than the ones of the last run take effect at once, and every hour while it runs. A file that cannot be deleted, because another program holds it open, stays and is tried again; the file that is open is never deleted. The Controller log is written by `controller/internal/logfile` (the Windows service writes `controller.log` through it; run in the foreground, the Controller logs to its standard error and keeps no file); the Node log by `SetLogLimits` of the log writer (`LogWriter.c`), whose writer thread deletes the files and writes a line of the log for each. The log of the BGP sidecar of a Node (`ranz-bgp.log` in the node log directory) keeps within the same limits: the Node starts the sidecar with `-log-days` and `-log-mb`, and the sidecar of the `ranz` executable writes its log through `controller/internal/logfile` (`ranz-bgp` is not under `controller/`, so it takes the writer through `bgpcmd.OpenLog`, which `controller/cmd/ranz` sets).
- **The diagnostics bundle** is one ZIP archive with the logs, the configuration and the status of a Controller or of a host, and a manifest (`manifest.json`) that lists every part with its size, its hash and the number of secrets that were replaced in it, and names what could not be collected. It is built from sources that each name the parts they give (`controller/internal/bundle`), so that what no source names, the keys, the token file and the stores, is not in it. Every part goes through the redaction: the value of a field whose name holds a secret (password, token, key, hash, salt and the like) in JSON and in text, a secret that has a form of its own (a bearer token, a token of the API, a private key in PEM, a password hash, a password in a URL, a web token) and a JSON document that a line holds as an escaped string, are replaced by `[redacted]`. A part is at most 16 MB and a bundle 48 MB; of the log files, the newest records go in.
- **The bundle of a Controller** is the answer of `POST /api/v1/diagnostics/bundle`: the host and its services, the status, the nodes with their Capabilities, the intent, the revisions, the events, the licence in force, the address pools, and the files of the Controller log with a report of what they take against their limits. It is a POST, since it makes a file at this moment, and so it needs the role operator and is an `operation` in the audit log, under the token that asked; keeping the logs from operators needs a rule in the Guard (`api.Needs`), which is not part of this change. The web UI offers it on the Diagnostics page (the UI action `diagnosticsBundle`), to the roles that may. In a cluster a standby forwards the call, so the bundle is the one of the leader.
- **The bundle of a host** is `ranz doctor --bundle`: the report of the checks, the host and its services, the log files of the Node and of the Controller that run there, and the text dump of the Node's Configuration store (`node_config.txt`, which the Node writes into its data directory at its start; the dump has no password hash and no key). It writes the file given with `-o`, which must not exist yet, or `ranz-host-NAME-TIME.zip` in the current directory.

## Amendment 2026-10-27: a read of the tokens, the audit log or the licence is an access (AUD1-DT-13)

Recorded by AUD1-DT-13 (#461), which closes the audit of reads of gap G-17 of the threat model (AP-8). The audit log recorded every call that changes something and no read, so the log could not say who looked at the API tokens, at the log itself or at the licence.

- **A new kind, `access`.** A read of `GET /api/v1/tokens`, `GET /api/v1/audit` or `GET /api/v1/licence` (a `HEAD` of them too) that the API answers with a success is a record of the kind `access`, under the API token that read it (`token:NAME`), from the address that the call came from, with the call as its action, for example `GET /api/v1/audit`. The query of the call is not in the record. It is written when the call ends, by the same wrapper that records the calls that change something (`api.AuditCalls`), so a read of the audit log does not list its own record. The kind is in `audit.Kinds`: `ranz get audit -kind access` lists the records, and an audit target may name it in its `types`.
- **Only those three reads.** Any other read stays unrecorded: the status, `whoami`, the Intent, the nodes, the events, the audit retention and the audit targets. A read that the Guard refuses (a viewer that reads the tokens gets 403) and a read that fails is no access: nothing was shown. The three are the list `auditedReads` of `controller/internal/api/accessaudit.go`; a later ticket that audits another read adds a path to it.
- **At most one record a minute for each token and each read.** A read changes nothing and a caller can repeat it as often as it likes, as a page that refreshes itself or a script does. A record for each read would let a viewer fill the log and push the records of changes out of it by the maximum number of records of the retention, which is what the throttle of the failed authentications keeps from happening too. So the Log (`audit.Log`) records the first read of a token of each of the three, and the reads of the same token of the same thing in the minute after it are dropped without an error; the log then says that the token read it and when it began. The Log remembers at most 4096 such pairs, and a read of a new pair is not recorded while the memory is full of reads that are less than a minute old.
