# ADR-0031: Declarative intent API with revisions, rollback, explain and three global roles

**Status:** Accepted (2026-10-20, from the SDN spec #176 that Hilmi filed; recorded by SDN-1, #177). The API is served by the controller (ADR-0026); the web UI relates to #44 (ADR-0021).

## Context

ADR-0021 gives the slim fork an RPC-style HTTP API that mirrors the admin RPCs one to one. An SDN needs a different contract: the network described declaratively so it is reproducible and reviewable, every change undoable, a safe way to make risky changes, and a fast answer to "why can't A reach B". The intent has to stay the truth, so imperative commands must not become a second way to configure the network.

## Decision

### Resource model

1. The Intent is a set of declarative resources:
   - `VRF`: id, name, ULA /48, MTU, conntrack quota and timeouts, topology, route-target import and export lists (ADR-0025).
   - `Network`: belongs to one VRF; L3 (Wintun) or L2 (ADR-0014, VLANs per ADR-0019); IPv4 and IPv6 pools (ADR-0028).
   - `Node`: identity, tags, VRF memberships, roles, reported Capabilities and Egress tier (ADR-0033).
   - `Tag`, `Policy` (rules between tags or FQDN sets with protocol and port, priority, action; ADR-0029), `Route` (static or learned), `DnsRecord`, `Endpoint` (service IP and port in a source VRF, consumer VRF), `Mirror` (source selector, filter, sensor IP, rate limit), `Gateway` (egress, LAN prefixes, HA group), and `BgpPeer` and `EvpnPeer` per gateway and per VRF (ADR-0032).
   - The Legacy phase adds `CompatListener` and `LegacyGateway` (ADR-0037).

### Apply, revisions and rollback

2. **A declarative REST/JSON API.** `ranz apply -f` applies a file of resources, `ranz diff` shows the change, `ranz rollback <revision>` returns to an earlier state.
3. **Every apply creates a revision** that can be diffed and rolled back.
4. **`ranz apply --confirm <duration>`** (for example `--confirm 5m`) rolls back by itself unless the administrator confirms in time, so a risky change cannot lock anyone out. An automatic rollback raises an event (ADR-0030).
5. **The controller reconciles desired and actual state and reports status per resource**, so an administrator sees what is applied and what failed.
6. **Imperative calls exist only for debugging.** The declared intent stays the truth.

### Explain

7. **`ranz explain A B` walks the compiled model for a packet from A to B** and names each step: the VRF, the route (with leaking), the NAT and the policy rule.
8. **Explain is checked against the real data plane.** Scenario files (topology, intent, test packets) run twice, through `ranz explain` in the controller and through the data plane in the vpntest harness, and both must give the same verdict for each packet. Explain cannot drift from what forwarding does.

### Roles and clients

9. **Three global roles:** `admin`, `operator` (applies intent, cannot change roles) and `viewer`. There are no per-VRF roles; a multi-tenant layer is out of scope.
10. **The `ranz` CLI and the web UI are clients of the public HTTP API only**, so everything an administrator can click can also be scripted.

### Migration

11. **A one-time importer reads `ranz_server.config`:** each Virtual Hub becomes a VRF with one Network, users and groups become tags, and the access list becomes policy, building on CORE-F5 (#65) and #76. The old core runs side by side until every Hub has moved.

## Consequences

- The new core's administrative surface is this declarative API on the controller, not the RPC-style API of ADR-0021. That departs from ADR-0021's aim of an API contract that survives the core swap; #224 records the slim fork's web admin (#44) as superseded by the controller web UI (SDN-28). ADR-0021 itself is not amended by #176. *(ADR-0021 is superseded since 2026-10-21 by this ADR, ADR-0026 and ADR-0038; see its amendment.)*
- The importer settles the question left open by the ADR-0022 amendment of 2026-10-19 (whether the importer is needed): #176 keeps it, as SDN-27 (#203).
- The unified-management spec #224 (2026-10-21) adds administrators scoped to one Network with quotas and permissions (SDN-38, #231) and a separate operations API for live sessions (SDN-50, #243). The three role names stay; the scope is a Network, not a VRF.
- The controller conformance seam (ADR-0026) covers revisions, rollback, `--confirm` and RBAC; explain conformance is its own suite over shared scenario files.
- Tickets: SDN-13 (#189), SDN-14 (#190), SDN-15 (#191), SDN-27 (#203), SDN-28 (#204).

## Amendment 2026-10-23: source restrictions for the console and for enrolment (SDN-39)

Recorded by SDN-39 (#232), the source-IP restrictions of the unified-management spec #224 (stories 25 and 51). Decisions 9 and 10 hold: there are still three global roles, and the CLI and the web UI are still clients of the public API.

- **The admin source allowlist** is a list of source prefixes (CIDR prefixes or single addresses, at most 256) that the controller's API and web UI accept connections from. It replaces `$adminip.txt` of the slim fork. With no prefix in it, every address is accepted, as before: it is off until an administrator sets it, because a controller on a rented host is often managed from anywhere.
- **It is not an Intent resource.** It lives in the store (table `admin_sources`) and is read and changed through `GET` and `PUT /api/v1/admin-sources`, which need the `admin` role (`ranz admin-sources`; `Needs` names the path beside `/api/v1/tokens`). An operator applies Intent, and must not widen from where the console can be reached; a revision, a rollback or an import must not change it either. A store backup holds it, an Intent export does not.
- **The check stands in front of the API and the web UI, outside the Guard** (`api.Sources`, wired in `ranz-controller`): a request from an address outside the list is answered 403 before anyone looks at its token, so an address outside learns nothing about tokens. Every member of a controller cluster makes the check on the requests it accepts, from the store, which it reads once in 2 s. While the store fails, the list read last stays in force; a member that never read one serves nothing but loopback requests: 503.
- **A loopback address always passes**, before the list is read, so the administrator of the controller's host can always reach it, and `ranz` on that host (`https://127.0.0.1`) works whatever the list says, a damaged one or one that cannot be read included. A controller must not run behind a reverse proxy on its own host, which would make every client look like loopback; it ends its own TLS and shares its port with the control stream (ADR-0035).
- **A change cannot lock its maker out.** A `PUT` of a list that does not hold the address the call came from is refused with 409 Conflict, unless that address is loopback.
- **In a cluster, the list holds the addresses of the members too.** A standby forwards a call to the leader over HTTPS from its own address, which the leader checks like any other. No header of a forwarded call is trusted for the address of the first caller: a client could set it and skip the check.
- **Each refusal and each change is an Event** (`admin-access-refused` with the method, the path and the address; `admin-sources-changed` with the API token that made the change). An Event is a write through the Raft log of the store, so a client that is refused again and again must not make one per request: `event.Throttle` records a source once a minute and 30 sources at most in a minute, and the next record carries the count of the refusals it left out. The audit log of SDN-49 (#242) records failed authentications and enrolments too; these Events are the records until it exists.
- **Enrolment sources.** A Network may carry `enrolSources`, the source prefixes that its Nodes may open their control stream from. The controller checks the address of every control stream against every Network of the VRFs of its node, once the node's key is known and before the node reports its Capabilities or gets any state. One Network that does not hold the address refuses the node: `REFUSE_REASON_UNKNOWN_NODE`, the one reason of the control protocol for a node that is not admitted, with a message that names the address and the Network. The refusal is an Event too (`enrolment-refused`), throttled in the same way. A change of the Intent that tightens `enrolSources` refuses the streams that it no longer allows at once.
- **The check is made at every stream, not only the first.** The Intent holds no record that a node enrolled, and a stolen node key then does not work from another network. A node that moves to another address must be allowed in, or its Network lists no source prefix. `enrolSources` stays on the controller: it is no part of a node's desired state, so changing it gives no node a new Generation.

## Amendment 2026-10-25: users and groups as Intent resources (SDN-31)

Recorded by SDN-31 (#225), the identity resources of the unified-management spec #224 (stories 1 to 6). Decisions 9 and 10 hold: there are still three global roles, and the CLI and the web UI are still clients of the public API. The resource list of decision 1 gains `User` and `Group`.

- **Two resources.** A `Group` has a name and an optional `displayName`. A `User` has a `displayName`, its `groups`, an expiry (`expires`, an RFC 3339 time, in UTC to the second once the Controller has completed it), `mayChangePassword` (true when it is left out), `maxDevices` (0 or left out: no limit) and `noSavedPassword`. They are the user fields of the slim fork: the expiry of a user, `FixPassword`, `MultiLogins` and `NoSavePassword`. A name is a DNS label, as for every resource, so a user whose login name is no DNS label needs a name of its own when the identity providers of #224 come. A User holds no API role. The logins of SDN-32 (#226) decide which users manage the Controller, and the Guard keeps the three roles of decision 9. The expiry of API tokens and their in-place role change, which the decision of 2026-10-22 ties to those logins, are SDN-32's, not done here.
- **Groups become policy tags.** The name of a Group is a tag. A Node names its owner (`Node.owner`, a User), and its tags are its own and the name of every Group of that User (`intent.NodeTags`). They are the tags of the Node's own object, of the Peer object that every other Node holds of it, of the rules it gets (ADR-0029 amendment of 2026-10-25: "users and groups add identities to the members and the ends") and of the selection of a Mirror. A rule written for a Group so applies to the devices of its members, and the control protocol does not change. A Node carries at most 16 tags, its own and its owner's together, the size of `NodeConfig.tags` and `Peer.tags` in `control.options`: an intent that gives one more is refused, for a Node without an owner too, which the 16 of a Policy end did not cover before.
- **Devices and the maximum.** The devices of a User are the resources that name it as their owner (`intent.DevicesOf`): the Nodes today. The WireGuard Devices of #374 add a loop of their own there, so the maximum counts them, and the self-service portal of #251 lists them from the same place; neither is built here. `maxDevices` is a property of the Intent, not of a login: an intent that holds more devices of a user than its maximum is refused when it is applied or imported, with a message that names the devices, so the enrolment of SDN-32 and the portal meet the same refusal as `ranz apply`. Lowering the maximum below the devices that exist is refused the same way. A User that owns a Node and a Group that a User belongs to cannot be deleted.
- **Passwords are not Intent resources.** They are kept in the table `user_passwords` of the store, one hash for each User, for the reasons that API tokens are: a viewer reads the Intent and must not hold a hash, an export and a revision would carry it, and a rollback would change a password. The hash is PBKDF2-HMAC-SHA256 with 600000 iterations and a salt of 16 random bytes for each password, written as the PHC string `$pbkdf2-sha256$i=...$salt$hash`, so the count can be raised later, as the Configuration store of a Node does (ADR-0022 amendment of 2026-10-19). The derivation is CNG (`BCryptDeriveKeyPBKDF2`) on Windows and the Go standard library elsewhere, which give the same bytes, so a store backup moves between them. A password has at least 8 characters and at most 256 bytes. The store backup holds the hashes, an Intent export does not: an import into another Controller makes users that have no password until an administrator sets one. A change of the Intent that removes a User (a delete, a rollback, an import, an automatic rollback) deletes its hash, so a User made again under the name starts with none.
- **Authentication.** `Controller.AuthenticateUser` checks a login: the password first, in constant time and with the work of a derivation also for a name that no User has, so the refusal and its time tell nothing of which names exist; then the expiry, so a User past its `expires` cannot authenticate (`ErrUserExpired`, told only to the holder of the right password). SDN-32 builds the login endpoints on it, with the rate limits and the audit records of failed logins.
- **May change password and no saved password.** `mayChangePassword` is enforced where a user changes its own password (`ChangeUserPassword`: the current password, then the flag): false is `ErrPasswordFixed`. An administrator sets the password of any user, whatever the flag says, with `PUT /api/v1/users/{name}/password`. `noSavedPassword` is enforced where a client keeps a password: a login says whether the client took the password from its own storage (`Login.Saved`), the Controller refuses that login (`ErrSavedPassword`), and the answer of a login carries the flag, as the SE-VPN login of the slim fork told its client not to keep the password. Neither flag is part of a node's desired state.
- **API and CLI.** `GET /api/v1/users` and `/api/v1/groups` (viewer) list them, with the devices of each user, whether it has a password, and the members of each group; `PUT` and `DELETE` of `/api/v1/users/{name}` and `/api/v1/groups/{name}` (operator) make, change and delete them, each a revision of the Intent, like an apply of the same resource; `PUT /api/v1/users/{name}/password` (operator) sets a password. `ranz user list|set|password|delete` and `ranz group list|set|delete` call them. `ranz user password` reads the password from a file or standard input, never from an argument. When SDN-32 gives a User an API role, setting the password of such a User must need the admin role, since it would change who may manage the Controller.
- **Not here.** Session profiles on users and groups (SDN-40), identity providers and users that come from them (SDN-34 to SDN-36), banning a user (SDN-50), and the roles and scopes of administrators (SDN-38).

## Amendment 2026-10-27: the admin destination lists (AUD1-DT-9)

Recorded by AUD1-DT-9 (#457), which closes gaps AP-6 and AP-7 of the threat model (G-16). Decisions 9 and 10 hold: there are still three global roles, and the CLI and the web UI are still clients of the public API. An operator applies Intent and makes export targets, and until now could point the Controller at any host (a webhook, OTLP, IPFIX or syslog target), copy the traffic of a VRF to any address (a Mirror), have a Node reach any UNC path (a Listener) and shorten the audit log. Now the admin owns the lists of what these may name, and the operator works inside them.

- **Three lists, like the admin source allowlist.** The target hosts, the sensor prefixes and the UNC servers (`intent.Destinations`) live in the store (table `admin_destinations`, one row for each entry), not in the Intent: an operator must not widen them, and a revision, a rollback or an import never changes them. A store backup holds them, an Intent export does not. They are read and changed through `GET` and `PUT /api/v1/admin-destinations`, which need the `admin` role (`ranz admin-destinations list|set`; `Needs` names the path beside `/api/v1/tokens` and `/api/v1/admin-sources`). An entry of the target hosts and of the UNC servers is a DNS name, a prefix or an address; an entry of the sensor prefixes is a prefix or an address; each list holds 256 entries at most. A change is an Event (`admin-destinations-changed` with the API token that made it). The lists are empty until an admin sets them.
- **Targets.** A target of events, metrics or flow records, and an audit target, must not name an address that is loopback, link-local (the metadata service of a cloud host), unspecified, or the store of the Controller (whose HTTP port asks for no credential), unless the admin lists the host or a prefix that holds it. Any other address needs no entry. The check is made twice (`export.Guard`): when a target is made, where the name is resolved and each address of it checked and a refusal is 400 Bad Request, and at every connection, where the name is looked up again, each address is checked and the connection goes to an address that was checked, with a second check at the socket, so a name that answers with another address when it is used, and a target stored before the list changed, get no connection. A connection that stays open (IPFIX over UDP or TCP) is checked again before each write. The exporters use no proxy, follow no redirect and keep no connection between calls, so each call meets the list as it is then. The Guard reads the target hosts from the store once in 2 s, and a store that cannot be read refuses the connection. A name that the admin lists is trusted for what it resolves to.
- **Mirrors and Listeners.** An apply, an import and a rollback are refused with 400 Bad Request, naming the resources, when the intent they make holds a Mirror whose sensor is outside every sensor prefix, or a Listener whose certificate file, password file or ACME CA file is a UNC path (`\\server\share`, `\\?\UNC\server\share`) to a server that the admin does not list. A path of the device namespace of Windows that names no server is refused the same way. With no prefix and no server listed, no Mirror and no UNC path is allowed. Only what the change adds is refused: a Mirror that the intent in force holds, and that a later change of the lists left outside, does not keep an operator from changing anything else, and the automatic rollback of an unconfirmed apply is not checked. A path on a drive is not a UNC path.
- **Audit.** `PUT /api/v1/audit/retention` and every call on `/api/v1/audit/targets`, the list included, need the `admin` role, since both decide whether the trail of an operator survives. `GET /api/v1/audit` and `GET /api/v1/audit/retention` stay with the viewer. `TestRegisteredRolesMatchNeeds` holds each route to what `Needs` says.
- **What stays with the operator.** The export targets (`/api/v1/targets`) and the Intent, inside the lists. Question 2 of the threat model, what else moves to admin, is not decided here.
