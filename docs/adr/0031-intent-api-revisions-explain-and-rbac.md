# ADR-0031: Declarative intent API with revisions, rollback, explain and three global roles

**Status:** Accepted (2026-10-20, from the SDN spec #176 that Hilmi filed; recorded by SDN-1, #177). The API is served by the controller (ADR-0026); the web UI relates to #44 (ADR-0021).

## Context

ADR-0021 gives the slim fork an RPC-style HTTP API that mirrors the admin RPCs one to one. An SDN needs a different contract: the network described declaratively so it is reproducible and reviewable, every change undoable, a safe way to make risky changes, and a fast answer to "why can't A reach B". The intent has to stay the truth, so imperative commands must not become a second way to configure the network.

## Decision

### Resource model

1. The Intent is a set of declarative resources:
   - `VRF`: id, name, ULA /48, MTU, conntrack quota and timeouts, topology, route-target import and export lists (ADR-0025).
   - `Network`: belongs to one VRF; L3 (Wintun) or L2 (ADR-0014, VLANs per ADR-0019); IPv4 and IPv6 pools (ADR-0028).
   - `Node`: identity, tags, VRF memberships, roles, reported Capabilities and Egress tier (ADR-0033).
   - `Tag`, `Policy` (rules between tags or FQDN sets with protocol and port, priority, action; ADR-0029), `Route` (static or learned), `DnsRecord`, `Endpoint` (service IP and port in a source VRF, consumer VRF), `Mirror` (source selector, filter, sensor IP, rate limit), `Gateway` (egress, LAN prefixes, HA group), and `BgpPeer` and `EvpnPeer` per gateway and per VRF (ADR-0032).
   - The Legacy phase adds `CompatListener` and `LegacyGateway` (ADR-0037).

### Apply, revisions and rollback

2. **A declarative REST/JSON API.** `ranz apply -f` applies a file of resources, `ranz diff` shows the change, `ranz rollback <revision>` returns to an earlier state.
3. **Every apply creates a revision** that can be diffed and rolled back.
4. **`ranz apply --confirm <duration>`** (for example `--confirm 5m`) rolls back by itself unless the administrator confirms in time, so a risky change cannot lock anyone out. An automatic rollback raises an event (ADR-0030).
5. **The controller reconciles desired and actual state and reports status per resource**, so an administrator sees what is applied and what failed.
6. **Imperative calls exist only for debugging.** The declared intent stays the truth.

### Explain

7. **`ranz explain A B` walks the compiled model for a packet from A to B** and names each step: the VRF, the route (with leaking), the NAT and the policy rule.
8. **Explain is checked against the real data plane.** Scenario files (topology, intent, test packets) run twice, through `ranz explain` in the controller and through the data plane in the vpntest harness, and both must give the same verdict for each packet. Explain cannot drift from what forwarding does.

### Roles and clients

9. **Three global roles:** `admin`, `operator` (applies intent, cannot change roles) and `viewer`. There are no per-VRF roles; a multi-tenant layer is out of scope. *(Since SDN-38, #231, each of the three roles can also be held for one Network, which is a Network and not a VRF: see the amendment of 2026-10-29 on roles held for one Network. "Global" then means held for the whole API.)*
10. **The `ranz` CLI and the web UI are clients of the public HTTP API only**, so everything an administrator can click can also be scripted.

### Migration

11. **A one-time importer reads `ranz_server.config`:** each Virtual Hub becomes a VRF with one Network, users and groups become tags, and the access list becomes policy, building on CORE-F5 (#65) and #76. The old core runs side by side until every Hub has moved.

## Consequences

- The new core's administrative surface is this declarative API on the controller, not the RPC-style API of ADR-0021. That departs from ADR-0021's aim of an API contract that survives the core swap; #224 records the slim fork's web admin (#44) as superseded by the controller web UI (SDN-28). ADR-0021 itself is not amended by #176. *(ADR-0021 is superseded since 2026-10-21 by this ADR, ADR-0026 and ADR-0038; see its amendment.)*
- The importer settles the question left open by the ADR-0022 amendment of 2026-10-19 (whether the importer is needed): #176 keeps it, as SDN-27 (#203).
- The unified-management spec #224 (2026-10-21) adds administrators scoped to one Network with quotas and permissions (SDN-38, #231) and a separate operations API for live sessions (SDN-50, #243). The three role names stay; the scope is a Network, not a VRF.
- The controller conformance seam (ADR-0026) covers revisions, rollback, `--confirm` and RBAC; explain conformance is its own suite over shared scenario files.
- Tickets: SDN-13 (#189), SDN-14 (#190), SDN-15 (#191), SDN-27 (#203), SDN-28 (#204).

## Amendment 2026-10-23: source restrictions for the console and for enrolment (SDN-39)

Recorded by SDN-39 (#232), the source-IP restrictions of the unified-management spec #224 (stories 25 and 51). Decisions 9 and 10 hold: there are still three global roles, and the CLI and the web UI are still clients of the public API.

- **The admin source allowlist** is a list of source prefixes (CIDR prefixes or single addresses, at most 256) that the controller's API and web UI accept connections from. It replaces `$adminip.txt` of the slim fork. With no prefix in it, every address is accepted, as before: it is off until an administrator sets it, because a controller on a rented host is often managed from anywhere. *(Since AUD1-DT-6, #454, `ranz install --controller` has the first start set it to loopback and the private subnets of the host, or to the prefixes of `--admin-from`, and `--admin-from any` keeps it off; see the amendment of ADR-0034. A controller that is run without `-admin-from` still starts with it off.)*
- **It is not an Intent resource.** It lives in the store (table `admin_sources`) and is read and changed through `GET` and `PUT /api/v1/admin-sources`, which need the `admin` role (`ranz admin-sources`; `Needs` names the path beside `/api/v1/tokens`). An operator applies Intent, and must not widen from where the console can be reached; a revision, a rollback or an import must not change it either. A store backup holds it, an Intent export does not.
- **The check stands in front of the API and the web UI, outside the Guard** (`api.Sources`, wired in `ranz-controller`): a request from an address outside the list is answered 403 before anyone looks at its token, so an address outside learns nothing about tokens. Every member of a controller cluster makes the check on the requests it accepts, from the store, which it reads once in 2 s. While the store fails, the list read last stays in force; a member that never read one serves nothing but loopback requests: 503.
- **A loopback address always passes**, before the list is read, so the administrator of the controller's host can always reach it, and `ranz` on that host (`https://127.0.0.1`) works whatever the list says, a damaged one or one that cannot be read included. A controller must not run behind a reverse proxy on its own host, which would make every client look like loopback; it ends its own TLS and shares its port with the control stream (ADR-0035).
- **A change cannot lock its maker out.** A `PUT` of a list that does not hold the address the call came from is refused with 409 Conflict, unless that address is loopback.
- **In a cluster, the list holds the addresses of the members too.** A standby forwards a call to the leader over HTTPS from its own address, which the leader checks like any other. No header of a forwarded call is trusted for the address of the first caller: a client could set it and skip the check.
- **Each refusal and each change is an Event** (`admin-access-refused` with the method, the path and the address; `admin-sources-changed` with the API token that made the change). An Event is a write through the Raft log of the store, so a client that is refused again and again must not make one per request: `event.Throttle` records a source once a minute and 30 sources at most in a minute, and the next record carries the count of the refusals it left out. The audit log of SDN-49 (#242) records failed authentications and enrolments too; these Events are the records until it exists.
- **Enrolment sources.** A Network may carry `enrolSources`, the source prefixes that its Nodes may open their control stream from. The controller checks the address of every control stream against every Network of the VRFs of its node, once the node's key is known and before the node reports its Capabilities or gets any state. One Network that does not hold the address refuses the node: `REFUSE_REASON_UNKNOWN_NODE`, the one reason of the control protocol for a node that is not admitted, with a message that names the address and the Network. The refusal is an Event too (`enrolment-refused`), throttled in the same way. A change of the Intent that tightens `enrolSources` refuses the streams that it no longer allows at once.
- **The check is made at every stream, not only the first.** The Intent holds no record that a node enrolled, and a stolen node key then does not work from another network. A node that moves to another address must be allowed in, or its Network lists no source prefix. `enrolSources` stays on the controller: it is no part of a node's desired state, so changing it gives no node a new Generation.

## Amendment 2026-10-25: users and groups as Intent resources (SDN-31)

Recorded by SDN-31 (#225), the identity resources of the unified-management spec #224 (stories 1 to 6). Decisions 9 and 10 hold: there are still three global roles, and the CLI and the web UI are still clients of the public API. The resource list of decision 1 gains `User` and `Group`.

- **Two resources.** A `Group` has a name and an optional `displayName`. A `User` has a `displayName`, its `groups`, an expiry (`expires`, an RFC 3339 time, in UTC to the second once the Controller has completed it), `mayChangePassword` (true when it is left out), `maxDevices` (0 or left out: no limit) and `noSavedPassword`. They are the user fields of the slim fork: the expiry of a user, `FixPassword`, `MultiLogins` and `NoSavePassword`. A name is a DNS label, as for every resource, so a user whose login name is no DNS label needs a name of its own when the identity providers of #224 come. A User holds no API role. The logins of SDN-32 (#226) decide which users manage the Controller, and the Guard keeps the three roles of decision 9. The expiry of API tokens and their in-place role change, which the decision of 2026-10-22 ties to those logins, are SDN-32's, not done here.
- **Groups become policy tags.** The name of a Group is a tag. A Node names its owner (`Node.owner`, a User), and its tags are its own and the name of every Group of that User (`intent.NodeTags`). They are the tags of the Node's own object, of the Peer object that every other Node holds of it, of the rules it gets (ADR-0029 amendment of 2026-10-25: "users and groups add identities to the members and the ends") and of the selection of a Mirror. A rule written for a Group so applies to the devices of its members, and the control protocol does not change. A Node carries at most 16 tags, its own and its owner's together, the size of `NodeConfig.tags` and `Peer.tags` in `control.options`: an intent that gives one more is refused, for a Node without an owner too, which the 16 of a Policy end did not cover before.
- **Devices and the maximum.** The devices of a User are the resources that name it as their owner (`intent.DevicesOf`): the Nodes today. The WireGuard Devices of #374 add a loop of their own there, so the maximum counts them, and the self-service portal of #251 lists them from the same place; neither is built here. `maxDevices` is a property of the Intent, not of a login: an intent that holds more devices of a user than its maximum is refused when it is applied or imported, with a message that names the devices, so the enrolment of SDN-32 and the portal meet the same refusal as `ranz apply`. Lowering the maximum below the devices that exist is refused the same way. A User that owns a Node and a Group that a User belongs to cannot be deleted.
- **Passwords are not Intent resources.** They are kept in the table `user_passwords` of the store, one hash for each User, for the reasons that API tokens are: a viewer reads the Intent and must not hold a hash, an export and a revision would carry it, and a rollback would change a password. The hash is PBKDF2-HMAC-SHA256 with 600000 iterations and a salt of 16 random bytes for each password, written as the PHC string `$pbkdf2-sha256$i=...$salt$hash`, so the count can be raised later, as the Configuration store of a Node does (ADR-0022 amendment of 2026-10-19). The derivation is CNG (`BCryptDeriveKeyPBKDF2`) on Windows and the Go standard library elsewhere, which give the same bytes, so a store backup moves between them. A password has at least 8 characters and at most 256 bytes. The store backup holds the hashes, an Intent export does not: an import into another Controller makes users that have no password until an administrator sets one. A change of the Intent that removes a User (a delete, a rollback, an import, an automatic rollback) deletes its hash, so a User made again under the name starts with none.
- **Authentication.** `Controller.AuthenticateUser` checks a login: the password first, in constant time and with the work of a derivation also for a name that no User has, so the refusal and its time tell nothing of which names exist; then the expiry, so a User past its `expires` cannot authenticate (`ErrUserExpired`, told only to the holder of the right password). SDN-32 builds the login endpoints on it, with the rate limits and the audit records of failed logins.
- **May change password and no saved password.** `mayChangePassword` is enforced where a user changes its own password (`ChangeUserPassword`: the current password, then the flag): false is `ErrPasswordFixed`. An administrator sets the password of any user, whatever the flag says, with `PUT /api/v1/users/{name}/password`. `noSavedPassword` is enforced where a client keeps a password: a login says whether the client took the password from its own storage (`Login.Saved`), the Controller refuses that login (`ErrSavedPassword`), and the answer of a login carries the flag, as the SE-VPN login of the slim fork told its client not to keep the password. Neither flag is part of a node's desired state.
- **API and CLI.** `GET /api/v1/users` and `/api/v1/groups` (viewer) list them, with the devices of each user, whether it has a password, and the members of each group; `PUT` and `DELETE` of `/api/v1/users/{name}` and `/api/v1/groups/{name}` (operator) make, change and delete them, each a revision of the Intent, like an apply of the same resource; `PUT /api/v1/users/{name}/password` (operator) sets a password. `ranz user list|set|password|delete` and `ranz group list|set|delete` call them. `ranz user password` reads the password from a file or standard input, never from an argument. When SDN-32 gives a User an API role, setting the password of such a User must need the admin role, since it would change who may manage the Controller.
- **Not here.** Session profiles on users and groups (SDN-40), identity providers and users that come from them (SDN-34 to SDN-36), banning a user (SDN-50), and the roles and scopes of administrators (SDN-38).

## Amendment 2026-10-27: the admin destination lists (AUD1-DT-9)

Recorded by AUD1-DT-9 (#457), which closes gaps AP-6 and AP-7 of the threat model (G-16). Decisions 9 and 10 hold: there are still three global roles, and the CLI and the web UI are still clients of the public API. An operator applies Intent and makes export targets, and until now could point the Controller at any host (a webhook, OTLP, IPFIX or syslog target), copy the traffic of a VRF to any address (a Mirror), have a Node reach any UNC path (a Listener) and shorten the audit log. Now the admin owns the lists of what these may name, and the operator works inside them.

- **Three lists, like the admin source allowlist.** The target hosts, the sensor prefixes and the UNC servers (`intent.Destinations`) live in the store (table `admin_destinations`, one row for each entry), not in the Intent: an operator must not widen them, and a revision, a rollback or an import never changes them. A store backup holds them, an Intent export does not. They are read and changed through `GET` and `PUT /api/v1/admin-destinations`, which need the `admin` role (`ranz admin-destinations list|set`; `Needs` names the path beside `/api/v1/tokens` and `/api/v1/admin-sources`). An entry of the target hosts and of the UNC servers is a DNS name, a prefix or an address; an entry of the sensor prefixes is a prefix or an address; each list holds 256 entries at most. A change is an Event (`admin-destinations-changed` with the API token that made it). The lists are empty until an admin sets them.
- **Targets.** A target of events, metrics or flow records, and an audit target, must not name an address that is loopback, link-local (the metadata service of a cloud host), unspecified, or the store of the Controller (whose HTTP port asks for no credential), unless the admin lists the host or a prefix that holds it. Any other address needs no entry. The check is made twice (`export.Guard`): when a target is made, where the name is resolved and each address of it checked and a refusal is 400 Bad Request, and at every connection, where the name is looked up again, each address is checked and the connection goes to an address that was checked, with a second check at the socket, so a name that answers with another address when it is used, and a target stored before the list changed, get no connection. A connection that stays open (IPFIX over UDP or TCP) is checked again before each write. The exporters use no proxy, follow no redirect and keep no connection between calls, so each call meets the list as it is then. The Guard reads the target hosts from the store once in 2 s, and a store that cannot be read refuses the connection. A name that the admin lists is trusted for what it resolves to.
- **Mirrors and Listeners.** An apply, an import and a rollback are refused with 400 Bad Request, naming the resources, when the intent they make holds a Mirror whose sensor is outside every sensor prefix, or a Listener whose certificate file, password file or ACME CA file is a UNC path (`\\server\share`, `\\?\UNC\server\share`) to a server that the admin does not list. A path of the device namespace of Windows that names no server is refused the same way. With no prefix and no server listed, no Mirror and no UNC path is allowed. Only what the change adds is refused: a Mirror that the intent in force holds, and that a later change of the lists left outside, does not keep an operator from changing anything else, and the automatic rollback of an unconfirmed apply is not checked. A path on a drive is not a UNC path.
- **Audit.** `PUT /api/v1/audit/retention` and every call on `/api/v1/audit/targets`, the list included, need the `admin` role, since both decide whether the trail of an operator survives. `GET /api/v1/audit` and `GET /api/v1/audit/retention` stay with the viewer. `TestRegisteredRolesMatchNeeds` holds each route to what `Needs` says.
- **What stays with the operator.** The export targets (`/api/v1/targets`) and the Intent, inside the lists. Question 2 of the threat model, what else moves to admin, is not decided here.

## Amendment 2026-10-27: the live operations (SDN-50)

Recorded by SDN-50 (#243), the operations API of the unified-management spec #224 (user stories 52 to 54). Decisions 9 and 10 hold: there are still three global roles, and the CLI is still a client of the public API. Decision 6 holds too: these are the imperative calls, they change nothing that the Intent holds, and a revision, a rollback or an import never undoes them.

- **One path, one role.** The calls are under `/api/v1/operations`, and `Needs` gives every one of them the role operator, the reads too: a viewer reads the Intent, and who is connected from where, and what a node learnt of the members of a Network, is more than the Intent says. An admin passes, as it passes every call of an operator. The calls are `GET /sessions` (the query `user` and `node` narrow it), `POST /sessions/{id}/disconnect`, `POST /users/{name}/disconnect`, `GET /bans`, `PUT /bans/{name}` (an optional body `{"reason": "..."}`), `DELETE /bans/{name}`, and `GET` and `DELETE` of `/networks/{network}/mac-table` and `/networks/{network}/ip-table` (the query `node`, and for a `DELETE` the one entry to remove, `mac` or `address`). A query that names a parameter that the call does not take is 400, so that a misspelt narrowing does not widen the call. `ranz session list|disconnect`, `ranz ban list|set|clear`, `ranz mac-table [clear]` and `ranz ip-table [clear]` call them.
- **A session is a control stream.** It is the control stream of a node, from the moment the Controller accepts it until it ends, and it has an id of its own (16 hex digits from `crypto/rand`), so a node that dials again has another. The list gives, for each, the node, its user (the owner of the Node resource), the address that the stream came from, since when, the VRFs of the node, its addresses in the Networks of them, its Generation and the one that it acknowledged, whether it reports the Capability `operations`, and its traffic: the sum over its VRFs of the counters of the last summary that it sent (ADR-0030), which is 0 until it sent one. The sessions of a Device (WireGuard, SDN-80) are not control streams and are not listed.
- **A disconnect is at once.** The Controller detaches the node from its stream, so the node is no longer `Connected` when the call answers, and has the stream send a Refuse with the new reason `REFUSE_REASON_OPERATOR` and close. A disconnect alone does not keep the node off: it dials again after the delay of a refused stream (the C node doubles it up to 60 s), unless its user is banned. `POST /users/{name}/disconnect` does it for every session of the nodes that the user owns, and answers with none for a user with no node connected.
- **A ban keeps a user off.** A ban names a User of the Intent and has the time, the token that made it and a reason, which is optional, UTF-8 with no control character and at most 256 bytes. It lives in the store (table `user_bans`), not in the Intent, for the reason that the admin source allowlist does: a revision, a rollback or an import must not lift it. A store backup holds it, an Intent export does not. It goes with the User: a change of the Intent that removes the User deletes its ban, as it deletes its password, so a User made again under the name starts with none. Banning a user:
  - ends every session of the nodes that the user owns at once, with the Refuse above, which says `User "alice" is banned` and the reason, and refuses every stream that they open later, before their Capabilities are looked at; each refusal is an `auth-failed` audit record, throttled as every failed authentication is (one for a source in 10 s);
  - gives each Node that had a Peer for a node of the user a new Generation without it, compiled from the Intent as if the nodes of the banned users were not in it, so that no other node has a Peer, a Relay or a route that leads to one of them, and none takes a packet of theirs while it runs on; the nodes of the banned user keep their own state and their own Generations, so that the first Generation after an unban follows the ones that they applied, as it does for a node that was never banned;
  - makes `AuthenticateUser` answer `ErrUserBanned` for a login with the right password, after the expiry is checked and told only to the holder of the password, as the expiry is.

  An unban gives the nodes of the user their place in the desired state of the others, and they open their streams again by themselves. A ban of a user that is banned already changes nothing and answers with the first ban; an unban of a user that is not banned is 404. A user that the Intent does not hold cannot be banned (404). The ban is of a User, never of a Node: the devices of the user follow it.
- **The tables are asked of the nodes.** The MAC table and the IP table of an L2 Network are held by the nodes that run it. The Controller sends each node that holds the Network and reports the Capability `operations` an `Operation` on its control stream, with an id of its own, and the node answers with an `OperationResult` of the same id (ADR-0027 amendment of 2026-10-27). The call names the Network, and a node to ask one only; with none it asks every node that holds the Network, at most 32, so a Network on more needs the call to name a node. A clear takes every entry, or the one that `mac` or `address` names. The answer has a result for each node with a status of its own, `ok`, `not-connected`, `unsupported` (the node reports no Capability `operations`, so it was not asked), `no-network`, `failed` or `timeout` (the Controller waits 10 s, `Config.OperationTimeout`), because a node that is down or does not answer must not hide what the others say. The call is 200 when it could be made, and its audit record is a failure when a node did not do what was asked, and so is the exit code of `ranz mac-table` and `ranz ip-table`. A table is listed with at most 512 entries and with its total, ordered by VLAN and then by address; an entry that is not well formed is left out and counted in the message, and the time of the last frame of an entry is left out when the node gives none or one after the year 9999, which JSON cannot write (one such entry would leave the whole answer empty). An L3 Network has no table (400), and a Network or a node that does not exist is 404.
- **Every operation is in the audit log.** The Controller records each call as an `operation` record by itself (ADR-0030 amendment of 2026-10-27), the reads too, under the token that made the call and from its source. The action is `session-list`, `session-disconnect`, `user-disconnect`, `ban-list`, `user-ban`, `user-unban`, `mac-table`, `mac-table-clear`, `ip-table` or `ip-table-clear`, the subject is what it was done to, and the message says what it did: the sessions that it ended, or the status of each node. A call that fails, for a user, a session or a Network that does not exist too, is a record with the outcome failure and the reason. `AuditCalls` does not record these paths a second time.
- **Scope.** The spec allows the operations to the roles operator and admin within scope. The scope that exists today is the three global roles: a viewer is refused every call (403), and a call is refused (400 or 404) for what it names and the Intent does not hold or does not allow, such as an L3 Network, a node that is not a member of the Network, or a user or a session that does not exist. SDN-38 (#231) scopes administrators to a Network and will narrow these calls by the Network that each names, or that the node or the user of each belongs to; a table call already names it in its path. None of that is built here. *(SDN-38 did not narrow these calls. A role held for one Network is refused every path outside its own Network, these calls included, and has calls of its own for the sessions of its Nodes: see the amendment of 2026-10-29 on roles held for one Network.)*
- **Not here.** A page of the web UI for the operations. The answer of the C node: `src/Core/Control.c` ends the stream on a frame that it does not know, so the node reports no Capability `operations` yet and is sent no Operation, and reading and clearing the tables of the L2 switch of a Node is for the node ticket that follows. The disconnect of a Device. Session limits, idle timeouts and the automatic disconnect (SDN-40), and the usage reports (SDN-51).

## Amendment 2026-10-27: explain and its conformance (SDN-15)

Recorded by SDN-15 (#191), which builds decisions 7 and 8. Decision 10 holds: `ranz explain` is a client of the public API.

- **The model that explain walks** is the desired state of each Node that the licence in force covers, as the Controller sends it (`internal/explain`), with the intent only to name what the states hold by number: the VRF that a leaked route comes from, the route targets of a leak and the NAT resource of a 1:1 NAT rule. The walk follows the data plane of a Node (`NodeOverlay.c` with `NodeLeak.c`, `NodeNat.c` and `NodePolicy.c`) check for check: at the sender its 1:1 NAT rules, its own source, the longest-prefix route of the destination (of two routes of one prefix the one of the greater next hop, the host first), the policy of the VRF on the way out and the link; at the Node that the route leads to the VRF that the record names, the route of the source back to the sender (so a leak carries traffic both ways only), its own destination, the policy of the VRF on the way in, which sees the sender of leaked traffic as the end outside the VRF, and its 1:1 NAT rules. The packet is the first of a flow; the rule that judges it is the first by priority, a deny rule before an allow rule of one priority, then by name, or the default action `default:deny`, the names that the counters of the policy engine use.
- **The API and the CLI.** `GET /api/v1/explain?from=A&to=B` (viewer, with `vrf`, `protocol`, `sourcePort` and `port`) answers each step (VRF, route, NAT, link, policy) with its text and the verdict: delivered to a host in a VRF with the addresses that it sees, or dropped by a Node for its route, NAT, link or policy. A is a Node, a WireGuard Device or an address of either, B a Node, a Device or an address; a Node as B is the address of it that the VRF of A leads to it, so the outside of its 1:1 NAT rule when only that leaks. `ranz explain [flags] A B` is a subcommand that calls it, with the connection flags of the CLI. The link of a step says whether it encrypts: a link of kind vxlan or geneve is unencrypted (SDN-76, #356); and it shows the endpoints of its two Nodes, where each is dialled (SDN-93, #410).
- **The conformance suite.** A scenario of `tests/explain` is a topology (each Node and the first byte of the scalar of its static key), an intent and test packets, each with its verdict: where it ends and the rule that judged it at each Node. The Go tests run every scenario through the walk and through `GET /api/v1/explain` of a Controller. `ranz-explainplan`, a test tool, writes the plan of each scenario: the state of each Node as the ControlMessage of its Update, and each packet as its host sends it with the verdict of explain. `vpntest explain` runs the plans through real Nodes, which take their states from a stand-in controller over their own control streams, sends each packet from its host, and finds where it ends and which rule of each Node's policy engine counted it; every verdict must be the one of explain (`build_and_test` of windows.yml, `.github/scripts/explain-conformance.ps1`). A scenario of `tests/explain/broken` carries a fault, a state of a Node without one of its rules, and the suite must fail on exactly the packets that the fault names, so a drift of explain or of the data plane cannot pass unseen.

## Amendment 2026-10-27: a token has a life, and the CLI checks the certificate toward loopback (AUD1-DT-13)

Recorded by AUD1-DT-13 (#461), which closes gap G-17 of the threat model (AP-2, AP-8). Decisions 9 and 10 hold: there are still three global roles, and the CLI and the web UI are still clients of the public API. A token never expired, showed no last use, and a leaked one worked until an admin deleted it; and `ranz` checked no certificate toward `127.0.0.1`, its default, so a program of the host that listened on a port that the Controller was not on got the token of whoever ran `ranz`.

- **An expiry.** `POST /api/v1/tokens` takes `expires`, an RFC 3339 time in the future (kept in UTC to the second, in the years 1 to 9999; anything else is 400). The Controller refuses the secret of the token from that instant with 401: the challenge is `error="invalid_token"` with `error_description="the token expired"` (RFC 6750, section 3), and the answer says when the token expired and not its name. An admin lists it, with `expired: true` and its expiry, and can still delete it. A token with no expiry never expires, as before. There is no call that changes the expiry of a token: an admin makes another. `ranz token create -expires` takes an RFC 3339 time or a time from now, such as `720h`.
- **The last use.** The Controller keeps when each token last authenticated a call, and `GET /api/v1/tokens` shows it as `lastUsed`: a call that the role of the token refuses is a use, and a call with a secret that no token has, or with the token of an expired one, is none. A use is stored at most once a minute for each token, by the statement that stores it (so the members of a cluster that see the same token at once change the row once) and by a short memory in each member, so a busy token costs the store one write a minute and its last use is right to the minute. The answer of `whoami` and the token that a call carries are as the store held them before that call. `ranz token list`, and `ranz tokens`, print it, as JSON or, with `-o table`, one line for each token.
- **Where the life is kept.** In a table of its own, `api_token_life` (name, expiry and last use, as Unix seconds), not in columns of `api_tokens`: the store of an earlier release and a backup of it have no such columns, and nothing in the store alters a table that exists. A token with no row there never expires and was never used. Deleting a token deletes its row in the same transaction, so a token that is made again under the name starts with no life of the old one, and the backup holds the life with the tokens.
- **`ranz` checks the certificate toward loopback too.** A loopback address is no longer trusted for being one: `api.NewClient` leaves a loopback host unchecked for the tests that start their own Controller, and `ranz` never uses it so. Toward a loopback host with no `-tls-fingerprint`, `ranz` accepts only the certificate with the TLS fingerprint that the Controller of this host wrote to `tls.fingerprint` in its data directory (`-controller-dir` or `RANZ_CONTROLLER_DIR` names it; the data directory of the service is the default). The Controller writes the file at every start and at every change of the certificate it serves (`controller-cert set` or `clear`, a setting that another member made, an ACME renewal), in one step, so the file is right again when the call that changed the certificate ends. Only the owner of the data directory and the administrators write there, so another program of the host cannot make `ranz` trust its key (the amendment of 2026-10-29 below, AUD1-DT-14, makes `ranz` check who wrote the file); what the file holds is public. When `ranz` cannot read the file and has no `-tls-fingerprint` it sends no token and does not connect: it says where it looked and asks for `-tls-fingerprint` (the ticket calls the flag `-fingerprint`; it is the flag that `ranz` has had since SDN-14). When the certificate has another fingerprint, the TLS handshake fails before the first byte of the call, so the token never leaves `ranz`, and the message names both fingerprints. A host that is not loopback is checked as before, by its chain or by `-tls-fingerprint`. The logins of SDN-32 (`ranz login`, `ranz node login`) make their client the same way and take `-controller-dir` too, so a password or a code goes to a loopback address only after the same check.
- **Not here.** A scope below the role (SDN-38, #231) stays open: a token still holds one of the three roles for all of the API. *(SDN-38 built it: see the amendment of 2026-10-29 on roles held for one Network.)* The change of the role of an API token in place, and the user tokens of the logins, are SDN-32 (#226), the amendment of 2026-10-28 below. A user token has its own end, 12 hours at most, in a table of its own (`user_tokens`), so it has no `expires` and no `lastUsed` of an API token and `GET /api/v1/tokens` does not list it; a read of the tokens, the audit log or the licence with a user token is an access under its actor, `user:NAME` (ADR-0030, amendment of 2026-10-27).

## Amendment 2026-10-28: the logins of users (SDN-32)

Recorded by SDN-32 (#226), the logins of the unified-management spec #224 (stories 9, 17 and 20). Decisions 9 and 10 hold: there are still three global roles, a login gives one of them and nothing else, and the Guard checks the calls of a login's token as it checks the calls of an API token. Multi-factor login is postponed (maintainer decision of 2026-10-24), so a login is a password login.

- **Three ways in, each the standard one.** A password login (`POST /api/v1/login`, the name and the password in the body). A browser login: the authorization code grant of OAuth 2.0 with PKCE (RFC 6749 section 4.1, RFC 7636, the S256 method only) for a native client (RFC 8252): the client listens on a port of `127.0.0.1`, opens the browser at the authorization page `GET /api/v1/login/authorize`, the user signs in there, the browser brings the code to the loopback port, and the client exchanges it at the token endpoint `POST /api/v1/login/token` with its verifier. A device code login (RFC 8628): the device asks `POST /api/v1/login/device/code` for a device code and a user code, the user types the user code into the device page `GET /api/v1/login/device` on any other device and signs in there, and the device polls the token endpoint. The one client is the public client `ranz` (`ranz login`, `ranz node login`, and the tray of SDN-55 later). A redirect URI is `http://127.0.0.1:PORT/PATH` and nothing else: any port, as RFC 8252 asks, and the IPv4 loopback address only, which the Content Security Policy of the page can name for the redirect after the form (`form-action`).
- **No token, in front of the Guard.** A login is how a caller gets a token, so no call of a login carries one: `api.WithLogins` serves every path under `/api/v1/login` in front of the Guard and every other path behind it, and a standby forwards the logins to the leader as it forwards every call. The admin source allowlist stands in front of the logins as of every call. Since AUD1-DT-6 (#454) the first install (`ranz install --controller`) sets that list to loopback and the private subnets of the host, so a user whose browser or `ranz node login` comes from another address signs in only once an admin adds the source (`ranz admin-sources`, or `--admin-from` at the install); whether the logins of users get a reach of their own is left to the self-service portal (SDN-58, #251). The two pages are rendered by the controller as plain HTML forms, with no script at all, the style sheet of the web UI and its security headers; the web UI's own pages, which call only the actions of their table, do not change.
- **What a login gives.** A login with a static key of a device (`node_key`, and `node_name` for the name it asks for) enrols the device: the Controller makes the Node resource of the key, owned by the User, as one revision of the intent under the actor `user:NAME` (`controller.EnrolDevice`). The Node names no VRF, so it joins VRF default when the intent has it (ADR-0034); its name is `node_name`, or the first of `NAME-1`, `NAME-2` that no Node has. The maximum devices of the User and every other rule of the intent hold as for an apply, so the enrolment of a device above the maximum is refused with the message of `ranz apply`, and the client gets `access_denied`. A key that a Node of the User holds already is that Node's enrolment again, with no revision; a key or a name of another User's Node is refused. The check of the name and of the key runs under the lock of the apply (`checkPrecondition`), so no other change slips in between. The answer gives the device the keys of the Controller, its Noise key and the TLS fingerprint of its certificate, and `ranz node login` makes them the Controller settings of the Node with the host and port that it reached the Controller at (ADR-0035: the control stream shares the TLS port). A login without a key gives a user token.
- **API roles of users.** A User holds no API role of its own (SDN-31). An admin gives one: `PUT` and `DELETE /api/v1/tokens/users/{name}` and `GET /api/v1/tokens/users`, under `/api/v1/tokens` because who holds which role is what the API tokens say too, so `Needs` gives them admin as it gives every call there (`ranz user role list|set|clear`). The roles are in the store (table `user_roles`), not in the Intent, for the reasons of the API tokens: an operator applies Intent and must not grant himself admin, and a revision, a rollback or an import must not change who holds which role. A User that a change of the Intent removes loses its role, as it loses its password. Setting the password of a User that holds a role needs admin, as the amendment of 2026-10-25 asked: whoever knows the password may act with the role.
- **User tokens.** A login of a User that holds a role gives it a user token: a bearer secret (`ranz_u_` and 128 random bits), shown once, of which the store keeps the SHA-256 (table `user_tokens`), with the name of the User and its end, 12 hours after the login and never after the expiry of the User. The Guard takes it as a token of the role that the User holds when it is used (`rbac.Tokens.Authenticate`), so a change of the role takes effect at the next call, and taking the role away, a ban of the User and a logout (`POST /api/v1/login/logout`) end the tokens at once; an expiry of the User that moves earlier ends them then. Its name in the API is `user:NAME`, which no API token can have, and the audit records of its calls name the actor `user:NAME`. A User without a role gets no user token: its login is refused with 403, after the password checked out.
- **Refusals, the audit log and the throttle.** A wrong password, a name that no User has and a User without a password are one refusal, 401, in the same words (`ErrBadCredentials`). Every refused login is an `auth-failed` record with the name that it gave as its actor (`user:NAME`, or `unknown` for a name that no User can have) and its source; the audit log records the failed authentications of one source once in 10 s (SDN-49). A login that succeeds is a `login` record of the User; one that gives nothing (no role, a device refused) is a `login` or `enrolment` record with the outcome failure. After five failed logins in a row for one name, whether a User has it or not, or from one source (an IPv4 address, or an IPv6 /64), the next one is refused at once with 429 and Retry-After, without a check of the password, and the refusal is recorded; one try comes back each minute. The user codes of the device page that no device waits with count the same way, by source. A device code lasts 10 minutes and is polled every 5 s at most (`slow_down`), an authorization code lasts a minute and is exchanged once, and at most 16 device codes of one source (an IPv4 address, or an IPv6 /64, as the throttle counts a source) wait at a time.
- **The role of an API token changes in place**, as the decision of 2026-10-22 tied it to these logins: `PATCH /api/v1/tokens/{name}` with `{"role": ...}` (admin, `ranz token role NAME ROLE`) keeps the secret, and the next call of the token has the new role. The last admin token that has not expired keeps the role admin (409), as it cannot be deleted. The guard counts only the admin tokens that have not expired (AUD1-DT-15, #497), because an expired token cannot manage the tokens. An expired admin token can be deleted beside another admin token. The last admin token that exists stays even when it has expired, so the Controller never has none, and `ranz controller reset-admin` on the host is the way out when every admin token has expired. The expiry of API tokens, the other half of that decision, is AUD1-DT-13 (#461).
- **Not here.** The web UI's own sign-in with a user (the pages of the self-service portal, SDN-58 #251, are the place for it), multi-factor login, the identity providers (SDN-34 to SDN-36), key expiry and approval mode (SDN-56 #249), and the tray (SDN-55 #248). A login that waits when the leader of a cluster changes is started again, since its grant is held in the memory of the leader.

## Amendment 2026-10-28: key expiry and approval mode (SDN-56)

Recorded by SDN-56 (#249), the node keys of the unified-management spec #224 (stories 65 to 67). Decisions 9 and 10 hold: there are still three global roles, and the CLI is still a client of the public API. Until now the static key of a Node was good for as long as its Node resource held it, so a device that was lost, or whose user had left, worked until somebody deleted its resource, and every Node resource that an operator applied or that a login enrolled joined its VRFs at once.

- **A key has a life.** The static key of a Node lives for the **key lifetime** of its Networks from the moment that the Node was admitted, or that it authenticated last. The key lifetime is `keyLifetimeDays` of a Network (1 to 3650, 90 when it is left out), and the shortest one of them for a Node that is in the VRFs of several. A Node that an admin marks `nonExpiring` (`Node.nonExpiring`, a field of the Intent, for a server or a gateway that no user logs in for) has a key with no end; taking the mark off starts a period from that moment, so the key does not end at once. A change of `keyLifetimeDays` moves no key that exists: it applies to the next refresh.
- **The policy is in the Intent, the outcome is in the store.** The Intent says how long a key lives, which Node never expires and how a Network admits its Nodes; when each key ends, and which Node an admin approved, are rows of the store (table `node_keys`, `internal/store`, `nodekeys.go`), as the passwords, the bans and the API roles are, so that a revision, a rollback or an import does not give an expired key another life and does not approve a Node. A store backup holds them and an Intent export does not. A row is by the key and not by the name: a Node that is deleted and made again, or whose `publicKey` changes, is a new key with a life and an approval of its own, and a change of the Intent that no longer holds a key deletes its row. The first start of this release gives each Node that exists a life of a full period and admits it, since no Network could hold a Node before.
- **A refresh is a re-authentication.** The login of a User with a device whose static key a Node of that User holds already is the enrolment of that Node again (SDN-32, no revision), and now it also gives the key another period from that moment (`Controller.EnrolDevice`). The Controller checks that the User is still valid before it does, whatever its caller checked: a User past its expiry (`ErrUserExpired`) or banned (`ErrUserBanned`) cannot refresh. So a User that was removed where it comes from, which for the local accounts of today is an account that expired, cannot refresh the keys of its devices, and each of them loses access when its key ends, which is "at the next refresh", while the devices of the Users that are valid are refreshed and go on. The removal alone cuts nobody off: an operator who wants that bans the User (SDN-50). With the identity providers of SDN-34 to SDN-36 a User that the provider removed is a login that the provider refuses, so the rule is the same. A Node that has no owner has no User to log in: an operator refreshes its key (`POST /api/v1/operations/node-keys/{name}/refresh`), and the key of a device of a User is refreshed by that User only (409).
- **Held back, as the Nodes of a banned User are.** A Node whose key ended, or that waits for approval, is left out of the desired state of every other Node, which is compiled as if it were not in the Intent (the ban of the amendment of 2026-10-27), so no Node has it as a Peer, a Relay or a route and none takes a packet of its, and its control stream is refused. The Refuse has the reason `REFUSE_REASON_UNKNOWN_NODE`, the one reason of the control protocol for a node that is not admitted (SDN-39), and a message that says which of the two it is: `the key of Node "alice-laptop" expired at 2026-01-31T10:00:00Z: its user logs in again to refresh it`, or `Node "files" waits for an administrator to approve it in Network "corp-lan"`. No reason and no schema version is new. The refusal is a failed authentication in the audit log, throttled as every one is. A Node that is held keeps its own desired state and its Generations, so the first update that it gets once it is admitted again follows the one that it applied. As for a ban, a Node that cannot reach the Controller keeps forwarding on the list it has: the end of a key reaches a peer with its next Generation (ADR-0026 decision 5, CS-10 of the threat model).
- **When it takes effect.** The check of the key of a Node is made at its Hello, at the instant, and the Controller looks at all the keys every 10 seconds (`Config.KeyCheck`) and at every change that it commits: a Node whose key ended while its stream was open is detached and refused at the next look, and the states of the others are compiled again, each a new Generation. A cluster runs the look on its leader, which loads the lives from the store when it takes the lease.
- **Approval mode.** A Network admits its new Nodes at once (`approval: auto`, the default) or holds each of them until an operator approves it (`approval: manual`). A Node is new when its key has no life yet, and it is admitted at the moment that no Network of its VRFs holds it for approval: turning approval on cuts off no Node that was admitted, a Node that joins afterwards waits, and a Network that goes back to `auto` admits the Nodes that waited. The rule is for every new Node resource, whoever made it, an operator with `ranz apply` or the login of a User. `POST /api/v1/operations/node-keys/{name}/approve` (`ranz node-key approve`) approves one: it is admitted from then, its key lives from then, so that a Node that waited long is not admitted with a key that has ended, and the others get it as a Peer; it opens its stream again by itself at its next try. A second approval changes nothing. The operator role approves, as it applies the Nodes.
- **API and CLI.** The calls are under `/api/v1/operations`, so they need the operator role, the reads too, and the Controller records each as an `operation` of the audit log (ADR-0031 amendment of 2026-10-27): `GET /node-keys` lists the key of every Node (its state `valid`, `expired` or `pending`, when it last authenticated, when it ends, whether it was approved, by whom, and the Network that holds it), `POST /node-keys/{name}/approve` and `POST /node-keys/{name}/refresh`; the actions are `node-key-list`, `node-approve` and `node-key-refresh`. `ranz node-key list|approve|refresh` call them.
- **Not here.** A page of the web UI for the keys and the approvals; an Event for a Node that waits or whose key ended; a key life for the keys of Devices (SDN-80), which are WireGuard keys and no static keys of Nodes; an end of the key that follows the expiry of the User's account; join tokens for headless Nodes (until they come, a server is marked `nonExpiring`, or an operator refreshes it); and the identity providers (SDN-34 to SDN-36).
- **CI.** `controller/internal/controller/nodekeys_test.go` runs the controller conformance with the node simulator on a clock that it moves: a key that ends stops the node until its user logs in again or an operator refreshes it (`TestAnExpiredKeyStopsTheNodeUntilItAuthenticatesAgain`), a User that was removed cannot refresh and its device loses access when its key ends while the device of another User goes on (`TestAUserRemovedFromTheProviderLosesAccessAtTheNextRefresh`, `TestABannedUserCannotRefreshTheKeysOfItsDevices`), a new Node of a Network in approval mode waits until it is approved (`TestInApprovalModeANewNodeWaitsUntilItIsApproved`, `TestChangingTheApprovalModeAffectsOnlyTheNodesThatJoinAfter`), a Node marked `nonExpiring` keeps its key, the lifetime follows the Network, the lives survive a restart and a rollback (`TestANodeMarkedNonExpiringKeepsItsKey`, `TestKeyLifetimeFollowsTheNetwork`, `TestTheLivesOfTheKeysSurviveARestartAndAreNotPartOfTheIntent`), and every operation is in the audit log under the operator role (`TestNodeKeyOperationsAreAuditedAndNeedTheOperatorRole`). The packages `intent` (`keylife_test.go`), `store` (`nodekeys_test.go`), `api` (`nodekeys_test.go`) and `cmd/ranz` (`nodekeys_test.go`) test their parts.

## Amendment 2026-10-29: `ranz` trusts the fingerprint file only when no other account can have written it (AUD1-DT-14)

Recorded by AUD1-DT-14 (#496), which follows the read-only review of AUD1-DT-13 (the amendment of 2026-10-27). That amendment said that only the owner of the data directory and the administrators write to it, so that another program of the host cannot make `ranz` trust its key. Nothing checked it. When no Controller runs on the host, or it runs with another `-data`, the folder may not be there, `C:\ProgramData` lets every user make it, and a user's own fingerprint in it, with a listener on `127.0.0.1:443`, got the token of an administrator who ran `ranz` with the default server and no `-tls-fingerprint`. Decisions 9 and 10 hold.

- **What `ranz` checks.** On Windows `ranz` opens `tls.fingerprint` itself and reads it through that handle, so what is checked is what is read, and nobody can write, delete or replace the file while it is open (`controllercmd.ReadFingerprint`). It takes the file only when the file and its folder are owned by SYSTEM, the Administrators or the account of the Controller service, and no access entry lets another account write either of them: write or append data, add a file or a folder, write the attributes or the extended attributes, delete the file or what a folder holds, or change the access list or the owner. An entry that denies, one that only what is made in a folder inherits and one with no right to write let nobody write, and the entry for OWNER RIGHTS is for the owner. A missing or null access list, an entry of a kind that `ranz` does not read that gives a right to write, a link (a symbolic link or a junction) in place of the file or its folder, and a volume that keeps no access lists are refused.
- **Why the service account is trusted and the account of `ranz` is not.** The Controller writes the file as its virtual account (ADR-0039 decision 3), which then owns it, so that account has to be on the list, as it is for the data directory itself (AUD1-DT-10). The account that runs `ranz` is not, because a program of the same user that is not elevated could have made the folder, and the token that `ranz` sends may be one that such a program cannot read; what an elevated Administrator makes belongs to the Administrators.
- **What it says.** The refusal names the folder or the file and says why in one line, connects to nothing, sends no token and asks for `-tls-fingerprint`, which takes the call through as before and never reads the file. A folder or a file that is not there, or a file that holds no fingerprint, is refused as before: `ranz` never falls back to a connection that it did not check.
- **Not here.** The check is Windows only: elsewhere the data directory of the service is `/var/lib/ranz-controller`, which only root can make, and `makeDataDir` makes it with mode 0700. An Administrator, SYSTEM or a flaw of the Controller that runs as its service account can still write the file, which is the host (threat model, section 14).
- **CI.** `TestReadFingerprintRefusesWhatAnotherAccountMayHaveWritten`, `TestReadFingerprintTakesTheFilesOfTheInstallAndTheService` and `TestCheckWritersByTheOwnerAndTheAccessList` of the package `controller`, and `TestRanzRefusesAFingerprintFileThatAnotherAccountMayHaveWritten` of `cmd/ranz`, run on the Windows runner of `ranz.yml`. `controller-service.ps1` checks the file that the real service writes, and that `ranz.exe` refuses the same file in a folder that the Users group may write. The job first test calls `ranz` toward the Controller that `ranz install` made, with no fingerprint on the command line, and checks who owns the file and who may write it.

## Amendment 2026-10-29: the self-service portal (SDN-58)

Recorded by SDN-58 (#251), the user portal of the unified-management spec #224. Decisions 9 and 10 hold: there are still three global roles that an admin gives, the web UI and the CLI are still clients of the public API, and the Guard still decides every call. A User now signs in to the web UI to see and manage its own devices, and to make join tokens for the devices that cannot sign in themselves.

- **The self scope.** A login for the portal is the password login of SDN-32 with `"scope": "self"` in the body (`POST /api/v1/login`). It gives a token of the scope `self`: `ranz_s_` and 128 random bits, shown once, of which the store keeps the SHA-256 in a table of its own (`self_tokens`). It needs no API role of the User, since the portal is for every User. It ends as the user tokens of a role end: 12 hours after the login and never after the expiry of the User, and at once at a ban, at the removal of the User from the Intent, at an expiry that moves earlier and at a logout (`POST /api/v1/login/logout`). The scope is fixed when the token is made: an admin who gives the User an API role later does not make the token more, and the token of a role is never taken for one of the scope. After the password checks out, a scope that the controller does not know is 400. `rbac.Self` is no fourth API role: an admin cannot give it (`ParseRole` refuses it and `Roles` does not list it), and it ranks below viewer, so a token of the scope reaches no call that asks for a role of the API (403, `whoami` included), and every user token of a role of the whole API reaches the calls that ask for it. A role limited to a Network is another thing, which SDN-38 (#231) builds (the amendment of 2026-10-29 below, SDN-38): this scope is a token with no role at all, and it is how a User whose role is held for one Network reaches the portal.
- **The self calls.** Every path under `/api/v1/self` asks for `Self` (`api.Needs`), and a call of it is about the User that holds the token and about nothing else. An API token names no User, so a self call with one is 403. The user token of a User that holds an API role for the whole API names it, so it makes the self calls too, and they are its own. A user token whose role is held for one Network does not (the amendment of 2026-10-29 below, SDN-38): the Guard refuses it every call but `whoami` and the calls of its Network, the self calls included (403). Such a User uses the portal through a login with the scope `self`, which needs no role. A User that expired or that an operator banned has no token. The two calls that make something, adding a device and making a join token, ask the controller once more whether the User may act now, and refuse one that may not with 403 when a token reaches them anyway. A body that is not what a call takes and a static key that is none are 400.

  | Call | What it does |
  |---|---|
  | `GET /api/v1/self` | The User, its Groups, and how many devices it has of how many it may |
  | `GET /api/v1/self/devices` | Its devices, each with how it stands |
  | `POST /api/v1/self/devices` | Adds a device by its static key (`publicKey`) and the name it takes (`name`, drawn when left out) |
  | `DELETE /api/v1/self/devices/{kind}/{name}` | Removes one of its devices |
  | `GET /api/v1/self/join-tokens` | Its join tokens that wait, without their secrets |
  | `POST /api/v1/self/join-tokens` | Makes a join token, with the name that the device takes (`name`); the secret shows once |
  | `DELETE /api/v1/self/join-tokens/{id}` | Revokes one of its join tokens |

- **A User sees its own devices and no others.** A device is a resource that names the User as its owner (`intent.DevicesOf`): a Node, or a WireGuard Device. The list says how each stands: a Node is `connected` or `offline`, or has the state of its key (`expired`, `pending`, ADR-0031 amendment of 2026-10-28), or is `banned` or `unlicensed`; it shows its VRFs, its tags (its own and those of the Groups of the User), its addresses in the Networks of its VRFs, when its key ends and its Generations; a Device shows the VRF of its Network, its tags (its own and those of the Groups of the User, `intent.DeviceTags`), its addresses and the last handshake that its gateway reported, and is `unlicensed` when it is above the node cap of the licence in force. The Devices of a User are the ones that an administrator made with the User as owner (SDN-82), and they count against its maximum devices as its Nodes do. A device that another User owns, or that no User owns, is not found (404) whatever its name, and so is a resource that is no device, such as a VRF: the check runs under the lock of the delete, against the intent that the delete changes, so no other change slips in between.
- **Adding and removing a device are revisions under the User's actor.** Adding is the enrolment of SDN-32 (`EnrolDevice`) made by the User from the portal: the Node resource of the key, owned by the User, as one revision under the actor `user:NAME`, joining VRF default (ADR-0034). So the maximum devices of the User and every other rule of the Intent hold as for `ranz apply`, with the same message (400); the key of a Node that is no device of the User is 409, and a key that a Node of the User holds already is that Node again, with no revision. A name that is no name of a resource is 400 whatever key comes with it, also one that the User holds already. Removing is the delete of `ranz delete` under the same actor, and a resource that the Intent keeps is refused as it is there. A Device that goes is revoked as an administrator revokes it: its gateway stops terminating it with the next Generation and its sealed PresharedKey goes with it. The keys of a Device show once, so the page tells the User that the configuration that the Device holds stops working for good and that an administrator makes the next one. The audit log holds each revision as an `intent-change` of the actor `user:NAME`, and each call that changes something as an `operation` of that actor.
- **Join tokens.** A User makes a join token for a device of its own that cannot sign in itself, such as a Node without a browser, and gives the secret to the device. The secret is `ranz_j_` and 128 random bits, shown once; the store keeps the SHA-256 of it with an id of 16 hex digits that names the token in the list and in the revocation, the User, the name that the device takes, and the end (table `join_tokens`). Like a password and a user token it is no Intent: a revision, a rollback or an export never changes one, a backup holds them, and a User that the Intent loses takes its tokens along. A token works once and ends a day after it was made (`JoinTokenLife`), and a User has 16 that wait at most (409 above). A User lists and revokes its own; the token of another is not found. The device presents the secret with its static key at `POST /api/v1/login/join` (the form fields `token`, `node_key` and `node_name`), which carries no bearer token and so is served with the other logins, in front of the Guard. The Controller claims the token first, in one statement, so of two devices that present one secret at once only one gets it. Then it enrols the device as `EnrolDevice` does, as a Node that the User owns, in VRF default and with the tags of the Groups of the User, under the actor `user:NAME` whatever the source address, and deletes the token. The enrolment is refused for a User that expired or that an operator banned (403), for a device above the maximum devices (400) and for a key of another User's Node (409), and the token goes back to its User then, so that it can be used once the cause is gone. A secret that is none, one that was used, one that ended and one that was revoked are one refusal, 401 (`ErrBadJoinToken`), which says nothing of which tokens exist. It takes a try from the source as a wrong password does (five in a row, then 429 with Retry-After, one try back each minute), and is an `auth-failed` record of the actor `unknown`.
- **`ranz node join`.** The device side: `ranz node join [-server URL] [-token-file FILE] [-name NAME]` reads the secret from the file or from standard input and never from an argument, so that no process list and no history holds it, takes the public half of the static key from the Node service, joins, and makes the keys that the answer holds the Controller settings of the Node, as `ranz node login` does. The portal shows the command with the secret, once, as `echo SECRET | ranz node join -server URL`. A device that has a browser adds itself with `ranz node login` or by its key in the portal.
- **The pages.** The web UI has three pages for the portal, each its own URL and its own module, as the other areas are: `/portal-sign-in`, `/portal` (My devices: the User, its devices with how each stands and a button that removes it, and the form that adds one) and `/portal-join` (Join tokens). The portal keeps its token in the tab under its own key (`ranz.selfToken`), apart from the API token of the console (`ranz.apiToken`): a page of the console never opens with the token of the portal, and a page of the portal never opens with an API token. Every control of the portal is an action of the action table (decision 10 above), with the role `self`, or `public` for the sign-in, which needs no token. Text from the API only ever becomes text nodes, a refusal is shown in the words of the API, and the pages change nothing of the Content Security Policy. The sign-in page of the console links to `/portal-sign-in`, so a User who lands on the controller finds the portal.
- **Not here.** A reach of its own for the portal: the pages, the logins and the join are behind the admin source allowlist as every call is (ADR-0031 amendments of 2026-10-23 and 2026-10-28), so a User whose browser or device comes from an address that the list does not hold signs in or joins once an admin adds the source. Multi-factor login and the identity providers (SDN-34 to SDN-36), a User that changes its own password, the rename of a device, and a role limited to a Network (SDN-38). A join token is a User's: it enrols a device that the User owns, so the servers and gateways that no User owns still wait for the join token or the certificate that an administrator makes for them (story 18 of the spec #224). The portal makes no WireGuard Device: a User who wants a phone or a router on a stock WireGuard client has an administrator make a Device that names it as owner (`ranz device create -owner`), and the portal lists it and lets the User remove it. A Device that its User makes in the portal, with the keys and the QR code of SDN-82 and the admission mode of its Network, is SDN-85 (#381), which waits for this ticket.
- **CI.** `controller/internal/controller/portal_test.go` runs the controller conformance with the node simulator: a User sees only its own devices and adds and removes them, with the maximum devices of the Intent and the audit log (`TestAUserSeesOnlyItsOwnDevicesAndAddsAndRemovesThem`), a join token from the portal enrols a device into the networks of a Node with the tags of the User's Groups and is spent (`TestAJoinTokenFromThePortalEnrolsADevice`), join tokens end, are their Users' alone and have a limit (`TestJoinTokensEndAndAreTheirUsersAlone`), and a token of the scope ends with its User (`TestATokenOfTheSelfScopeEndsWithItsUser`). `controller/internal/controller/portaldevice_test.go` runs the Devices of a User through the same seam: the list, the maximum devices, the handshake of the gateway, no key in the list, no removal of another User's Device, and the removal with its Generation at the gateway and its PresharedKey (`TestAUserSeesAndRemovesTheWireGuardDevicesThatAreHers`), and a Device above the licence (`TestTheDeviceOfAUserBeyondTheLicenceIsShownAsSuch`). `controller/internal/controller/portalstatus_test.go` moves the clock of the lives of the keys under a device and checks that the portal says that it waits for approval, that its key ended and when, and that a login of its User makes it live again (`TestThePortalSaysWhenADeviceWaitsForApprovalOrItsKeyEnded`). `controller/internal/webui/portal_test.go` drives the three pages with the headless browser against the same controller (`TestAUserUsesThePortal`), and `portaldevice_test.go` of that package the page of a User that has a Device (`TestThePortalListsAndRemovesAWireGuardDevice`). The packages `api` (`self_test.go`), `login` (`portal_test.go`, with the fuzz target `FuzzParseJoin`), `rbac` (`self_test.go`), `store` (`portal_test.go`) and `cmd/ranz` (`nodejoin_test.go`) test their parts.

## Amendment 2026-10-29: roles held for one Network, delegations and provider groups (SDN-38)

Recorded by SDN-38 (#231), the administrators scoped to one Network of the unified-management spec #224 (stories 21 to 24). Decisions 9 and 10 hold: the roles are still `admin`, `operator` and `viewer`, each allows what decision 9 says, and the CLI and the web UI are still clients of the public API. What is new is where a role is held. Until now a token held its role for all of the API, which is what "global" means in decision 9 and in the amendments above. Now a role can be held for one Network. The IT person of a branch then changes their branch and nothing else, like the administrator of a Hub of the slim fork, within the quotas and the permissions that an admin of the whole API sets.

- **A scoped role.** A role is held for the whole API or for one Network (`rbac.Grant`: the role and, for a scoped role, the Network). An API token holds one (`POST /api/v1/tokens` takes `network`). So does a User (`PUT /api/v1/tokens/users/{name}` takes `network`), and its user tokens carry the role and the Network of the User as they are when a token is used. A login through an identity provider can give one too (provider groups, below). The Network must be one of the Intent (404), and its name must be a name (400). The tables hold `role@network`, for example `operator@branch-a`, where they held a role, so a role is never stored without its scope. A controller of an earlier release does not know that form. It reads the text as a role that does not parse and authenticates nothing, so it never holds the role for the whole API. A change of the role of an API token keeps its scope (`PATCH /api/v1/tokens/{name}` with `role`). The same call with `network` sets the scope, and an empty `network` is the whole API. That is the one way to widen a scoped token, and it needs the role admin of the whole API, as every call under `/api/v1/tokens` does. An admin token that is held for a Network is no admin token of the whole API, so it does not count as the last one, and the last one cannot be scoped away (409). `whoami` shows the Network of a token.
- **A Network that goes takes what was held for it.** A change of the Intent that removes a Network deletes, in one transaction, its delegation, the API tokens and the API roles of Users that were held for it, the user tokens of those Users and the ones that carry such a role, and the provider groups that map to it (`store.DeleteScopedAccess`). A Network made again under the name starts with none of them, as a User made again starts with no password.
- **The Guard.** A role that is held for a Network passes `whoami` and the calls under `/api/v1/networks/{network}` of its own Network, and nothing else. Any other call is 403 with `insufficient_scope`, and the answer names the token, its role, its Network and the call (`scopeRefusal`). The Guard makes this check once it knows the token, before it asks what role the call needs. It compares the path that `Needs` reads, with its dots and slashes resolved, so a path that climbs out of the Network's own is the path that it climbs to. Each handler of a Network's call checks again that the Network of its path is the Network of the token. So a scope only narrows a role, and a call that a later ticket adds is out of its reach until it is put under a Network. A role of the whole API is refused the calls of a Network (403): they are for the roles that are held for it, and it changes the Intent with `/api/v1/apply`. Inside its Network a role needs what `Needs` gives each call. A read is viewer and any other call is operator. The list of sessions is operator too, as every call that shows who is connected is (SDN-50). The calls are:

  | Call | Role | What it does |
  |---|---|---|
  | `GET /api/v1/networks/{network}` | viewer | The Network, its delegation, what it holds of each quota and the sessions that its Nodes have open |
  | `GET /api/v1/networks/{network}/resources` | viewer | The Network, and the Nodes, Policies, Groups and Users in its scope |
  | `POST /api/v1/networks/{network}/apply` | operator | Applies an Intent document, checked as below |
  | `DELETE /api/v1/networks/{network}/resources/{kind}/{name}` | operator | Deletes one resource of the scope, checked as below |
  | `PUT /api/v1/networks/{network}/users/{name}/password` | operator | Sets the password of a User of the scope |
  | `GET /api/v1/networks/{network}/sessions` | operator | The sessions of the Nodes in the scope |
  | `POST /api/v1/networks/{network}/sessions/{id}/disconnect` | operator | Ends one of them at once |

  An admin of the whole API sets the delegations and the provider groups. Their calls are under `/api/v1/tokens`, as who holds which role is, so they need admin, and a read of either that succeeds is an `access` record, as a read of the tokens is (AUD1-DT-13):

  | Call | What it does |
  |---|---|
  | `GET /api/v1/tokens/delegations` | The delegation of every Network that has one, with its usage |
  | `PUT /api/v1/tokens/delegations/{network}` | Sets the delegation of a Network: its `quotas` and its `permissions` |
  | `DELETE /api/v1/tokens/delegations/{network}` | Removes it |
  | `GET /api/v1/tokens/provider-groups` | The mappings, by provider and group |
  | `PUT /api/v1/tokens/provider-groups/{provider}` | Maps a group of the provider: its `group`, its `role` and, for one Network, its `network` |
  | `DELETE /api/v1/tokens/provider-groups/{provider}?group=NAME` | Unmaps it |

- **A User whose role is held for a Network, and the portal.** A user token whose role is held for one Network gets 403 on every call but `whoami` and the calls of its Network. The self calls of the portal are among them, since `/api/v1/self` is no call of a Network (`TestAScopedTokenPassesOnlyTheCallsOfItsNetwork` has the case `GET /api/v1/self/devices`). The portal still works for such a User through a login with the scope `self` (the amendment of SDN-58 above), which needs no role.
- **The scope of a resource.** A User, a Group, a Node and a Policy may name a Network as their `scope`, and an Intent that holds a scope that is no Network is refused (400). A Network is in its own scope. A Node that names none is in the scope of its owner, so the device that a User of a Network enrols is in that Network and nobody has to say so. A resource that has no scope is changed by the roles of the whole API alone, and so is a resource of any other kind: a scoped role never changes a VRF, a Controller or the rest. The scope is part of the declared network, so it lives in the Intent, and a revision, a rollback and an export carry it. A Network that is the scope of a resource cannot be deleted, and the refusal names the resources.
- **The delegation.** An admin of the whole API sets the delegation of a Network, which is what its scoped roles are bound by. It is the successor of the admin options of a Hub of the slim fork. Its quotas are the most Users, Groups, Nodes and Policies (`users`, `groups`, `nodes`, `rules`) in the scope of the Network, the most control streams that its Nodes have open at once (`sessions`) and the greatest rate limit, in bit/s, that a scoped role gives a Node (`bandwidth`). A quota that is left out, or 0, is no limit. Its permissions are the kinds of resource that its scoped roles may change: `network` (the Network itself), `nodes`, `users`, `groups`, `rules` and `sessions`. Left out, they are none, so the scoped roles of a Network that has no delegation read and change nothing. The delegation is not an Intent resource. A role that the Intent could change would change its own limits, and a revision, a rollback or an import must not give a scoped role more. It lives in the store (table `scope_delegations`), a store backup holds it, and an Intent export does not. The leader keeps the delegations in memory and reads them when it takes the lease, and a change takes effect for the calls and the control streams that come after it. Removing the delegation of a Network leaves its scoped roles in place, and they may change nothing until another is set.
- **What a scoped role may change.** The check is made on the change, not on the call (`scope.Caller.Check`). It takes the Intent in force and the Intent that the change makes, under the lock of the apply, and it refuses the change when anything that the change adds, changes or removes is outside the scope or beyond the permissions. So a change cannot reach what the call did not name, such as the resources that the Controller completes. A resource that the change leaves as it was is not part of it. A refusal is 403 with a reason for each resource. It changes nothing and gives no Node a new Generation. A change that passes is an ordinary apply or delete: it makes a revision, and every rule of the Intent holds for it as for `ranz apply`. The scope is told first and alone: it is checked before the Intent is asked, so that a refusal never tells what the Intent knows of the resources of other scopes, such as what depends on a VRF. Everything that is not allowed here is refused, so a kind of resource that the scope does not know and a field of a Node that it does not list are the global roles', also when a later ticket adds one. What is allowed:
  - A resource of the kind Network, Node, User, Group or Policy, when the delegation permits the kind and the resource is in the scope before the change and after it.
  - The Network itself: the role admin only, and only its own Network. It may change all of it but the VRF, the mode and the pools, such as its source prefixes, its security, its DHCP, its approval mode and its key lifetime. A scoped role never makes or deletes a Network. A Node that the Network names for the first time (the one that answers DHCP, a gateway of its security) must be in its scope.
  - A Node: it is in the VRF of the Network and in no other. It sets its key, its VRFs, tags, addresses, rate limit, owner and scope, and no other field. The relay, the LAN subnets, the WireGuard end, the tunnel endpoint, the endpoints that other Nodes dial and the mark `nonExpiring` reach the Nodes of the other Networks of the VRF or the hosts around them, so they are the global roles'. Its tags are tags of the Network: its name, or a name that starts with it and a hyphen (the longest Network name wins), or the name of a Group in its scope. Its owner is a User of the scope.
  - A User: it belongs to Groups of the scope only. A Group that a scoped role makes takes the name of a tag of the Network, since the name of a Group is a tag of policy.
  - A Policy: a rule of the VRF of the Network between ends that are in it. Each end names tags of the Network or addresses in its pools. An end that names nothing is any end, and is refused.
  - A User that holds an API role, of any kind, is never changed, deleted or given a password by a scoped role: who may manage the Controller is for the global roles to say. The password of any other User of the scope is set with the permission `users`.
- **Quotas.** A change that takes a count over its quota is refused with 403, and the answer names the Network, the quota and the count that the change would make, for example `Network "branch-a" allows 3 users at most, and the change would make 4`. A change that adds nothing to a count passes, so a Network that is over a quota that was lowered later can still change what it holds and shrink. A refusal for the scope comes before one for a quota, and the two are not mixed. A device of a User of the scope counts as a Node. The bandwidth quota bounds the rate limit of each Node that the change makes or changes, and a Node with no rate limit, which sends at any rate, is over it. The sessions quota is kept at the door. The control stream of a Node of a Network whose open sessions are as many as the quota is refused, as one from outside its enrolment sources is (the amendment of 2026-10-23): with `REFUSE_REASON_UNKNOWN_NODE`, a message that names the Network and the quota, and a failed authentication in the audit log. The Node dials again after the delay of a refused stream and is admitted when a session of its Network has ended. A new stream of a Node that has one open replaces it, and does not count against itself. A session is the control stream of a Node (SDN-50), so a role with the permission `sessions` lists the sessions of the Nodes in its scope and ends one, and the audit log records both as `session-list` and `session-disconnect`, as it does for the operations of SDN-50.
- **Provider groups.** A provider group is a group of an identity provider, as the provider names it: a text of at most 256 bytes with no control character, matched as it is written, the case too. An admin maps it to a role that is held for the whole API or for one Network, and the members of the group get that role and that scope (story 21 of the spec). A mapping is no part of the Intent, for the reasons of an API role. It lives in the store (table `provider_groups`), and a store backup holds it. A login through the provider hands the groups of the person to `IssueProviderToken`, which gives the User a user token with the role that those groups give and the scope of their mapping, and nothing more. The groups that the person is not in give nothing, and a group that is mapped for one Network gives that Network and never the whole API. The User needs no API role of its own, and the login makes none. The role is fixed when the token is made (table `user_token_grants`), so a person that changes team gets the role of the new groups at the next login, and the old role ends with the token. A mapping that is deleted leaves the tokens that it made until they end. When the groups give several roles, a login that names no Network gets the greatest role of those for the whole API, else the role for the one Network that the groups name, and groups that give roles for several Networks and none for the whole API are refused until the login names one (`ErrAmbiguous`). A login that names a Network gets the greatest role of those for the whole API and for that Network, held for that Network: asking for a Network narrows a role of the whole API and never widens one. Groups that no mapping names give no token (`ErrNoRole`).
- **Not here.** The identity providers (SDN-34 to SDN-36). `IssueProviderToken` is for their logins to call. No login calls it yet, so a mapping gives a role to nobody until they come. A verb of `ranz` and a page of the web UI for scoped roles, delegations and provider groups: the API and its Go client have the calls, and `ranz token create` and `ranz user role set` make roles for the whole API. The bans, the MAC and IP tables and the keys of the Nodes, with the approval of a Node that waits (SDN-50 and SDN-56): a role held for a Network is refused every path outside its own Network, so they stay with the roles of the whole API. The permissions for bridges and logs that story 24 names: there are none, and those settings stay with the roles of the whole API too.
- **CI.** `controller/internal/controller/scope_test.go` runs the controller conformance with the node simulator, through the HTTP API. A scoped admin changes only its Network and the permitted kinds, and each refusal changes nothing and sends the Nodes nothing (`TestAScopedAdminChangesOnlyItsNetworkAndThePermittedKinds`). Exceeding a quota is refused with the count, and the control stream of a Node over the sessions quota is refused (`TestExceedingAQuotaIsRefusedWithAClearError`). A provider group that is mapped to a scoped role gives exactly that scope (`TestAProviderGroupMappedToAScopedRoleGrantsExactlyThatScope`). Tokens and Users hold a role for a Network alike, the role of a token changes with its scope kept, and a Network that goes takes what was held for it (`TestARoleHeldForANetworkIsHeldByUsersAndTokensAlike`). The package `scope` is new, with a coverage floor of 95, and tests the check on intents that it builds (`TestACallerChangesOnlyWhatIsInItsScope`, `TestTheDelegationPermitsTheKindsThatItNames`, `TestAChangeThatTakesTheNetworkOverAQuotaIsRefused`, `TestANetworkOverAQuotaCanStillShrink`, `TestTheBandwidthQuotaBoundsTheRateLimitOfANode`, `TestTheScopeIsToldBeforeTheIntent`, `TestAScopedRoleLeavesTheUsersThatHoldARoleAlone`). `api` (`scoped_test.go`) tests the Guard: a role held for a Network passes `whoami` and the calls of its own Network and nothing else, with every path that climbs out of it (`TestAScopedTokenPassesOnlyTheCallsOfItsNetwork`), and the role that each call needs (`TestTheRolesOfTheScopedCalls`). `rbac` (`scoped_test.go` and `grant_test.go`, with the fuzz target `FuzzParseGrant`) tests the grants, the scoped tokens and the roles of Users, the provider groups and what goes with a Network (`TestScopedTokens`, `TestScopedUserRoles`, `TestProviderGroupsGiveTheirScopeAndNoOther`, `TestDeleteScopedAccess`), and `intent` (`scope_test.go`) tests the scope of a resource.
