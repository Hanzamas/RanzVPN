# ADR-0026: The controller is a separate Go service with rqlite as its store

**Status:** Accepted (2026-10-20, from the SDN spec #176 that Hilmi filed; recorded by SDN-1, #177). Supersedes the `controller` role of ADR-0022 (one active plus a passive standby inside the node binary), CORE-S5-1 (#77) and CORE-S6-2 (#81). See the ADR-0011 and ADR-0022 amendments of 2026-10-20.

## Context

ADR-0022 put a `controller` role into the node binary, one active per deployment plus a passive standby, and left route advertisement, approval, health checks, ECMP and controller failover for a later spec. The SDN of #176 needs much more from the control plane: an intent store with revisions, IPAM and DNS zones, compilation of intent into per-node desired state, a web UI, an HTTP API and a CLI, licence checks, event and metrics export, and high availability without manual failover.

Replicated stores on Windows (research of 2026-10-20, #176):

- **hashicorp/raft** (used by Consul and Nomad on Windows) and **rqlite** (Windows binaries, Raft failover) work.
- **dqlite** and **LiteFS** have no Windows support. **Litestream** is backup only. **sqld** has no native Windows build. **Embedded etcd** is Tier 3 on Windows.
- **Postgres** would add a database server to every installation, including a small site with one controller.
- The stores that work on Windows (rqlite, hashicorp/raft) are Go, as is GoBGP behind the `ranz-bgp` sidecar (ADR-0010).

## Decision

1. **`ranz-controller` is a Go service** that runs as a Windows service, or as a Linux service or container. It is the single authority: it stores intent, owns IPAM and DNS zones (ADR-0028), compiles intent into per-node desired state and pushes it over the Noise control stream (ADR-0027), serves the web UI, the HTTP API and the `ranz` CLI (ADR-0031), checks the licence (ADR-0036), and exports events and metrics (ADR-0030).
2. **The node is the data plane only.** The `controller` role leaves the node binary; its roles are `server`, `client`, `bridge` and `relay` (ADR-0011 amendment of 2026-10-20).
3. **The store is rqlite, run as a sidecar of each controller**, with one code path for a single member and for a 3 or 5 member cluster. If rqlite proves unreliable on Windows, the fallback is hashicorp/raft embedded in the controller with an SQLite state machine, the library that rqlite itself uses. Postgres is not used.
4. **A single controller with its embedded store is the default**, so a small site runs one process and no database server. It grows into a 3 or 5 member cluster, so losing one (or two) members does not stop management. The cluster elects a new leader by itself; a failed controller host needs no manual failover.
5. **A control-plane outage is not a data-plane outage:** nodes keep forwarding with their last applied Generation when every controller is down (ADR-0027).
6. **The node keeps `winsqlite3` for its local state** (ADR-0022). The intent lives only in the controller.
7. **Scale target: one controller cluster handles 10,000 nodes, 1,000 VRFs and 100,000 routes**, so management is not split early. Federation between controllers is after v1.

## Consequences

- A new test seam, and the only new one of #176: **controller conformance with a node simulator.** The simulator is a protocol-only node (no Wintun, no data plane) that speaks nanopb over Noise to the controller. Tests apply intent through the public API and assert the control messages each simulated node receives and acknowledges, including controller failover in a 3 member cluster and the scale target.
- CI gains a Go build and test job for the controller (SDN-2, #178).
- The controller is a second product binary next to `ranz-node`, with its own Windows service and Linux packaging.
- To verify during the work: rqlite's Windows support level in practice. A failure there moves the store to the hashicorp/raft fallback without changing the API.
- Tickets: SDN-2 (#178), SDN-17 (#193), SDN-18 (#194).

## Amendment 2026-10-22: how the cluster elects its leader and upgrades (SDN-17)

Recorded by SDN-17 (#193) for the points where #176 and this ADR leave the mechanism open. Decision 3 holds: rqlite, one sidecar per controller, one code path for one member and for 3 or 5.

- **Members.** Each host runs one `ranz-controller` with its own `rqlited`. The rqlite members form one Raft cluster through rqlite's automatic clustering: every member starts, at every start, with the Raft addresses of all members (`-rqlite-join`, rqlited `-join`) and the cluster size (`-rqlite-expect`, rqlited `-bootstrap-expect`). Without `-rqlite-join` the controller is a cluster of one member, as before, with the rqlite node id `1` of SDN-2. `rqlited` ends with its controller, also when the controller is killed (Pdeathsig on Linux, a job object with kill-on-close on Windows), so a restarted controller finds its ports free.
- **The leader holds a lease in the store, not the rqlite leadership.** One row of rqlite is the lease, in the way of the Kubernetes Lease (client-go `tools/leaderelection`, the reference implementation): the holder renews it every fifth of the lease duration (15 s by default, `-lease`) and steps down when it could not renew for two thirds of it; a standby takes it over once it has seen it unchanged for the whole duration on its own clock, at once when it is free or holds the standby's own name (a restart). A controller that crashes while its rqlite member lives on therefore still fails over, and the Raft leader of rqlite may be any member.
- **Fencing.** Each take-over and each release ends an epoch of the lease. Every write of the leader carries, in the same rqlite transaction, a statement that breaks a CHECK constraint when the lease has another epoch, so rqlite rolls back the whole write: a leader that lost the lease and has not noticed yet writes nothing.
- **Only the leader runs the controller:** it loads the intent and the node states from the store when it takes the lease, applies, compiles, pushes and stores the Acks. A standby refuses a node with `REFUSE_REASON_NOT_LEADER` and the address of the leader, and forwards every API call except the status to the leader, checking the leader's TLS key against the lease, so management works through any member. A forwarded call carries the caller's bearer token (SDN-14, #190), which the standby and the leader both check: the API tokens are in the store, so every member knows them.
- **The members reach the nodes through schema version 2:** the Controller resources of the intent (address and Noise key of each member) go to the nodes of version 2 in a `Controllers` message, outside the Generations, so a node can reach every member. Nodes of version 1 keep working with the members they were given.
- **Rolling upgrade.** A controller of version N serves nodes of N and N-1 (ADR-0027). During a rolling upgrade, the members of the new release start with `-schema-version N-1` until every member runs the new release, in the way of the compatibility version of Kubernetes (`--emulated-version`, KEP-4330): a member that runs as N-1 serves the nodes N-1 serves, sends nothing that N-1 lacks, and refuses resources that N-1 does not know (the Controller resources for version 1). Then the members restart at N one after the other, and the fleet follows.
- **rqlite on Windows** works in practice: the cluster tests run three members, each with its `rqlited`, on the Windows and on the Linux runner, so the hashicorp/raft fallback is not needed.
- **CI** proves it with three controller processes on one runner (`controller/cluster_test.go`): a killed leader is replaced and applies keep working, the nodes keep their last applied Generation while no member is reachable, and a rolling upgrade from version 1 to version 2 keeps the cluster and the nodes working.

## Amendment 2026-10-23: the Controller is the subcommand `ranz controller` (ONE-1)

Recorded by ONE-1 (#310), from the ADR-0011 amendment of 2026-10-22 (the product ships as one `ranz.exe`).

- **`ranz-controller` is no executable of its own.** The Controller is the subcommand `ranz controller` of the one Go executable `ranz`: `ranz controller` runs it in the foreground or as the Windows service, and the commands `install`, `uninstall`, `reset-admin`, `backup` and `restore` follow the subcommand. Its code is the package `controller` in `controller/`, which `controller/cmd/ranz` links. The CLI of ADR-0031 is the same executable.
- **The service keeps its name, `ranz-controller`,** and with it the virtual account `NT SERVICE\ranz-controller` (ADR-0039) and the event source of its Application log entries. The service runs `ranz.exe controller` with the flags it was installed with. The data directory stays where it was.
- **The cluster tests** run the test binary as each member through the package's `Main`, in `controller/cluster_test.go`, which the sentence about CI above names. ONE-4 (#313) starts the members from `ranz` itself.

## Amendment 2026-10-23: the rqlite member is a Payload of ranz.exe, not a subcommand (ONE-4)

Recorded by ONE-4 (#313), which the amendment above left open: its ticket says "a payload or a subcommand: the ticket picks the one that passes the high-availability scenarios". Decision 3 holds: rqlite, one sidecar per controller, one code path for one member and for 3 or 5.

- **It is a Payload.** The rqlite member of a Controller is the `rqlited.exe` of the pinned rqlite release, carried inside `ranz.exe` as a Payload of the mechanism of ONE-2 (`controller/internal/payload`) and run as a separate process, as decision 3 says. `ranz controller` with no `-rqlited` writes it as `payload\rqlited.exe` under its data directory with `payload.Ensure`: when the file is missing, or differs in one byte from the one `ranz.exe` carries, the copy of `ranz.exe` is checked (its SHA-256, then its Authenticode signature) and put in place by an atomic rename. So deleting the file while the Controller is stopped does not break the next start, and a changed file is replaced by the carried one. `reset-admin`, `backup` and `restore`, which start the member while the service is stopped, do the same. `-rqlited PATH` runs another rqlited, and `-rqlite-external` runs none and uses the rqlite that answers at `-rqlite`. A Controller that `ranz install --controller` registered has no flags, so it runs the member of its own `ranz.exe`.
- **Where it is written.** `payload\` under the data directory, which has the ACL that the controller gives the data directory: full control for SYSTEM, the Administrators, the owner and the service account, nothing for anyone else. `payload.Install` asks for a directory that only SYSTEM and the Administrators can write, so that no other account can replace the temporary file between the check and the rename. Here the account that runs the file may write it too, because a Controller that could not write its member could not write it again at its next start (criterion 4), and that account already controls its own process and its child, so nobody else gains a way in.
- **It cannot be a subcommand.** `ranz rqlited` would have to run rqlite inside the process of `ranz`, and two facts rule that out. First, `rqlited` is the `main` package of rqlite's module and imports packages under rqlite's `internal/`, which no other module can import, so a subcommand needs a copy of rqlite's start-up code. Second, rqlite's database layer is written against the cgo SQLite driver (`github.com/mattn/go-sqlite3`), which without cgo is a stub that lacks what rqlite uses (`SQLiteStmt`, `Version` and the methods of `SQLiteConn`), so rqlite does not compile with `CGO_ENABLED=0`. `ranz` is built without cgo for Windows x64 and arm64, on a Linux runner and on both Windows runners, and the ADR-0011 amendment of 2026-10-22 already declines cgo with a second toolchain for the Node. Forking rqlite's start-up code and giving every target of `ranz` a C toolchain would cost more than carrying the file.
- **The pin.** The rqlite version is pinned by `RQLITE_VERSION` in ranz.yml and in windows.yml, which hold the same value (ranz.yml checks it), and ranz.yml checks the SHA-256 of each release archive it downloads against the digest of that release. The Windows x64 job signs the `rqlited.exe` of the archive with the self-signed certificate of CI before it embeds it; the production certificate signs it at release, as it signs `ranz-node.exe`. A new version changes the pin, the digests and the NOTICE together, and ranz.yml checks that the NOTICE holds the licence text of the pinned tag.
- **Windows arm64 and Linux.** rqlite publishes a Windows build for x64 only (`rqlite-vX-win64.zip`), and building it for arm64 needs cgo with an arm64 C toolchain. So the member of the arm64 `ranz.exe` is the x64 `rqlited.exe` of the release, which Windows 11 on ARM runs under emulation. Windows 10 on ARM runs no x64 programs, and a Controller there runs `-rqlited PATH` or `-rqlite-external`. A `ranz` for Linux carries no member, because the Authenticode check is Windows only; it keeps `-rqlited`.
- **Licence.** rqlite is MIT. Its release binary also holds SQLite (public domain) and Go libraries under their own licences, among them the HashiCorp libraries under the Mozilla Public License 2.0. It runs as a separate process and is not modified, so ADR-0036 decision 6 holds. The NOTICE of `ranz` holds the MIT text of the pinned tag and says where the sources are.
- **CI** proves it on the Windows x64 runner: the job embeds the signed `rqlited.exe` and runs the cluster tests of SDN-17 with each member the executable `ranz` itself, which writes its own rqlited from its Payload (no `-rqlited`, so no rqlited beside `ranz`), including a member whose file was deleted while it was stopped. The tests build that `ranz` with `go build` from the checkout, in a directory of its own, with the vendor key of the tests linked in the way a release links its own (`licence.vendorKeys`): a cluster needs an Enterprise licence key (ADR-0036), and only the vendor can sign one for the build that ships. This replaces the test binary that the cluster tests ran as each member in ONE-1, and the variable of the controller that only that binary set. The job also runs the Windows service of the `ranz.exe` that it builds as it ships, with no rqlited beside it: the service serves the API, writes the file again after it was deleted while the service was stopped, and `reset-admin` with the service stopped writes it itself. The arm64 job writes out and starts the x64 member under emulation.

## Amendment 2026-10-26: the certificate of the Controller (SDN-92)

Recorded by SDN-92 (#397). Until now the TLS port of the Controller always served the self-signed certificate that the first start made from its TLS key. The web UI, the API and the control streams of the Nodes share that port, so one certificate serves all three.

- **An operator sets the certificate; without a setting nothing changes.** `ranz controller-cert set`, `show` and `clear` call `PUT`, `GET` and `DELETE` of `/api/v1/controller-certificate` (package `controller/internal/servercert`). A `GET` needs the viewer role and the other two the operator role, as every call that changes something does (`api.Needs`). `show` prints the source, subject, issuer, names, thumbprint, TLS fingerprint and end, and never a key. With no setting the Controller serves its self-signed certificate, with the same fingerprint after every restart, as before.
- **Three sources, the ones of a Listener (SDN-45).** A PEM file with its key, as `ranz cert` writes them, at absolute paths that the account of the service (`NT SERVICE\ranz-controller`) can read; a certificate of the `My` store of the machine, or else of the user, named by its SHA-1 thumbprint, whose key stays in the Microsoft Software Key Storage Provider and signs there (ECDSA P-256, the keys that `ranz cert -ksp` makes); and an ACME service, whose HTTP-01 challenge the plain HTTP port of the Controller answers when it has one (`-http-listen`), or a port that each run listens on. The ACME certificate is made for the TLS key of the Controller itself, so its fingerprint does not change when it renews, and it is renewed in the process, 30 days before its end unless the setting says otherwise.
- **The Controller checks it before it serves it,** and refuses it with the reason: a key that is not the key of the certificate, a certificate that has ended or is not valid yet, a CA certificate, one that is not for a server, a key that the Schannel of the Nodes does not take (ECDSA P-256 and P-384, RSA of 2048 bits and more), and one that does not name each host of the setting and the host of `-advertise`. The certificate in use stays.
- **A new certificate goes to the next handshakes,** through `tls.Config.GetCertificate`; a connection that is up keeps the one it has. The fingerprint that the Nodes pin changes with the key, so the change first sends the Nodes the new fingerprint (ADR-0027 amendment of the same day).
- **The setting is in the store, outside the Intent:** one row of `controller_certificate`, with the fingerprint it was set with, so no revision, rollback or import changes it, and a backup of the store holds it. Each member of a cluster reads the row (every 2 seconds) and loads its own copy of the certificate: the files, or the thumbprint, must be on each member's PC. The lease holds the fingerprint that the member serves, which the standbys check when they forward a call. An ACME setting is for a Controller of one member: each member has a TLS key of its own and would ask the service for a certificate of its own. A member whose run of the ACME client failed for a setting, as a standby that cannot answer the challenge does, asks the service again for that setting after 10 minutes, not at each look at the store.
- **A setting that cannot be loaded at the start** (a file that is gone, a key that the service may not read) leaves the Controller on its self-signed certificate, with a warning in the log that says why, and it serves the certificate as soon as the setting can be loaded. A Node that was told only the new fingerprint does not reach the Controller meanwhile; the warning names the cause.
- **CI.** The conformance seam replaces the certificate under connected stand-in Nodes (`controller/internal/controller/certificate_test.go`); `controller/certificate_test.go` runs `ranz controller` itself; the Windows job tests a certificate of the key storage; the step `Controller certificate with ACME` of windows.yml runs the ACME source against Pebble, as SDN-45 tests its own; and step 21 of the first-test runbook replaces the certificate of a real Controller with one that `ranz cert` made, under the Node service of the runner.

## Amendment 2026-10-27: the credential of the store and the certificates of the members (AUD1-DT-8)

Recorded by AUD1-DT-8 (#456), from gaps G-18 and G-19 of the audit (#362): until now the Controller started `rqlited` with no credential and no encryption (ST-1, ST-2 of the threat model), so any local process read the store, `api_tokens` included, and any host that reached the Raft port could read the traffic of a cluster or join it. Decision 3 holds: rqlite, one sidecar per Controller, one code path for one member and for 3 or 5.

- **The credential.** The first start of a single Controller makes a random password (256 bits, `crypto/rand`) and writes it to `rqlite-auth.json` in the data directory, in the file format that `rqlited -auth` reads (one user, `controller`, with permission `all`), readable by its owner only, and starts `rqlited` with `-auth`. The data directory has the protected access list of ONE-4 (full control for SYSTEM, the Administrators, the owner and the service account, inherited), so a local process that is none of them reads neither the file nor the data of `rqlited`; the file is never replaced once it exists, and the password never appears on a command line. A request to the HTTP port of `rqlited` with no credential, or a wrong one, gets 401, `api_tokens` included. A store that already holds data starts with `-auth` at its next start: the credential is a start option of `rqlited`, not a change of the data.
- **Who sends it.** The store client (`store.OpenWith`) puts the credential in every request, those of gorqlite and the ones beside it (the status, the backup, the restore). `reset-admin`, `backup` and `restore` read the file in the data directory, so they work against the running service and against the stopped one, whose `rqlited` they start with `-auth` and the same file.
- **A cluster has one credential.** A member does not make the file: every member must hold the same credential, because the members join one another with it (`-join-as`), and two members that each made one could never join. The operator copies `rqlite-auth.json` of the first member (a single Controller made it at its first start, or any Controller that is not part of a cluster yet) to the data directory of each other member, with the same access list, before the members start. A member of a cluster with no file refuses to start and says so.
- **The certificates of the members.** The Raft transport and the node API of a cluster use mutual TLS: `rqlited` starts with `-node-cert`, `-node-key`, `-node-ca-cert` and `-node-verify-client` (rqlite has no `-node-encrypt` flag of its own: a certificate turns the encryption on), so a member that does not present a certificate of the cluster CA is refused, in both directions. The flags of the Controller are `-rqlite-node-ca-cert`, `-rqlite-node-cert` and `-rqlite-node-key`, all three or none, and `-rqlite-join` needs all three: a cluster with no mutual TLS does not start. **How the members get their certificates is the operator's decision: one CA of the cluster signs one certificate for each member**, with the host of its `-rqlite-raft` among its names and the uses of a server and of a client, for example with `ranz cert -signcert` (SDN-53). This is the model of rqlite and of Consul, and the Controller makes no CA of its own: a CA that every member held would be one key that opens the whole cluster, and a member that generated its certificate at its first start would have to be trusted at that moment, which is the trust the certificate exists to replace. The CA certificate is public; the key of the CA stays with the operator, off the members. These certificates are not the TLS certificate of the Controller (SDN-92): that one serves the web UI, the API and the Nodes, and this one serves the members to each other.
- **`-rqlite-external`.** The `-rqlite` URL of an external rqlite is `https`, with the CA that signed its certificate in `-rqlite-ca` (the system roots when it is empty), or `http` to a loopback host. A plain `http` URL to any other host is refused when the flags are read, before anything connects: it would carry the credential and the store across the network in clear text. The credential of an external rqlite is the file that `-rqlite-auth` names; with none, it is reached without a credential, as a loopback rqlite of another process may be.
- **Not changed.** The HTTP API of `rqlited` stays on the loopback address of its member (`-rqlite`), as the store package says, so only the Raft transport and the node API of a cluster cross the network. The cluster tests of SDN-17 still run three members with their own `rqlited`.
- **CI** proves it: `controller/rqliteaccess_test.go` runs `ranz controller` with its `rqlited`, shows the 401 with no credential and with a wrong one and the answer with the right one, and runs `reset-admin`, `backup` and `restore` against the running service and the stopped one; `controller/cluster_tls_test.go` and every cluster test of `controller/cluster_test.go` run three members with certificates of a CA of the test and one shared credential, and a fourth `rqlited` that joins with no certificate, or with one of another CA, is refused and never becomes a member; and the flags tests refuse a plain URL that is not loopback.

## Amendment 2026-10-27: the files of the Controller's host (AUD1-DT-10)

Recorded by AUD1-DT-10 (#458), from gaps G-20 and G-22 of the audit (#362): the data directory of the Controller could be a local user's, a backup took the access list of the folder it was written to, and the secrets of the export and audit targets were in the store in clear (ST-3 and ST-4 of the threat model). Decision 3 holds, and so does the data directory of ONE-4: this changes who owns it and what the store keeps in it.

- **The data directory has an owner.** `C:\ProgramData` lets every user make a folder, so a local user can make `C:\ProgramData\Ranz\controller` before the install, and whoever owns a folder can change its access list and put files in it: the `rqlited.exe` that the service starts from it, and a store that holds a token that the user knows. The access list of ONE-4 holds the owner of the folder, so a folder that a user made first gave that user full control in it. Now the data directory belongs to SYSTEM, the Administrators or the account of the service (`NT SERVICE\ranz-controller`). `ranz install` makes the directory with the Administrators as its owner and the protected access list, as `NodeMakeDataDir` does for the Node. A directory that exists and that SYSTEM, the Administrators, the service's account or the administrator who installs owns is kept, with what it holds, and gets that owner and that list. A directory that any other account owns is **not adopted**: its owner may have put anything in it, and may hold it open, and a handle that was opened before the access list changed still writes to it after. The install makes it again: an empty one is removed (which fails while anybody holds it open) and made anew, and one that holds anything, that is a link (a junction or a symbolic link, which the install never follows), or that cannot be read or removed is refused with a message that says what to do. Taking over a directory in place would have given the Administrators the files of the user.
- **The service refuses a directory that is not theirs.** The service refuses to start in a data directory that an account other than those three owns, and so does `ranz controller reset-admin`, `backup` and `restore`, which run the `rqlited` of its `payload` folder as the administrator who calls them; a data directory that is a link is refused the same way. The check ends the start before the service makes a file, writes a failure to the Application log (event ID 3) that names the owner, and leaves the directory as it was. This is what keeps out a directory that a user put in the place of the real one, for instance while the service is stopped, which the install cannot see. The log file that the service opens at its start holds the directory against a rename from then on. A user who owns the folder above the data directory (`C:\ProgramData\Ranz`, when the user made it first) can still make the start of the service fail that way, and nothing else: the start fails, and no file of the user's runs. On Linux the init system owns the directory, and the check does nothing.
- **A backup has an access list of its own.** The file of `backup` is made with the mode 0600, which Windows ignores, so it took the access list of its folder: a folder that the Users group may read gave Users the backup. The temporary file that `backup` writes first is now made with a protected access list for SYSTEM and the Administrators, whatever its folder says: `CreateFile` gets the list with the file, so the file never has the list of its folder, and it is opened for the backup alone until it is renamed to the file that was asked for. Setting the list after the file was made would not do: Windows checks the list when a handle is opened, so a member of the Users group that opened the file in between would keep a handle that reads the whole backup. A file of that name that an earlier backup left is removed, and one that somebody holds open makes the backup fail. On a volume that has no access lists, such as a FAT drive, `backup` says so, and the backup there is as readable as the volume. Elsewhere the mode is 0600, set again on a file that existed.
- **The secrets of the targets are sealed.** The secret of an export or audit target, the HMAC key of a webhook or the bearer token of an OTLP endpoint, was in the JSON of its row, so in the store, in every backup and in what a thief of the disk or of a snapshot reads. Now the store keeps it as a **Sealed secret**: `ranz-sealed:1:` and the base64 of a sealed box that only the **Sealing key** of the Controller opens. The Sealing key is a persisted X25519 key of the Microsoft Software Key Storage Provider, not exportable, named after the data directory, a key of its own beside the Noise static key and the TLS key (`controller/internal/keys`, kind `Store`), and its Diffie-Hellman runs inside the provider, so the private key never enters the memory of the Controller. It is in the key set of the account that runs the process: the service's account for the service, the machine key set for the commands of an administrator. A file `store.key` of mode 0600 in the data directory stands in for it on Linux. `Seal` makes an X25519 key pair for each secret, agrees a secret with the public Sealing key, derives an AES-256-GCM key by HKDF-SHA256 with both public keys as the salt, and forgets the private half; the label of the secret (`export_targets:<name>` or `audit_targets:<name>`) is authenticated with it, so a sealed secret copied into another row, or into the other table, does not open there (since the amendment of 2026-10-30 the label holds the SHA-256 of the URL of the target as well). `Open` fails with `ErrNotSealed` for anything that this key did not seal under that label, and has a fuzz target. The store seals what `PutTarget` and `PutAuditTarget` write and opens what `Targets` and `AuditTargets` read, so the exporters and the API see the secret as they always did, and the API still never returns it. At each start the Controller seals the secrets that an earlier release left in clear and logs how many; a store that no key opened never gets a secret rewritten. (The old text of such a secret stays in the data of `rqlited` beside the table, and the URL of a target is not sealed: the amendment of 2026-10-30, AUD1-DT-17.) The same mechanism is what a later ticket uses for another secret that the store holds (`keys.Sealer`, with a label of its own).
- **What a restore does.** A backup holds the secrets sealed, so a restore on the same host, whose Sealing key is the same, keeps the targets working. The key is named after the data directory and kept in the key storage of the host, so a restore on **another host**, on a host whose key storage was rebuilt, or with the data directory at another path, does not open them: the targets come back with their names, their URLs and their types and **with no secret**, the Controller sends to them with none (a webhook unsigned, an OTLP endpoint with no bearer token), logs at its start which targets lost theirs (`the secret of a target cannot be opened with the sealing key of this host`, once for each, with its kind and its name), and `GET /api/v1/targets` shows `hasSecret` false for each. The operator puts each target again with its secret, through `PUT /api/v1/targets/{name}` or `/api/v1/audit/targets/{name}`, which seals it with the key of the host. The text of `ranz controller backup` and of `restore` says so. This is the price of a secret that a copy of the disk or of a backup does not give away.
- **A cluster keeps them in clear.** The members of a cluster have no Sealing key in common: each has its own key in its own provider, and the member that leads next could not open what the member before it sealed. A Controller started with `-rqlite-join` therefore keeps the secrets of the targets as they are put, in clear, as before, says so in its log at each start, and says so in the text of `backup`. A key for the whole cluster is a decision about how the members would share it, and is left to a ticket of its own; ST-4 stays partial for a cluster. (Superseded by the amendment of 2026-10-29, AUD1-DT-16: a cluster seals them with its Cluster key.)
- **What a backup holds.** The text of `ranz controller backup` names everything that the store keeps: the Intent with every revision, the states and the Capabilities of the Nodes, the events and the audit log, the settings (the lists of admin sources and destinations, the certificate of the Controller), the leases of DHCP, the hashes of the API tokens and of the passwords of the users, the licence key (which can be copied, and whose watermark names its customer), and the secrets of the targets. It also says who may read the file and what a restore on another host does. It is not a list of secrets: a backup holds no key of the Controller, and no credential of `rqlited` (`rqlite-auth.json` is in the data directory, not in the store).
- **CI** proves it. On Windows: `datadir_windows_test.go` makes the data directory of a standard user (an account that is none of the trusted ones, with the right to restore that an elevated Administrator holds), and shows that the install takes over an empty one, with the Administrators as its owner and a protected list that the user and the Users group are not in, refuses one that holds files, a link, or a folder that is held open, and leaves them as they were, and that the start of the service, `run`, `reset-admin`, `backup` and `restore` refuse it; `backup_windows_test.go` writes a backup into a folder that the Users group may read, and a standard user cannot read it while an Administrator can, and shows that its temporary file has its list before its first byte, gives no second handle to anyone while the backup writes it, and is never made in the place of a file that a standard user holds open; the step of `controller-service.ps1` runs the same on the real service (`controller-hostfiles.ps1`: the owner of the data directory after the install, the access list of a backup made by `ranz controller backup`, the sealed secret of a target put through the API, a restore of that backup under the running service that brings the target back with its secret, and a service that does not start when the Users group owns its data directory and starts again once the Administrators do); and the first-test runbook reads the owner and the protected list of the data directory of a real install (step 6). Everywhere: `controller/internal/keys` (the sealed box, the labels, a changed byte, the key of a data directory across two loads, the fuzz target), `controller/internal/store/sealed_test.go` (the table of the targets shows no secret in clear, a secret that another key sealed, a sealed secret copied to another row, the secrets of an earlier release sealed at the start), `controller/internal/controller/sealed_test.go` (a webhook is signed with its secret through the API, and again after the Controller starts again), and `controller/backup_sealed_test.go` (a backup and a restore on the same host keep the secrets working, on another host the target loses its secret and the store says which, and the message of `backup`).

## Amendment 2026-10-29: the keys of the WireGuard Devices (SDN-82)

Recorded by SDN-82 (#377), from gap G-28 of the audit (#362) and the spec of the WireGuard Devices (#374): an administrator makes a Device without knowing anything about WireGuard keys, so the Controller makes keys, and has to decide which of them it keeps.

- **The private key of a Device is never kept.** The Controller makes the key pair of a Device in the memory of the one call that makes it (`POST /api/v1/devices`, `ranz device create`, the Devices page), puts the private key into the finished configuration and the QR code of that one answer, and forgets it. It is in no row of the store, resource, revision, export of the Intent, state of a Node, log, audit record or diagnostics bundle. The answer says `Cache-Control: no-store`, and a second call for a Device that exists is refused with 409: a key is never changed in place, and rotation is a new Device and the delete of the old one. When the administrator supplies the public key of the Device, a router or an advanced user, the Controller never sees a private key.
- **The PresharedKey is a Sealed secret.** Every Device that the Controller makes has one unless the administrator asks for none (`noPresharedKey`), shown once with the private key, and carried in the configuration. It is the only protection of a recorded WireGuard session against a future quantum computer, and the gateway needs it to terminate the Device, so the Controller keeps it, sealed to its Sealing key as the secret of a target is, in the table `device_keys` under the label `device_keys:NAME`. It is no part of the Intent, so no revision, export or rollback holds or changes one: a rollback that brings a Device back brings it without a PresharedKey, and the Device is made again to get one. The states that the Controller stores and compares hold it sealed. The Update that carries a Device to its gateway has it opened, and no other Node gets it: it is in clear inside the control stream to that gateway. A Device that an apply declares has none. A Device that was made before SDN-82 has none either, and the Controller adds none to a Device that exists.
- **What a restore does.** The same as for the targets: a restore on another host brings the Devices back with a PresharedKey that does not open, and the log of the Controller says so once for each Device, at the start. The gateway then terminates the Device without its PresharedKey, and a client that holds it completes no handshake until the Device is made again.
- **A cluster makes no PresharedKey.** The members of a cluster have no Sealing key in common (the amendment of 2026-10-27), and a PresharedKey is never kept in clear. A Controller started with `-rqlite-join` therefore refuses to make a Device that has a PresharedKey, with a message that says so, and makes one with `noPresharedKey`; it says so in its log at each start. A key for the whole cluster is the decision that the amendment of 2026-10-27 leaves to a ticket of its own, and it would give the Devices of a cluster their PresharedKeys.
- **CI** proves it. `controller/internal/controller/devicekeys_test.go` makes a Device through the API and searches the store with the files of its `rqlited`, the log, the audit log, the revisions, the export, the diagnostics bundle and the frames of the Nodes for the private key and the PresharedKey in every form that a key is written in, and finds the private key nowhere and the PresharedKey in clear in the frames of the gateway alone; it opens the sealed key of the store with the Sealing key, and with no other key and no other label; it restarts the gateway and the Controller; and it makes a Device with no Sealing key, and with a provider that is locked. The step WireGuard Device tracer of `windows.yml` has a stock WireGuard client (`wireguard-go`) take the configuration that `ranz device create` made, complete its handshake with a gateway Node that applies the PresharedKey in WireGuardNT, and reach an overlay host, while the same configuration without its PresharedKey line gets no handshake, and the client of a revoked Device gets none either.

## Amendment 2026-10-29: the Cluster key (AUD1-DT-16)

Recorded by AUD1-DT-16 (#501), which the amendment of 2026-10-27 (AUD1-DT-10) left to a ticket of its own: a cluster kept the secrets of its targets in clear, and made no Device with a PresharedKey (the amendment of SDN-82 above), since its members have no Sealing key in common. Decision 3 holds, and so does the Sealing key of a single Controller.

- **One Cluster key, wrapped to the Sealing key of each member.** A cluster seals the secrets of its export and audit targets, and the PresharedKeys of its Devices, with one key of its own, the **Cluster key**: a random X25519 key that seals a secret as a Sealing key does (`keys.Sealer`, the sealed box of AUD1-DT-10 with the label of its row), so the Sealed secret of a cluster has the form of the one of a single Controller. The store holds the public half of the key (table `cluster_key`), by which the members know which key is the cluster's, and for each member, by its `-name`, the public half of the member's Sealing key and a **copy** of the Cluster key sealed to it under the label of the row (table `cluster_key_copies`), in the form of a Sealed secret. Only that member opens its copy, inside its own key storage provider, and it holds the Cluster key in its memory only. So no key of a provider leaves its host, and no row, no backup and no log holds the Cluster key or a private key. One key of the provider that the members shared is not possible: a key of the Microsoft Software Key Storage Provider is not exportable, and a key that left the provider is what ST-4 keeps out.
- **How a member gets the key.** At each start a member publishes the public half of its Sealing key in its row (`controller/clusterkey.go`, `internal/clusterkey`); a row that held another key loses its copy. The first member that starts and finds no Cluster key makes one, with its own copy, in one transaction, so members that start at once make one key. Every member that holds the key reads the store every 2 seconds and gives a copy to every row that has none, its own included; a member opens its copy with its Sealing key, and holds a key only while the store names it. A member waits up to 10 seconds at its start for its copy, so that it holds the key before it can lead. Then it seals the secrets that are in clear and logs `sealed the secrets of the targets that were in clear, with the Cluster key` with how many: the store of an earlier release holds them in clear, so the first start of a member of this release seals them. It does so again every minute, for a target in clear that a member of an earlier release puts during a rolling upgrade, or that a restored backup of one brings.
- **A member that holds no Cluster key keeps no secret.** It refuses a target with a secret, and the API answers with the error that says so; it opens no secret, so the targets are sent without their secrets until it holds the key; and its log says `this member does not hold the Cluster key yet`. A member of an earlier release during a rolling upgrade cannot open a sealed secret either, and its log says so: once a member of this release has started, the targets are sent without their secrets while a member of the earlier release leads.
- **A lost Cluster key.** A copy that its member's key does not open is removed, so that a member that holds the key gives another. When no row has held a copy for a minute, no member can get the key any more, since every member that holds it writes its own copy within 2 seconds: the member that sees it makes a new key in the place of the old one, which removes every copy of the old one, and logs `the Cluster key was lost`. The secrets that the old key sealed are lost, as on another host, and the targets are sent without them until each is put again. Every member must have lost its Sealing key at once for this: every host rebuilt, or every member run under another account, whose key set holds another key. The row of a member that left the cluster keeps its copy, and while it does the key is not taken for lost.
- **Restore.** The Cluster key is the cluster's, as the Sealing key is the host's: a restore keeps the rows of `cluster_key` and `cluster_key_copies` that the store held before (`store.Restore`). A backup of the same cluster opens as it was. A backup of another cluster, restored into this one or on a single Controller, brings its targets back with no secret, as on another host: the log names them, and the operator puts each one again. The text of `backup` and of `restore` says so.
- **The PresharedKeys of the WireGuard Devices, in the table `device_keys`.** The amendment of SDN-82 above seals the PresharedKey of a Device with the Sealer of the store, under the label `device_keys:NAME`, and its bullet **A cluster makes no PresharedKey** has a member of a cluster, whose store had no Sealer, refuse a Device with one. That bullet holds no more: the Keeper of the Cluster key is the Sealer of the store of a member, so the controller of a member seals and opens the PresharedKeys with the Cluster key as the store does the secrets of the targets, and makes a Device with a PresharedKey. The member that makes a Device seals its PresharedKey, the member that leads next opens it for the gateway of the Device alone, and the store, a backup and the log never hold it in clear. A member that holds no Cluster key refuses a Device with a PresharedKey, with the error that says so, and sends the Devices to their gateways without theirs, which its log says; the gateway gets its PresharedKey with the next whole state that a leader that holds the key sends it. A backup of another cluster brings its Devices back with a PresharedKey that does not open, as on another host, and a lost Cluster key loses the PresharedKeys with the secrets: each of those Devices is made again.
- **A writer of the store.** Whoever writes to the store can publish a key of its own in a row, which a member that holds the Cluster key then gives a copy to, or put a copy of a key of its own in the row of a member, which then seals the secrets that are put after with it: either way the writer gets secrets of the targets and PresharedKeys of the Devices. A writer of the store is more than that already: it is an admin of the Controller (a token of its own in `api_tokens`, ST-1), and it can point a target at a URL of its own (which gets the events and no secret since the amendment of 2026-10-30: the secret does not open for another URL). The store asks for the credential of `rqlited` on loopback and for a certificate of the cluster CA on the Raft port (AUD1-DT-8), so a writer is a member, an administrator of the host of a member, or a holder of the credential on such a host. The Cluster key keeps the secrets from a reader of the store, of its data, of a snapshot and of a backup (ST-4), as the Sealing key does, not from a writer: ST-12 of the threat model says so.
- **Not changed.** A single Controller seals with the Sealing key of its host. A single Controller that becomes a member of a cluster keeps the secrets and the PresharedKeys that the key of its host sealed, which the other members cannot open: the operator puts each target again, and makes each Device that has a PresharedKey again, once the cluster has formed. Rotation of the Cluster key, which needs a decision on who may start it and a new seal of every row, is a ticket of its own.
- **CI** proves it. `controller/internal/clusterkey` runs members on an rqlite cluster of three on one runner: members that start at once make one key and open what the others sealed, with no secret in clear in the rows of any rqlite member; a member that joins later opens what the cluster sealed before; a member without the key refuses a secret and says so; no row, no backup and no log holds the Cluster key or a private key; a restore into another cluster keeps the key of that cluster and loses the secrets of the backup; a lost key is made again; a copy that does not open is given again; the store names the key; and the fuzz targets `FuzzOpenCopy` and `FuzzDecodeCopy`. `controller/clusterkey_test.go` runs `sealTargets` of two members on the store of an earlier release, and the texts of `backup` and `restore`. `controller/cluster_sealed_test.go` runs the three `ranz controller` members of the cluster tests: a target put through each member holds no secret in clear in the store of any member, and the leader signs the webhook of the audit log with the secret before and after it is killed. `controller/internal/controller/devicekeys_cluster_test.go` runs the controller of a member on the conformance seam with the node simulator: a Device made through one member has its PresharedKey sealed with the Cluster key, which no Sealing key of a member opens; the controller of the other member opens it for the gateway after a change of leader; and a member without the key makes no Device with a PresharedKey and sends the Device without it until a member that holds the key gives it a copy. The tests of the store, the backup and the restore of `internal/clusterkey` hold a sealed PresharedKey too.

## Amendment 2026-10-30: what holds for a secret that the upgrade sealed, the URL of a target and the label (AUD1-DT-17)

Recorded by AUD1-DT-17 (#502), from the read-only review of AUD1-DT-10 (#458): the amendment of 2026-10-27 says that the table, the data of `rqlited`, a snapshot and a backup hold no secret of a target in clear, and that holds for a secret that is put after the upgrade, not for one that the earlier release kept in clear and the upgrade sealed. Decision 3 holds, and so do the Sealing key and the Cluster key. This amendment makes the claims true, or the text honest.

- **A secret that the upgrade sealed is in clear in some places for a while.** `SealTargetSecrets` seals such a secret by an UPDATE of its row: at the start of a single Controller, and in a cluster by the first member that holds the Cluster key. SQLite does not wipe the bytes of a row that it changes: the old text stays in the free space of the page, so the SQLite file of `rqlited` holds it, and a plain copy of that file, which is what `GET /db/backup` returns without `?vacuum`, carries it into a backup. rqlite also keeps what it was told in its Raft log until a snapshot truncates the log, which on a quiet Controller can be a long time, and in its snapshots until newer ones replace them. The test shows the file (`TestBackupOfAMigratedStoreHoldsNoSecretInClear`); the log and the snapshots are the design of rqlite, and no test reads them. A secret that is put after the upgrade has none of this: it is sealed before it is written, so no byte of its clear text is in the table, the file, the log, a snapshot or a backup.
- **The backup is vacuumed.** `store.Backup` asks rqlite for `GET /db/backup?vacuum`, which copies the database, vacuums the copy and returns it. The free space is not in it, so a backup holds the rows that the store holds now and none of the old text of a changed or deleted row. The backup does not vacuum the live file of `rqlited`. A backup that the earlier release made is what it was: it holds the secrets in clear.
- **The Controller cannot make the rest clean, so the operator rotates.** What `rqlited` keeps beside the table, its Raft log, its snapshots and the free space of its file, is rqlite's, on each of its members, and the Controller makes no call that removes one write from them. The note of the upgrade tells the operator to put each target that has a secret again with a **new** secret, and to change it at the receiver, so that what rqlite still holds is of no use. A cluster leaves the old text in the rqlite of every member.
- **The URL of a target stays in clear.** A webhook URL often carries its token in its path or its query, and the URL is in the table, in the data of `rqlited` and in every backup as it was put; the API shows of it the scheme, the host and the port only. Sealing it, with the secret or on its own, was weighed and not done. The Controller sends to a target whose secret is lost (another host, a lost key) with no secret, and needs the URL for that: a sealed URL would make every lost key a lost destination, so the target could not be sent to at all and the operator could not see where it points. The URL is no credential of the Controller either: `Validate` refuses a user name and a password in it and asks for the secret field. What follows is in the text of `backup` and in ST-4 of the threat model: a token in the URL is as safe as the backups, the data directory and the disk, and a token that the receiver takes in a header or a signature belongs in the secret.
- **The label of a sealed secret holds the URL.** The label that the box authenticates was `export_targets:<name>` or `audit_targets:<name>`. It is now that text, a colon and the SHA-256 of the URL of the target in hexadecimal (`targetLabel`, which has one length whatever a row holds, so that no name and URL make the label of another). Whoever can write a row of the store, or change a backup that an administrator restores, could point a target at a URL of its own, and the Controller then sent the unsealed secret there. A row whose URL was changed now has a secret that does not open: the target comes back with its new URL and with no secret, the log names it (`the secret of a target cannot be opened ... or the URL of the target was changed after the secret was sealed`), and the Controller sends to the new URL with none, a webhook unsigned and an OTLP request with no bearer token. A change of the URL through the API is a `PUT` that replaces the target, secret included, which seals it for the new URL, so an operator sees no difference. The form is still `ranz-sealed:1:`, since no release holds the label of before: a store that a build of `integration` sealed between the amendment of 2026-10-27 and this one holds secrets that no longer open, which the log names at the start, and each is put again. ST-12 of the threat model has the writer that can also publish a key of its own, which this does not change.
- **A restore under the running service.** `ranz controller restore` runs in a process of its own, and on Windows with the machine key set of the administrator and not the key set of the service account, so it cannot seal for the service the secrets of a backup that the earlier release made. The service seals them: a single Controller looks for secrets in clear every minute (`sealAgain` in `controller/sealing.go`), as a member of a cluster already does (`internal/clusterkey`), so the restore brings them back in clear and the service seals them within a minute with no restart. A Controller that is stopped seals them at its next start. The text of `restore` says so, and that the file of such a backup keeps them in clear.
- **A rollback to the earlier release** cannot open a sealed secret. It takes `ranz-sealed:1:` and the text after it for the secret itself, signs each webhook with that text as the HMAC key and calls an OTLP endpoint with it as the bearer token, and its API shows `hasSecret` true. The note of the upgrade says to put each target again through the earlier release, which keeps it in clear as before.
- **Two Controllers on one store.** A cluster is the Controllers that start with `-rqlite-join`, each with a rqlite member of its own, and they seal with the Cluster key. Two Controllers that use one store through `-rqlite-external`, or through an rqlite that another process runs, are two single Controllers as far as the sealing goes: each seals with the key of its own host and cannot open what the other sealed, and the log of each names the secrets that it cannot open, with the reasons. It is not detected as a cluster: `-rqlite-external` is no sign of a second Controller (a Controller on Linux uses the rqlite of another process without it), and nothing in the store tells a second Controller that runs from one that ran. Two Controllers on one store use `-rqlite-join`, and the text of the flag says so.
- **CI** proves it. `controller/internal/store/sealed_test.go`: `TestBackupOfAMigratedStoreHoldsNoSecretInClear` puts secrets with a store that has no Sealer, seals them with `SealTargetSecrets`, shows that a plain copy of the SQLite file holds the old text, and that the backup holds none of it, holds each secret sealed, and holds the URL of each target with the token of its path and its query in clear; `TestSealedSecretStaysWithItsURL` changes the URL of a row with SQL and finds the target with its new URL and no secret, the store naming it, the secret open again with the old URL back, and a target that is put again sealed for its new URL. `controller/internal/controller/sealed_test.go`: `TestChangedURLOfATargetSendsNoSecret` has a webhook signed and an OTLP endpoint called with its token, then points both rows at the URLs of a writer and starts the Controller again, and the new URLs get an unsigned webhook and an OTLP request with no bearer token and nothing that holds a secret, opened or sealed. `controller/sealing_test.go`: `TestRestoreOfAnEarlierBackupIsSealedWithoutARestart` restores a backup that holds secrets in clear under a Controller that runs, and finds them sealed with no restart; `TestTwoControllersOnOneStoreCannotOpenEachOther` shows what two Controllers on one store do. `controller/backup_sealed_test.go`: the text of `backup` and of `restore`.
