# ADR-0010: Routing is the OS's job; overlay routes from the control plane, BGP at the edge via a GoBGP sidecar, no OSPF

**Status:** Accepted (2026-10-13; amended 2026-10-20: EVPN type-5 through `ranz-bgp`, VXLAN in the node, SDN spec #176; amended 2026-10-21: per-VRF forwarding inside the overlay, Windows IP forwarding only at a gateway's LAN edge, the `Gateway` resource is the approval). Hilmi accepted Windows IP forwarding in place of the Layer 3 switch ("accepted"), chose the GoBGP sidecar and control-plane overlay routes, wants both overlay routing and peering with customer routers, agreed that OSPF is not implemented, and asked to record it ("catat"). Originally Proposed as the assistant's answer to "static routing ganti ke BGP".

## Context

SoftEther offered an L3 switch (`Layer3.c`, static routes between hubs); it is removed by the scope cuts (spec #26, PR #25). Hilmi asked for routing between hubs and VLANs, dynamic routing, and his own OSPF/BGP, under the rule "jangan reinvent the wheel". Writing BGP or OSPF inside the daemon would be roughly ten to fifteen thousand lines each of network-facing parsers, months of work and interoperability testing; OSPF has no maintained implementation on Windows (Microsoft removed it from RRAS, BIRD and FRRouting are Linux/BSD only).

OSPF and BGP do different jobs: OSPF routes inside one organisation's network (every router knows the full topology); BGP routes between networks with explicit peers and rich filtering. Ranz's overlay is "another network" from a customer router's point of view, which is BGP's job; cloud VPN gateways (AWS, Azure, GCP) peer with customer routers over BGP for the same reason.

## Decision

1. **Routing between networks and VLANs is done by the Windows IP stack** on a gateway node. Each routed network (the successor of a Virtual Hub) or VLAN gets one Microsoft KM-TEST loopback adapter attached as an access port (ADR-0018, ADR-0019) and carries the gateway address of its subnet; IP forwarding is enabled on those adapters and the kernel routes between them. WinNAT (`New-NetNat`) provides NAT to the internet where needed. *(Replaced by the three egress tiers, amendment of 2026-10-20 below.)* Filtering between networks uses the Ranz policy engine at the gateway's ports (ADR-0019) and WFP rules at the forwarding layer. In the current SoftEther-based code the same setup works manually today: a Local Bridge from each hub to its own loopback adapter, plus `Set-NetIPInterface -Forwarding Enabled` or RRAS LAN routing. *(Amended 2026-10-21 below: inside the overlay, forwarding uses the node's per-VRF tables; Windows IP forwarding is used only at a gateway's LAN edge.)*
2. **Overlay routing is automatic, from the control plane** (ADR-0011): gateways advertise the subnets behind them; an administrator approves advertised subnets *(amended 2026-10-21 below: declaring the LAN prefixes in the `Gateway` resource is the approval)*; the control plane distributes routes to every node, health-checks gateways, fails over, and spreads load over several gateways (ECMP). Static routes exist only as administrator overrides distributed by the same mechanism. The daemon installs routes into Windows through IP Helper. No routing protocol runs between Ranz nodes. *(Amended 2026-10-29 below: the Nodes of a VRF of the standard mode whose peering is `bgp` exchange their LAN subnets and addresses by BGP, SDN-77.)*
3. **Edge routing with customer routers uses BGP through a GoBGP sidecar** (Apache-2.0, a separate process controlled by the daemon; see the 2026-10-13 amendment for the transport, which is a local named pipe with JSON, not gRPC). It announces overlay subnets to the customer's routers and learns theirs, with filters on both sides. GoBGP's route installation is Linux-only, so the daemon installs learned routes into Windows through IP Helper. RRAS BGP is not used.
4. **OSPF is not implemented.** Customers who run OSPF internally redistribute the BGP-learned Ranz routes into OSPF on their own routers (MikroTik, Cisco, Juniper and pfSense/FRR all can). Routers that speak neither protocol use static routes.
5. **Router-on-a-stick stays possible**: a VLAN trunk over Local Bridge to a physical NIC lets a customer's router route between Ranz networks.
6. L2 switched networks (ADR-0014) are subnets like any other from the router's point of view. EVPN remains the matching model if L2 segments are ever stretched between sites with BGP-speaking routers; noted, not decided. *(EVPN type-5 for IP prefixes per VRF is decided in the amendment of 2026-10-20 below; L2 stretch stays after v1.)* *(Amended 2026-10-22 below: L2 stretch over EVPN is in scope.)*

## Consequences

- `Layer3.c` is gone (PR #25) and is not carried into the new core; kernel IP forwarding replaces it and is faster than routing in user mode. *(Inside the overlay, the node's per-VRF tables replace it; amendment of 2026-10-21 below.)*
- The number of loopback adapters on a gateway grows with the number of routed networks and VLANs; the bridge path to those adapters (SeLow today, XDP later) is the throughput limit, not the routing. *(Superseded for the overlay by the amendment of 2026-10-21 below.)*
- The control plane needs route advertisement, approval, health checks and ECMP; its design still needs its own ADR. *(Covered since 2026-10-20 by ADR-0025 to ADR-0027, except the approval step for advertised subnets, which #176 does not mention; since 2026-10-21 the `Gateway` resource is the approval, amendment below.)*
- The GoBGP sidecar adds a Go binary to gateway installations that peer with routers; nodes that do not peer never run it.

## Amendment 2026-10-13: GoBGP sidecar shape, RRAS BGP ruled out

The 2026-10-13 grilling fixed the sidecar and reaffirmed the routing decision (full detail in ADR-0022):

- **RRAS BGP is ruled out**, here and in ADR-0014 (which previously read "RRAS or GoBGP"). The GoBGP sidecar is the only edge-BGP path.
- The sidecar is a small Go program, **`ranz-bgp`, that embeds GoBGP as a library**. The C core talks to it over a **local named pipe with a few JSON messages** (announce, withdraw, learned routes) — **not gRPC**, correcting decision 3's "over its gRPC API". The core installs learned routes into Windows through IP Helper.
- Packaging: an **optional MSI feature**, built in CI (Go cross-compiled for x64 and arm64), spiked on Windows (BGP on TCP 179, no FIB) when L3 networks land at **strangler step 7** (ADR-0022).
- Overlay routing between Ranz nodes still uses the control plane (decision 2), not BGP; the `controller` role and its nanopb control stream are specified in ADR-0022. *(Since the amendment of 2026-10-20 below, the control plane is the separate `ranz-controller` service, ADR-0026.)* *(Except in a VRF of the standard mode whose peering is `bgp`: amendment of 2026-10-29 below.)*

## Amendment 2026-10-20: EVPN type-5 through `ranz-bgp`, VXLAN in the node

Maintainer decision, from the SDN spec #176 that Hilmi filed ("EVPN type-5 through `ranz-bgp`, VXLAN in the node"). The full edge design is ADR-0032; the VRFs it hands off are ADR-0025.

- **`ranz-bgp` gains EVPN type-5** (IP prefix routes per VRF). GoBGP stays a library inside it, and its named-pipe JSON contract with the node is extended for EVPN routes per VRF. RRAS BGP stays ruled out, and OSPF stays out (decision 4).
- **The gateway node does VXLAN encapsulation and decapsulation in user space**, because Windows has no VXLAN interface for applications. The same module carries Mirrors to a sensor (ADR-0029).
- **Overlap-safe handoff is EVPN only.** Overlapping prefixes never reach the single Windows routing table. VRF-lite (one VLAN per VRF) carries non-overlapping prefixes only: on Windows Server through LBFO team interfaces, on client SKUs one VRF per physical NIC.
- **Decision 6 is settled for L3:** EVPN is decided for IP prefixes per VRF (type-5). EVPN type-2 and L2 stretch over EVPN are after v1. *(Superseded by the amendment of 2026-10-22 below.)*
- **Decision 2 is now the controller's job:** route advertisement of LAN subnets behind gateways, health checks, gateway HA and optional ECMP are compiled by `ranz-controller` (ADR-0026) and delivered by Generation (ADR-0027). #176 does not mention the approval step for advertised subnets; LAN prefixes are part of the `Gateway` resource in the intent (ADR-0031). *(The approval is settled by the amendment of 2026-10-21 below.)*
- **Decision 1:** forwarding inside a VRF uses the node's per-VRF tables (ADR-0025). Its WinNAT sentence is replaced by the three egress tiers of the ADR-0008 amendment of 2026-10-20.

## Amendment 2026-10-21: per-VRF forwarding inside the overlay, the `Gateway` resource is the approval

Maintainer decisions (Hilmi: "ya ya ya semua").
- **Decision 1: inside the overlay, forwarding uses the node's per-VRF tables** (ADR-0025). Windows IP forwarding is used only at a gateway's LAN edge, through the VRF's adapter. Routing between the overlay's networks and VLANs no longer runs through loopback adapters and the Windows IP stack.
- **Decision 2: declaring LAN prefixes in the `Gateway` resource is the approval** (ADR-0031). Intent always goes through revisions, `ranz diff` and `ranz apply --confirm`, so a prefix is reviewed before it applies and can be rolled back. There is no separate approval step for advertised subnets.

## Amendment 2026-10-22: EVPN type-1 to 4 and L2 stretch are in scope

Maintainer decision (Hilmi, after a grilling round; the full design is the amendment of the same date in ADR-0032).
- **Decision 6 is settled for L2 as well:** EVPN type-1, 2, 3 and 4 join type-5, so an L2 Network can be stretched to a fabric and two gateways can share an Ethernet segment. This replaces "L2 stretch stays after v1" in decision 6 and "EVPN type-2 and L2 stretch over EVPN are after v1" in the amendment of 2026-10-20.
- **`ranz-bgp`** carries all five route types over the same named pipe, in batches with a full resync after a reconnect. GoBGP stays a library inside it.
- A Network with a stretch must not also have a `bridge` role node (router-on-a-stick, decision 5, stays possible on other Networks).

## Amendment 2026-10-23: `ranz-bgp` is the subcommand `ranz bgp` (ONE-1)

Recorded by ONE-1 (#310), from the ADR-0011 amendment of 2026-10-22 (the product ships as one `ranz.exe`).

- **The sidecar is no executable of its own.** It is the subcommand `ranz bgp` of the one Go executable `ranz`. The node starts it as `ranz.exe bgp -pipe NAME -log FILE` from the folder of its own executable when its configuration names BGP peers, as it started the separate file before. The named pipe, its strict DACL, the JSON messages, the filters and the sidecar's own log (`ranz-bgp.log` in the node log directory) are unchanged, and so are the packages `ranz-bgp` and `ranz-bgp/internal/sidecar`. The ready message names `ranz bgp` and its GoBGP; `ranz version` prints the one version of the executable.
- **The optional MSI feature of the amendment of 2026-10-13 is replaced by the executable.** GoBGP's Apache-2.0 licence text, which section 4 of that licence asks to ship with the binary, is inside `ranz.exe`: `ranz notice` prints the NOTICE file that holds it, and a test compares it with the licence of the GoBGP that `go.mod` pins. The other components that ONE-3 (#312) and ONE-4 (#313) add to the file go into the same NOTICE.
- **The node's test proves it:** `vpntest bgp` starts a node with BGP peers and reads the command line of the sidecar from the sidecar's own log, which must be `ranz.exe bgp -pipe`.

## Amendment 2026-10-29: BGP between the Nodes of a VRF of the standard mode (SDN-77)

Recorded by SDN-77 (#357), from the breakdown of the SDN spec #176 that the maintainer approved on 2026-10-24. The standard mode is plain by his decision of that day, for a network that the operator trusts (SDN-76, #356; section 12 of `docs/threat-model.md`), and in it two Ranz Nodes may exchange IP prefixes by BGP, as routers do. This changes decision 2 ("No routing protocol runs between Ranz nodes") and the amendment of 2026-10-13 for those VRFs alone: every other VRF keeps the routes of the control plane, and decisions 3 and 4 hold.

- **The Intent.** A VRF whose link is of kind `vxlan` or `geneve` may set `peering`, for example `{"protocol": "bgp", "holdTime": 9}`: its Nodes then peer by BGP in a full mesh. Its LAN subnets go by BGP only, so the Controller gives none of them as a route of a peer; the routes of 1:1 NAT rules and of leaks stay the Controller's. An intent is refused, naming the VRF or the Node, that sets the peering on a link of kind `noise` or on a VRF of topology hub-and-spoke (a Node passes on nothing that it learned, so a spoke would learn no route of another; the route reflector of SDN-79 is that form), a hold time outside 3 to 65535 seconds (90 when left out), tunnel endpoints of two families in one such VRF, two Nodes with one router id, `ecmp` on such a VRF, or a Node that more than 16 routes lead to at one of its peers. A Node takes one best path for each prefix from BGP, so the flows to a LAN subnet of several gateways would never spread over them: the groups of gateways of the Controller (SDN-19) do not apply in such a VRF, and two gateways that advertise one LAN subnet there are a group for BGP alone. The 16 routes are those that the Controller gives for a peer and the LAN subnets that the Node learns from it by BGP, which take the same slots (SDN-77-R2, #532).
- **One AS, internal BGP.** Every Node is in AS 4200000000, a private AS of four bytes (RFC 6996). The router id of a Node is the IPv4 address of its tunnel endpoint, or the first 4 bytes of the SHA-256 of an IPv6 one.
- **The Controller writes the settings of the sidecars and nothing else**, so it is not in the path of the routes: in the NodeConfig of a Node its AS, router id and address (the one of its tunnel endpoint) and the LAN subnets that it announces (`NodeConfig.peering`); in the Peer object of each Node that shares such a VRF with it the address of that Node's sidecar, the hold time of their session (the shortest of the VRFs that they share, where a VRF that names none counts as 90 s), the VRFs of the session and the accept list: what that Node may announce there, its addresses as host routes and its LAN subnets (`Peer.peering`). No LAN subnet may be the default route, so no Node may announce one.
- **A sidecar of its own.** A Node runs a second `ranz bgp` for the peering (`NodePeering.c`) beside the one toward the routers of the operator (decision 3, `NodeBgp.c`), on a pipe of its own with the same strict DACL and with its log `ranz-bgp-peering.log`. The sidecar listens on TCP 179 of the address of the tunnel endpoint only and connects from there; of two Nodes, the one of the lower address connects. GoBGP refuses a session from an address that no Peer object names, and the sidecar reports each such session to the Node, which counts it. Version 2 of the pipe protocol adds the address of the start message, the hold time and the VRFs of a peer, the `peers` message, the VRF of a route and the `refused` message.
- **VPN routes.** A route is a VPN route (RFC 4364) whose route distinguisher and route target hold the VRF id, so the routes of two VRFs stay apart over the one session of two Nodes, even for one prefix. The sidecar reports a learned route only when its peer may announce it in that VRF: inside a prefix of its accept list.
- **The Node installs what it learns** as a route of the peer of the best path (`CONTROL_PEER.Routes`): the forwarding table of the VRF leads the prefix to that peer, and the VRF adapter of the host puts it into the Windows routing table through IP Helper, as it does the routes of the Controller. GoBGP installs nothing (decision 3). The tables take 16 routes of a peer at most, its other routes included, and a Node holds 4096 learned routes at most. When the learned routes change, the Node builds the tables of the Generation in force anew. The routes of a peer go when its session ends, because the hold time ran out or the peer sent a Cease as it stopped, and a sidecar that ends by itself starts again 5 s later, without them.
- **The report.** The Node reports the peers of its sidecar, the state of each session, the prefixes learned from each and the sessions refused, in a Telemetry message of its own whenever they change (`Telemetry.peering`). The Controller keeps the last report of each Node in memory, and `GET /api/v1/peering/{node}` (viewer) and `ranz explain NODE` show it with the Nodes that the intent names as its peers; `ranz explain` stays a client of the public API (ADR-0031 decision 10).
- **Licence.** BGP between Nodes is part of the Enterprise feature EVPN and BGP (ADR-0032 decision 7, ADR-0036), which the licence check asks for before the intent applies.
- **Capability.** A Node reports the Capability `bgpPeering` when its release has the peering and `ranz.exe`, which holds the sidecar, is next to it (ADR-0033 amendment of 2026-10-30, SDN-77-R2, #532). The Controller refuses an intent that makes a Node that does not report it a member of such a VRF, naming the Node, the VRF and the Capability, and refuses the stream of such a Node. Without it a Node of an earlier release, which passes the check of `plainLinks`, would ignore the settings of the sidecar and lose every LAN route of the VRF, which the Controller no longer gives it, and its own LAN subnets would be gone from every other Node, with no error.
- **Not here.** Protection of the sessions (TCP-AO or MD5, a TTL check): they are plain on the network that the operator trusts, which provides it (section 12 of the threat model). A maximum of prefixes for each peer beyond the limits of the tables. EVPN between Nodes (SDN-78, #358) and the route reflector (SDN-79, #359).
- **Tests.** `vpntest peering` runs three Nodes, each with its own sidecar on 127.0.0.2, 127.0.0.3 or 127.0.0.4, in a full mesh of two VRFs, in the build jobs of windows.yml on x64 and arm64 (`.github/scripts/bgp-peering.ps1`). Its data links are of kind `noise`: on one host the VXLAN module of each Node would send from one address, and a plain link names its peer by the source address. The Go tests cover the sidecar (`TestPeering`), the compile and the licence, the report and `ranz explain NODE`.
