# The formal model of the session handshake

AUD-5 (#389), and AUD-6 (#409), which made the models follow the code as the second review of AUD-5 read it, and AUD-7 (#425), which added the mimic path. The design of the handshakes of Ranz VPN is proved, not only tested: ProVerif checks models of the session of a client with a Login over TLS 1.3, over QUIC and over the REALITY session of the mimicry sidecar, of the overlay sessions between nodes, of the control stream of a node to the controller, of the join of a further connection to a tunnel, of Noise_IK alone and of the peer layer, and a CI job fails when a query that must hold does not hold, or an attack that must show does not. The models follow the code as it is today, and where the code differs from ADR-0022 and ADR-0023 this page says how (D1 to D9). Every query of every model gets an answer from the prover: none is left to Tamarin.

## The model

The attacker is the network (the Dolev-Yao attacker of ProVerif): it reads, drops, rewrites and sends every message, runs as many sessions as it likes, and may hold a key or a password that its scenario gives it.

**The outer session.** A TLS 1.3 handshake of one round trip with the authentication of the server only: the client sends a random value and a key share, the server its random value, its key share, its certificate and a signature of the transcript. The keys of the records and the exporter come from the Diffie-Hellman secret and the transcript, so two sessions that differ in any value of the transcript have different keys and different exporters, as the key schedule of RFC 8446 gives. The client does not check the chain: it compares the certificate with its pin (`TlsCheckPin`, `QuicConnCallback`, or on the control stream the check of the TLS fingerprint, `NodeControllerVerify`), which a variant can leave out. A middlebox is the attacker with a certificate of its own that terminates the session of the client and opens one to the server.

**The Noise handshake.** On the first stream the client runs Noise_IK with the static key of the node identity and the static key of the server that it expects, with the prologue that holds the binding. Each side decides from its own transport whether its session is bound or encrypted (`TransportNoiseStart`): a transport that gives a binding makes it bound, one that gives none makes it encrypted, and the two sides do not agree on it first. The binding is the TLS exporter (`NOISE_BINDING_EXPORTER`): `TlsExporter` on the TLS-443 path, and on the QUIC path since CORE-H5 (#408) the exporter of the QUIC connection, which msquic 2.6 gives (`TransportQuicExporter`). The QUIC path of the build before CORE-H5 bound the tls-server-end-point of RFC 5929 (`NOISE_BINDING_SERVER_END_POINT`), which the negative control `endpoint-cert` keeps. A QUIC client that got no certificate has none, runs an encrypted session with the prologue of no binding, and its handshake with a bound server fails because the prologues differ (`quic-nocert-none`). The handshake payloads are empty and the records after it go in clear inside the outer session, which encrypts them once (ADR-0023, single encryption). A record of a session is its type byte, then on the handshake records the suite byte, then the body. The responder runs the suite of the first record if it can (`NoiseSuiteAvailable`), as one process for each suite in the models.

**The responder takes the static key of any initiator.** `NoiseSessionAccept` completes the handshake with whatever static key message 1 carries, and what that key is worth is decided after the handshake, by the caller, in one of four ways:

- **A session with a Login** (`NodeAcceptSession`): the first record must be a control record that parses as a Login (a data record before the Login is refused, the Login gate of `NoiseSessionReceive`). For a password Login, Sam checks the password of the user (`NodeLogin`), then `NodeLoginPinned` compares the static key with the key pinned to that user. The first Login of a user pins the key that it comes with (trust on first use, `CsPinUserKey`), a user that the configuration store does not keep (a domain account) is not pinned, and an anonymous Login has no password and no pin. The model has the password Login, with the key pinned (`kp_on`) or with no key compared (`kp_none`: the first Login, D8). The Login has one version, which the parser takes exactly, so it negotiates nothing; what a session negotiates is its suite.
- **A join Login** names a hub and the id of a Tunnel; the key is compared with the key of the Tunnel (`NoiseTunnelJoin`), and `NodeLoginPinned` is not run (`tunnel-*`).
- **The control stream**: the controller looks the key up among its Node resources (`byKey`) and takes the stream as that node's, with no password (`control-*`).
- **An overlay session**: the overlay keeps the session only for a peer of its desired state with that key, and replaces the session that the peer had (`NodeOverlayAccept`); there is no Login (`overlay-*`).

**The control stream** is not a session of `NoiseSession.c`. Its frames are a 4-byte length and a message, with no record type byte and no suite byte: the two handshake messages, then one protobuf `ControlMessage` per frame. The suite is Noise_IK only, and the prologue is the label and the exporter, with no binding type byte. The node sends its Hello (the schema version and the Capabilities), then Acks and the leases of its DHCP responders, and the controller sends the Updates. The C node asks its transport for the exporter of `CONTROL_EXPORTER_LABEL` (`NodeControllerTls` sets it, SDN-90); `ControlRun` itself takes any binding of the exporter type and 32 bytes.

**The two keys of a node.** A server node has its Noise identity key and the key of its TLS certificate, and a compromise of one does not give the other (ADR-0023, key separation).

**The scenarios.** A model is the session with the compromises of one scenario and no others, and none of its queries is conditional on a leak: it holds in the scenario or it does not. The scenarios are `none` (the attacker is the network), `cert` (it holds the key of the certificate of the server: the middlebox that can present the pinned certificate), `client` (the Noise key of the client), `cert-client` (both), `noise-client` (the Noise keys of the server and of the client), `both` (both keys of the server), `noise` (the Noise key of the server), `pw` (the password of the user of the client) and `fs` (every key, after the sessions, in phase 1 of ProVerif, which is what forward secrecy asks). A leak is an event, so the trace of an attack shows it.

**The tunnel join** (`tunnel-*`). A tunnel of several connections (ADR-0022, amendment of 2026-10-15): the first connection of a peer node logs in and makes the Tunnel of an id, which is the HMAC-SHA256 of a label under its handshake hash (`NoiseTunnelId`, which the client and the server both compute); each further connection runs a handshake of its own in an outer session of its own and sends a join Login that names the hub and the id (`NOISE_LOGIN_JOIN`). The hub name selects the Sessions of that Hub whose connection carries a Tunnel (`NodeJoinTunnel`), the user name is never read, and the connection joins the Tunnel of the id when its static key is the one of the Tunnel (`TunnelJoin`, `NoiseTunnelJoin`). A join is also refused when the Tunnel is halting, when no index of it is free and when the same session joins twice, and the server sends no answer to a join either way; those refusals keep the bookkeeping of the Tunnel and are not in the model. The model has the first connection as the Tunnel that it makes, with a new id for the static key of its peer, which the attacker is given, since the id is no secret inside the outer session and nothing rests on it; and it has the join in full: the outer session with the pin, the binding, the handshake and the join Login. `charlie`, whose keys the attacker holds, has a Tunnel of his own and dials with the ids of the others. The client of a join is `NoiseHubConnect` of vpntest.

**The mimic path** (`mimic-*`). The third outer session: the mimicry sidecar `ranz mimic` makes it, and the node speaks to its sidecar over named pipes (CORE-P2-6, #406). The server sidecar is a REALITY server with a key of its own (the REALITY private key, X25519, which is neither the Noise key nor the key of a certificate), a list of short ids and a decoy; the client sidecar dials a link of its settings, which names the address, the public key of the server and a short id. The client sends the ClientHello of a browser whose session id is the proof: the version of the client and the short id (and its clock, which the model leaves out), sealed with AES-GCM under the auth key, the HKDF of the X25519 secret of the key share of the ClientHello and the public key of the server (`authenticate`). The server opens the proof with its private key and takes it when the short id is one of its own; then it answers as a TLS 1.3 server with a temporary certificate, a fresh Ed25519 key whose signature is the HMAC-SHA512 of that key under the auth key, which the client checks and nothing else (`temporaryCertificate`), inside the handshake keys of the session. A ClientHello whose proof does not open, or whose short id is not one of the server's, is spliced to the decoy, a real site that answers with its own certificate and its page: that is the prober, and also a client with a wrong short id, which sees a certificate that is no temporary certificate and gives up (`errNotAuthenticated`) before its node sends a byte. The record keys and the exporter come from the key shares and the transcript, as on the other paths. The sidecar writes the binding, the exporter of `BindingLabel` (the label of the session module), as the first line of the stream on the data pipe (`bind <binding>` on the server role, `ok <binding>` after the `dial <address>` of the node on the client role), and the node takes it from the line (`NodeMimicParseBind`, `NodeMimicParseAnswer`, `NodeMimicBinding`) into the prologue of the Noise handshake, which runs as on the other paths, with the Login. The pipes are open to the account of the node alone, and the node takes only the process that it started as the other end of each pipe (`GetNamedPipeClientProcessId`, `GetNamedPipeServerProcessId`), so the model has the sidecar and its node as one process, the settings of the start message (the private key and the short ids of a server, `NodeMimicStartMessage`) as a value that the process takes, and the first line of a stream as a value that it passes; the pump of the sidecar, which copies the stream between the pipe and the TLS session and looks into neither, is the node sealing its records under the keys of the TLS session. A sidecar that ends by itself is started again with the same settings (`NodeMimicSupervisor`), and every connection of the model is one run of a sidecar. The public key of the server is always the attacker's: a link holds it and it is no secret.

**Noise_IK alone** (`noise-encrypted`). A session that nothing binds encrypts its records under the Noise keys (`NOISE_SESSION_ENCRYPT`). That is where the session keys of Noise, their secrecy and their forward secrecy, are graded: the authentication and confidentiality grades of the Noise Explorer for the four messages of IK. The handshake payloads are empty in the code (the Login follows in the first control record, "under the forward secrecy of the complete handshake"), and the grades show why: message a has no forward secrecy, message c has all of it. The responder of this model serves one expected initiator, as the Noise Explorer grades IK; the code takes any key, which the session models have.

**The peer layer** (`peer-leaks`, `peer-honest`). The envelopes of binds, signals, punch messages, bounds and bind challenges, sealed with the one-way pattern K, and the data datagrams in a peer session, as the code has them (CORE-H2, #399). A relay binds a node at the address of its bind only with the cookie of that address, which it sent there in a challenge sealed to the node (`PeerInputBind`, `PeerChallengeSend`); the node answers a challenge of its relay to its last bind with a bind that holds the cookie (`PeerInputChallenge`). A punch probe sets no path: the end with the lower static key sends a nonce sealed to the peer to the address of a probe, the other end echoes it from there with a nonce of its own, which a proof echoes back, and each end moves the peer to the direct path at the address that its nonce went to (`PeerPunchInput`, with `Config.Punch`, which the peer agent of a Node sets where ICE runs since CORE-S5-7, #413). An end sends one nonce to an address until its echo comes, however many messages of the peer come from there (`PeerPunchNonce`, CORE-H2-R1 #436), as one challenge of the model that the attacker sends again. A node takes a bound only from a configured relay at the address of that relay, as the answer to its last bind (`PeerInputBound`). A signal names a relay, which the node takes only when the control plane assigned it at that address (`PEER_DROP_RELAY`); the content of a signal is one secret value in the model, so that check has no answer of its own. A data datagram is a record of a peer session: Noise_IK between the static keys of the two nodes, with the prologue `ranz peer session 1`, and records under the keys of its Split, with the clear header as their associated data (`PeerSession.c`); the model's clear header is the kind, the source key and the destination key, where the code's also holds the index of the keys and the counter of the record (the gaps of the peer session, below). The relay forwards a datagram of a session as it came, by its clear header, from a node bound to it to another node bound to it, inside a VRF of both and under a rate limit; the attacker of the model sends any datagram from any address, which is all that the forwarding would give it, so the model has no forwarding process. The ICE path delivers a datagram only with the peer of the ICE session as its source (`PeerSourcePath`), and its connectivity checks are those of libjuice, which the model does not have.

### How the models are written for the prover

The models are written so that ProVerif answers in seconds. Three choices do it, and a model that leaves them breaks the prover: the first runs of the models, with the habits of the Noise Explorer, ran for twenty minutes and at 15 GB without an answer.

- **Diffie-Hellman has no equation.** The Noise Explorer gives it the equation dh(a, pk(b)) = dh(b, pk(a)), and ProVerif then tries both orders of every Diffie-Hellman term of every clause. Every Diffie-Hellman of these handshakes is between a key of the side that dials and a key of the side that listens (es, ss, ee and se of IK, es and ss of K, the key shares of the outer session), so the model gives the initiator's computation as the term `dhi(a, B)` and rewrites the responder's `dhr(b, pk(a))` to the same term. The two sides agree, and an attacker still computes the secret when it has a scalar and the public key of the other side. What the encoding leaves out is a public key that is no `pk` of any scalar (a point of low order), which the code refuses (`NoiseMixDh`) and the responder's computation fails on.
- **A process creates its names before its first input.** ProVerif gives a name that is created after an input the received values as arguments: the ephemeral key of the responder was `e[cs, cp, E, sid]`, and every term that held it held both ciphertexts of the first message, a few hundred nodes each, over and over in the key schedule.
- **The pin, the binding, the key check and the suite are the choice of a rewrite rule or of the process that runs**, not boolean terms, and a model is one scenario with the queries that the scenario is about: the models that leaked three keys at once and asked "unless this key" never finished.

Where the attacker holds the Noise key of the server, the queries of the client (`auth-client`, `data-auth`) and of replay are left out of the model: the attacker is the server there, and ProVerif would have to prove a long list of attacks false one by one for no gain.

Since the responder takes the key of any initiator, the first derivations that ProVerif finds for some attacks of `endpoint-cert` (before CORE-H5, `quic-cert`), `nobinding-cert` and `neither-none` rest on an approximation of the actions of a process, and it cannot rebuild their traces ("cannot be proved" where the attack is real). Those three variants take `precise.pvl` first, which sets `preciseActions`: the prover then finds and rebuilds the real attacks, in under a minute each.

Where the attacker holds the REALITY private key of the server (`mimic-key`, `mimic-nobinding-key`), it makes the key share of every ClientHello that it sends, and ProVerif 2.05 selected `attacker(tpk(a))` in a loop and did not finish in 900 s. The two variants declare `noselect a: bitstring; attacker(tpk(a)).`, the declaration that the prover suggests. It changes only the order in which the prover resolves its rules, not what it proves, and the two variants then answer in about one and about six minutes.

### The queries of the session, control and overlay models

| id | says |
|---|---|
| `reach-took`, `reach-done` | the server can take a session as alice's and the handshake of alice can complete, so no query that holds is true for want of a run; in `quic-nocert-none` they hold, which says that the handshake cannot complete |
| `sec-pw` | the password that the client sends in its Login is secret (the session with a Login only) |
| `sec-data` | what the server sends in a session of alice (a data record, or the Update of the controller) is secret |
| `fs-pw`, `fs-data` | the same after every long-term key leaked: forward secrecy |
| `auth-server` | the server takes a handshake with the static key of alice only if alice started it, in the TLS session that the server is in (the transcript of the TLS session is its identity): the binding of a handshake to its session |
| `took-auth` | the server takes a session as alice's (her Login, her Hello, or her session as a peer) only if alice started it, in that TLS session |
| `cdata-auth` | what the server takes as the data of alice's session (a data record, a lease of the control stream) is what alice sent in that session |
| `auth-client` | the client takes the answer only if the server with the key that it expects made it, to her key, in her TLS session and with the same handshake hash |
| `data-auth` | what the client takes from the server after the handshake (a data record, or the Update of the controller) is what the server sent in that session |
| `negotiation` | the schema version and the Capabilities of the Hello that the controller takes for alice are ones that alice offered (the control stream only) |
| `suite` | the suite that the server runs with the key of alice is one that she chose: the suite is in the protocol name that the hash of the handshake holds (the sessions only: the control stream has no suite byte) |
| `replay-server`, `replay-client` | no replay: each handshake with the key of alice that the server takes, and each answer that the client takes, is one that was sent once |

The queries of the tunnel models (`tunnel-queries.pvl`):

| id | says |
|---|---|
| `reach-join` | a connection of alice can join, so no query is true for want of a run |
| `join-auth` | a connection with the key of alice that joins a Tunnel is one that alice made, in the outer session that the server is in: a middlebox that terminates the outer session of the join and opens one to the server is the case that the binding rules out |
| `join-identity` | a connection joins only a Tunnel that was made for its own static key, whatever ids it knows: the ids of all Tunnels are the attacker's |
| `join-replay` | no replay: each join that the server takes is of a Login that was sent once |

The mimic models ask the queries of the session models, and these of the outer session (`mimic-queries.pvl`):

| id | says |
|---|---|
| `mimic-auth` | the client sidecar takes a temporary certificate, and hands its node the stream, only in a REALITY session that the server sidecar answered: what a middlebox needs to terminate the outer session |
| `probe` | the server takes a proof, and so answers with the temporary certificate where it would splice to the decoy, only for a ClientHello that the client sidecar of alice made with that short id: what a prober can learn of the server |
| `probe-decoy` | a connection that does not prove the key is spliced to the decoy, so the queries about the prober are not true for want of a splice |
| `sec-shortid` | the short id of the link stays secret |
| `wrong-sid` | a client whose link names a short id that the server does not have never takes a certificate: it sees the decoy, and its node sends nothing |

The queries of `noise-encrypted` are the grades of the Noise Explorer for the messages a, b, c and d (`a-auth1` to `d-conf5`), and the ones of the peer layer are in `peer-queries.pvl` (`pe-*` the envelopes and `pe-cookie` the binding, `pp-*` the punch, `pb-auth` the bound, `pd-*` the data datagrams, and `reach-data`, `reach-bound` and `reach-direct`, which show that a record is delivered, a node bound and a direct path set at all).

### What holds

Every answer below is the one that ProVerif gives in the job of the variant, and `expected.tsv` is checked against it.

**The session with a Login over TLS-443, as the code has it.** Against an attacker that is the network (`tls443-none`) every query holds. Against the middlebox that holds the key of the certificate of the server (`tls443-cert`) every query holds too: it presents the pinned certificate and terminates the TLS session of the client, and the handshake that it relays to the server is in the prologue of another exporter, so the handshake does not complete, and it reads and rewrites nothing. The suite cannot be lowered. With the key of the certificate and the Noise key of the client (`tls443-cert-client`) the password, the data, the answer of the server and the Login are still safe, and the attacker can start handshakes as the client: `auth-server`, `suite` and `replay-server` fail, since the first message of Noise_IK is open to the compromise of the key of its initiator, and `took-auth` holds, because the Login needs the password. With the Noise keys of the server and of the client (`tls443-noise-client`) the password and the data are safe, because the pin keeps the holder of the keys from answering the client in a TLS session of its own. With both keys of the server (`tls443-both`) the attacker is the server and every query fails: each key guards the other. With every key leaked after the sessions (`tls443-fs`) the password and the data are still secret: forward secrecy. With the password of alice (`tls443-pw`) every query holds while her key is pinned: the pin of `NodeLoginPinned` is what keeps the holder of a stolen password out. Before her first Login (`tls443-pw-first`) it does not (D8).

**The control stream of a C node** (`control-node-*`), with the fingerprint of the certificate of the controller checked, holds every query against the network and against the middlebox with the key of the certificate. The controller knows a node by its static key and by nothing else, so the holder of the Noise key of a node is that node to the controller (`control-node-client`): it gets its Updates, sends its leases and chooses its Hello.

**The overlay sessions** (`overlay-*`), which run in production, hold every query against the middlebox with the key of the certificate on TLS-443. They have no Login, so the Noise key of a node alone is the node to its peers (`overlay-tls443-client`). On QUIC they hold every query against the same middlebox since CORE-H5 (`overlay-quic-cert`), which closed F1.

**The session with a Login over QUIC, as the code has it.** Since CORE-H5 (#408) the handshake is bound to the exporter of the QUIC connection, so QUIC holds what TLS-443 holds: every query against the network (`quic-none`) and against the middlebox with the key of the certificate (`quic-cert`), whose two connections, to the client and to the server, have two exporters; the password and the data against the Noise keys of the server and of the client (`quic-noise-client`); and forward secrecy (`quic-fs`).

**The tunnel.** A connection with the key of alice that joins a Tunnel is one that alice made, in the outer session that the server is in, also against the middlebox with the key of the certificate (`tunnel-none`, `tunnel-cert`, and on QUIC since CORE-H5 `tunnel-quic-cert`), and a connection joins only a Tunnel that was made for its own static key, whatever ids it knows.

**The mimic path.** The claims of AUD-7, each with the variant and the queries whose answers say it (`expected.tsv`, checked by the jobs of the variants):

- **The prober** (`mimic-none`). An attacker that is the network and knows the public key of the server, but no short id, cannot make a proof that the server takes (`probe` holds): every connection it makes is spliced to the decoy (`probe-decoy` can happen), and it sees the certificate and the page of the decoy and nothing of the sidecar. The short id stays secret (`sec-shortid` holds). A ClientHello of alice that it sends again is taken again, as `probe` allows: the library refuses one only when its clock is older than the time difference it allows, which the model leaves out, and the answer is under handshake keys that the prober cannot compute. Every query of the session holds.
- **A client with a wrong short id** (`wrong-sid`, in every variant but the ones of the private key). The server splices it to the decoy, the check of the temporary certificate fails on the certificate of the decoy, and the client gives up: it never takes a certificate (`wrong-sid` holds), so its node sends no Noise message and no Login. What it learns is what a prober learns: the decoy.
- **The holder of a link** (`mimic-link`). The public key and a short id are what a link holds, and the link is typed by hand today. With them the attacker proves the key, the server answers it as a server and not as the decoy (`probe` is an attack): a client of the server, and anyone who read its link, can tell the server from the decoy. It cannot answer alice as the server, since that takes the auth key of her ClientHello, the X25519 secret of her key share and the public key (`mimic-auth` holds), and every query of the session holds.
- **The middlebox that terminates the outer session** (`mimic-key`). It holds the REALITY private key of the server, the key that the public key of the link pins. It opens every proof and learns the short ids (`sec-shortid` is an attack), answers alice with a temporary certificate of its own, so that her sidecar takes it and hands her node the stream (`mimic-auth` is an attack), whatever the short id of her link (`wrong-sid` can happen), and opens a REALITY session of its own to the server with her short id. The binding stops it: the exporters of its two sessions differ, the handshake that it relays does not complete, and every query of the session holds, as in `tls443-cert`: it reads no password and no data, and can lower no suite.
- **The public key as the pin of the link** (the third point of the comment of CORE-P2-6 on CORE-H3, #400). On the mimic path the pin of a client is the public key of the server in its link, checked through the HMAC of the temporary certificate (D9): a holder of the private key terminates the outer session, as a holder of the key of the certificate does on TLS-443, and nothing else does (`mimic-none`, `mimic-link`). What the pin protects is the outer session and the disguise, the short ids and the answer to a prober; what keeps the session of the node safe against the holder of that key is the binding and the static keys of Noise. The key is a key of its own, and nothing ties it to the node identity yet.

**Noise_IK alone** (`noise-encrypted`) gives the grades of the Noise Explorer for the four messages: message a has the authentication of its sender only against a receiver whose key is not compromised (`a-auth1` and `a-auth3` hold, `a-auth2` and `a-auth4` do not), and no forward secrecy (`a-conf4` and `a-conf5` fail); message b holds every authentication grade and every confidentiality grade up to `b-conf4`; messages c and d, the first records of the two directions, hold every grade, with strong forward secrecy (`c-conf5`, `d-conf5`): that is why the Login is in the first control record and the handshake payloads are empty.

The negative controls each show their attack, and CI fails when one does not:

- **NC1, `nobinding-cert`.** Without the binding, the key of the certificate of the server alone is enough for a middlebox: it terminates the TLS session of the client with the pinned certificate, opens one of its own to the server, and the two Noise handshakes cross it unchanged. Every query but `suite` that holds in `tls443-cert` fails here.
- **NC2, `nopin-noise`.** Without the pin, the Noise key of the server alone is enough: its holder answers the client in a TLS session of its own, and the binding, which is of that session, matches. Every query but the two that say the handshake can complete fails.
- **NC3, `neither-none`.** With neither, and no key leaked, the middlebox reads and rewrites every record: nothing is left for it to need. Every query but `suite` fails.
- **NC4, `tunnel-nokey-none`.** If the server joined a connection to the Tunnel of the id that it names without comparing the static key of the connection with the Tunnel's, `charlie` would join the Tunnel of alice with her id, which the attacker is given. `join-identity` holds in `tunnel-none` and fails here.
- **NC5, `endpoint-cert`.** The binding of the QUIC path before CORE-H5, the tls-server-end-point, is the same for every connection to one certificate, so the key of the certificate alone is enough for a middlebox, as without a binding: F1 as it was. Every query but `suite` that holds in `quic-cert` fails here.
- **NC6, `mimic-nobinding-key`.** Without the binding, the REALITY private key of the server alone is enough for a middlebox on the mimic path: it terminates the REALITY session of alice with a temporary certificate of its own, opens one of its own to the server with her short id, and the two Noise handshakes cross it unchanged. Every query but `suite` that holds in `mimic-key` fails here. (The code runs a stream whose line says `-` as an encrypted session, `NOISE_SESSION_ENCRYPT`, which the control leaves out: it takes away the binding alone, as NC1 does.)

### The answers that AUD-6 changed, and why

The second review of AUD-5 found where the models said more than the code does. AUD-6 changed the models to the code, ran every variant again and put the new answers into `expected.tsv`. These are the answers that changed:

- **The control stream carries no password.** The control models had a password in the first record of the node, which the controller checked; the code has none, and the controller takes the static key alone. `sec-pw` and `fs-pw` are no longer asked of the control models. In `control-node-noise-client`, `sec-data` and `negotiation` held because of the password check that the controller does not make; they are attacks now: the holder of the Noise key of the node gets its Updates and chooses its Hello. The new variant `control-node-client` shows it with the key of the node alone (`sec-data`, `auth-server`, `took-auth`, `cdata-auth`, `negotiation` and `replay-server` are attacks; what the node takes from the controller still holds).
- **The control frames have no record type byte and no suite byte, and the prologue no binding type byte.** The control models have their own processes (`control-lib.pvl`), and `suite` is no longer asked of them: there is no suite to lower. No other answer of the control models changed with the framing.
- **The C control client checks the certificate.** The review found that the C client had no pin and asked for the exporter of the session label, so that its handshake could not complete on Schannel. SDN-90 (#395, PR 416) gave it both before this change: the node service dials over the TLS transport of `NodeControllerTls`, which checks the TLS fingerprint of the Controller settings (`NodeControllerVerify`) and exports `CONTROL_EXPORTER_LABEL`. So the control-node models keep the pin, and their answers stand as the answers of code that runs. The Go client of `Dial` still checks no certificate (C1); `DialPinned` checks the fingerprint.
- **The responder takes any key of an initiator.** The session server of the models took only the key of alice at message 1. It takes any key now, and the key check is the one of the caller after the Login (`kp_on`), so the server events name the key, and `took-auth` asks what the Login is for. Every answer of the AUD-5 session variants stands under it, but three: in `tls443-both`, `took-auth` and `cdata-auth` are attacks (the attacker logs in with the password that it read). The new variants `tls443-pw` and `tls443-pw-first` show the pin and its first use: with the key pinned a stolen password alone does not log in, and before the first Login the holder of the password pins a key of its own (`sec-data`, `took-auth` and `cdata-auth` are attacks, D8). The join server takes any key too, and compares it with the key of the Tunnel: the answers of `tunnel-*` did not change.
- **The Login negotiates nothing.** The Login has one version, which the parser takes exactly. The session models no longer ask `negotiation`, which held, and keep `suite`.
- **The overlay sessions have no Login.** They are new models (`overlay-*`), since they are the sessions that run. Against the middlebox on TLS-443 every query holds; the Noise key of the dialling node alone is the node (`overlay-tls443-client`); F1 holds on QUIC (`overlay-quic-cert`).
- **Each side decides bound or encrypted.** The client and the server of a model now take a binding each; `quic-nocert-none` proves that a client with no binding cannot complete the handshake with a bound server (`reach-took` and `reach-done` hold: the events cannot happen).
- **The Login gate and the data of the client.** A data record before the Login is refused, and the models now have a data record of the client after the Login: `cdata-auth` holds wherever `took-auth` does.
- **The peer layer has the punch probe and the bound.** `pp-addr` is an attack (the weakness of F3 holds for the direct path), and `pb-auth` holds.
- **The peer layer has a session, the bind challenge and the punch nonces** (CORE-H2, #399, after AUD-6). `pd-forgery` and `pd-secret` hold now: F2 is closed. `pe-cookie` and `pp-proof` are new and hold, and `pe-addr`, `pp-addr` and `pe-replay` stay attacks, as negative controls: an envelope holds no address, which is why no envelope alone binds a node or sets a path, and the receiver of the model keeps no sequence. `pe-replay` asks about the signal, which only the one-shot `PeerSeal` seals (the event `EnvelopeSealed`): with the leaked keys of `peer-leaks`, ProVerif did not end on the injective query over every envelope, whose seals of the bind with its cookie and of the punch come after inputs of the attacker. In `peer-honest` its non-injective form holds, so the attack is the replay alone. F3 is closed with them.
- **Three variants take `preciseActions`.** With the key of any initiator taken, ProVerif rebuilt the traces of some attacks of `quic-cert`, `nobinding-cert` and `neither-none` only with this setting (above); with it, `took-auth` of `quic-cert` is an attack, where it could not be proved, and the negative controls show every attack that they showed before.

## Findings

Each of these is an attack that the prover finds, and a result of `expected.tsv` that CI checks, so a fix of the code changes `expected.tsv` in the same change. The trace of each is in the artifact of its job (`formal-<variant>.attacks.txt`) and in the log of the job.

### F1: on QUIC the key of the certificate alone gives a middlebox the session

Closed by CORE-H5 (#408): the QUIC path binds the Noise handshake to the TLS exporter of its connection, which msquic gives from 2.6 on (`ConnectionExportKeyingMaterial`, on Schannel through `SECPKG_ATTR_KEYING_MATERIAL`; `TransportQuicExporter`), with `NOISE_EXPORTER_LABEL`, no context and 32 bytes, as the TLS-443 path does. Both ends take it in the CONNECTED event of msquic, while msquic still holds the TLS state. A middlebox with the key of the certificate has one connection with the client and another with the server, so the two exporters differ, the relayed handshake fails at message 1, and no Login leaves the client. `quic-cert`, `overlay-quic-cert` and `tunnel-quic-cert` hold every query that their TLS-443 twins hold, and the negative control `endpoint-cert` keeps the attack of the binding to the certificate. The vpntest test `quicbind` runs the middlebox: a QUIC listener with the same certificate that relays the stream of a client to the server. A side whose msquic gives no exporter leaves its streams unbound, so its session is encrypted, and its handshake with a bound peer fails, as with a node of the build before CORE-H5, which binds the tls-server-end-point. What this section said before:

`quic-cert`: every query but `suite` fails, where `tls443-cert` proves them; and so do the overlay sessions that run in production (`overlay-quic-cert`) and the join (`tunnel-quic-cert`: `join-auth` and `join-replay`). The tls-server-end-point is the same for every connection to one certificate (D1), so an attacker that holds the key of the certificate of the server, and not its Noise key, and sits on the path, terminates the QUIC session of the client with the pinned certificate, which passes the pin, opens a QUIC session of its own to the server, and relays the Noise handshake: the two prologues match. The records of a bound session then travel in the clear inside QUIC, with no Noise tag, so the attacker reads the Login, whose password is in the clear, reads and rewrites every record, injects records of its own, and replays message 1 on a new connection. A certificate Login is relayed in the same way, because its challenge comes from the handshake hash, which the relay leaves equal on both sides. The pin keeps the attacker out without that key (`quic-noise-client` holds). ADR-0023 binds the handshake to the outer session so that a middlebox that terminates it cannot read the data; on QUIC it can, with the certificate key. The code states the cause: msquic exposes no exporter. QUIC is the first entry of the race of a client, so it is the path that a client takes first.

### F2: the data datagrams of the peer layer have no confidentiality and no authentication

Closed by CORE-H2 (#399): every data datagram is a record of a peer session (`PeerSession.c`), a datagram of the old clear form is dropped (`PEER_DROP_CLEAR`), and `pd-secret` and `pd-forgery` hold in both variants. What this section said before:

`peer-leaks` and `peer-honest`: `pd-secret` and `pd-forgery` fail with no key leaked. `PeerSend` writes the tag, the key of the source, the key of the destination and the payload in the clear, and `PeerInputData` delivers a datagram whose source address is a path of its source (a relay, a binding or a direct path) and whose source is a peer: no key is checked, and a UDP source address is not authentication. Anyone on the path reads the payload and sends a datagram in the name of any peer. ADR-0015 items 3 and 7 and ADR-0023 have the data in the session of QUIC or TLS (D4). A node with the relay role runs the peer layer on a UDP socket of its own (`NodeRelayStart`): it takes the binds of its nodes and forwards their data datagrams. The overlay of `NodeOverlay.c` does not use the peer layer, it runs a Noise session over a data transport to each peer, so no node sends peer datagrams to a relay yet, and the exposure today is the UDP port of the relay role and the harness.

### F3: a relay binds the node to the address of the datagram, and the replay check forgets

Closed by CORE-H2 (#399). A relay binds a node at an address only with the cookie that it sent to that address in a challenge sealed to the node (`PeerChallenge.c`), so the same bind sent from another address draws a challenge that the attacker cannot open, and binds nothing (`pe-cookie` holds). A punch probe sets no path; an end moves the peer to the direct path only at an address where the peer echoed a nonce sealed to it (`pp-proof` holds). The sequences of binds, signals, punch messages and initiations must be above the clock when the receiver made its entry of the peer (`PeerFloorOf`), and the relay keeps the sequence of a bind with the peer, not with the binding, so a bind or a signal captured earlier is a replay after the expiry of a binding, a change of the peer list and a restart of the receiver. The floor tolerates no clock skew (finding 3 of the review of PR 429, CORE-H2-R1 #436, accepted): a peer whose clock is behind the receiver's by some time is refused for that time after the entry, until its clock passes the floor, and no longer (coretest `peersession`), since a sequence that a slow clock sealed just now and one that a right clock sealed before the loss look the same, and a tolerance would take the second again; the model has no time, so `pe-replay` stays an attack of its receiver, which keeps no sequence, and the tests show the code (coretest `relaypolicy` and `punch`). An attacker that is the whole network can still bring the relay's challenge for its address to the node and the node's answer back, as a NAT does: no bind can tell that from a NAT, and the records that reach it are those of peer sessions, which it can only drop. `pe-addr` and `pp-addr` stay attacks for that reason, as negative controls. What this section said before:

`peer-leaks` and `peer-honest`: `pe-addr`, `pp-addr` and `pe-replay` fail. The envelope of a bind holds a version and a sequence, not an address, and `PeerInputBind` binds the node to the address that the datagram came from, so an attacker on the path that drops the bind of a node, or outruns it, and sends the same envelope from an address of its own takes the binding, and with it the datagrams that other nodes send to the node through the relay (F2 makes them readable). While the relay keeps the sequence of the node, the same bind sent again is refused (`PEER_DROP_REPLAY`): the attacker must drop or outrun the original, and a binding that it takes lasts until the next renewal of the node, 25 seconds. A punch probe sets the direct path of a peer in the same way (`PeerPunchInput`, with `Config.Punch`, which no production code sets). The sequence that must grow (`PeerInputBind`, `PeerOpenSignal`, `PeerPunchInput`) is kept in memory: `PeerTick` drops the binding, and its sequence with it, after `BindExpiry` without a renewal, `PeerSetPeers` makes a new entry, with sequence 0, for a peer that left the table and came back, and a restart of the receiving node loses them all, so a bind or a signal that was captured earlier is taken again then. The model has a receiver that keeps no sequence, which is what such a receiver is.

The envelope has no forward secrecy (`pe-fs` fails in `peer-leaks`): its key comes from es and ss, as in every Noise_K, so a leak of the static key of the receiver opens the envelopes that were recorded. What it holds is a relay assignment and ICE candidates, which are no secret after the session.

### C1: the Go client of Dial relies on the key of the controller alone

`control-go-noise`: `sec-data`, `auth-server`, `took-auth`, `cdata-auth` and `negotiation` fail: the client of `Dial` (`controller/internal/control`), which sets `InsecureSkipVerify`, has the static key of the controller and the exporter, and nothing else, so the key of the controller alone is enough for an attacker. This is `nopin-noise` with the control stream. `ranz-nodesim` dials this way when its node has no TLS fingerprint, and so do the tests of the controller; `DialPinned` checks the fingerprint, as the C node does (`NodeControllerVerify`).

## Differences from ADR-0022 and ADR-0023

The model follows the code, so these are differences of the code from the ADRs, which the table cites by their number.

### D1: the QUIC path bound tls-server-end-point, not the TLS exporter, before CORE-H5

ADR-0023 (amendment of 2026-10-15) binds the Noise handshake to the TLS exporter, RFC 8446 section 7.5. The TLS-443 path does (`TlsExporter`: label `NOISE_EXPORTER_LABEL`, no context, 32 bytes), and since CORE-H5 (#408) so does the QUIC path (`TransportQuicExporter`), so the code no longer differs from the ADR here. Before it, msquic was taken to expose no exporter, and the QUIC path bound the tls-server-end-point of RFC 5929, the hash of the pinned server certificate (`QuicCertBinding`, `CryptoCertEndPoint`), which ADR-0022 (amendment of 2026-10-15) names as the fallback. The value is the same for every connection to one certificate, so it binds the handshake to the certificate and not to the connection. F1 was the consequence. The table still cites D1 for that binding, which `EndPointBinding`, a switch of the configuration for the test of an old node, gives, and which the negative control `endpoint-cert` has.

### D2: the pin is a thumbprint that a setting holds, not derived from the node identity

ADR-0023 pins the server certificate to the node identity. The pin of a client is the 40 hex digits of the SHA-1 thumbprint of the certificate in the Client setting (`servers[].thumbprint`, `NodeClientAddServer`), which `TransportTlsDefaultConfig` and `TransportQuicDefaultConfig` take; the pin of the control stream is the TLS fingerprint of the Controller settings, the SHA-256 of the public key of the certificate (`NodeControllerVerify`, `DialPinned`). The static key of a server comes from the desired state, and the one of the controller from the Controller settings. Nothing ties a pin to a static key, so a certificate that two nodes share, or the key of a certificate alone, is not tied to a node. The system roots are not trusted (`SCH_CRED_MANUAL_CRED_VALIDATION`, `QUIC_CREDENTIAL_FLAG_NO_CERTIFICATE_VALIDATION`), as ADR-0023 asks. The model takes a thumbprint as a hash without collisions; SHA-1 is deprecated, and `CryptoCertThumbprint` uses it because the certificate store finds a certificate by it.

### D3: the Go client of Dial checks no certificate

ADR-0023 pins the certificate of the server for node-to-node links, and the control stream is bound like them. The Go client of the control stream that `Dial` opens (`controller/internal/control`, used by `ranz-nodesim` without a fingerprint and by the tests of the controller) sets `InsecureSkipVerify`: C1. The C node checks the TLS fingerprint of its Controller settings and asks for the exporter of the control label (SDN-90, `NodeControllerTls`), and so does the Go client of `DialPinned`; `ControlRun` checks only the type and the size of the binding, not its label, which is the transport's.

### D4: the peer layer has no outer session

ADR-0015 items 3, 6 and 7 and ADR-0023 have the relay speak the same QUIC or TLS-443 session as the direct path, with the Noise_IK handshake of the first stream bound to it, and the signals signed with the node keys. The peer layer has no outer session: its envelopes are one-shot Noise_K messages (kind, sender key, ephemeral key, ciphertext; prologue `ranz peer 1` and the kind), sealed and not signed, and its data datagrams are the records of a peer session over UDP (CORE-H2, #399): Noise_IK between the static keys of the two nodes, with the prologue `ranz peer session 1` and no channel binding, whose records are under the Noise keys, as a session that nothing binds is (`NOISE_SESSION_ENCRYPT`), with a counter and a sliding window in place of the order of a stream. A relay forwards a datagram of a session as it came, by its clear header. Peer.h says the socket stands in for the QUIC datagrams until the transport interface carries them.

### D5: the outer rekey is a call that does nothing

ADR-0023 asks for a periodic rekey through the QUIC key update and the TLS 1.3 KeyUpdate. `NoiseSessionPoll` asks a bound session for it every `NOISE_REKEY_INTERVAL` (`NOISE_POLL_REKEY`), and both transports set a `Rekey` procedure, which returns true without updating anything: `TlsStreamRekey`, because SSPI has no call that sends a KeyUpdate (Schannel takes and answers the KeyUpdate of the peer), and `QuicStreamRekey`, because the transport does not set the forced key update of msquic. A bound session refuses a record with the REKEYED flag, which only an encrypted session uses. The keys of a session change by what the outer stack does by itself, and the forward secrecy of a long session rests on the ephemeral Diffie-Hellman of its handshake. The model has no rekey.

### D6: TLS 1.2 is allowed by default on TLS-443

ADR-0022 puts the session on Schannel TLS 1.3. `TransportTlsDefaultConfig` sets `Versions` to TLS 1.2 and TLS 1.3, and the production client of a session uses the default; the exporter of a TLS 1.2 session is the one of RFC 5705. The model is TLS 1.3 only: a session that negotiates 1.2 has the exporter and the downgrade protection of that version, which the model does not hold. The control stream of the C node is TLS 1.3 only (`NodeControllerTls`).

### D7: Noise_IKhfs runs only when a client asks for it, and no client does

ADR-0022 has the post-quantum hybrid "used where the OS provides it in both TLS and Noise". `NOISE_SUITE_IKHFS` is implemented (`NoiseHandshakeInit` and the tokens e1 and ekem1), and the TLS side puts X25519MLKEM768 first (`TransportTlsSetGroups`), but every client sets `NOISE_SUITE_IK` (`NodeOverlaySessionConfig`, `ControlRun`, the transports of the tests). It is not dead code: every responder runs IKhfs when the first record asks for it and CNG has ML-KEM (`NoiseSuiteAvailable`), with no policy of its own, and the suite is in the protocol name that `InitializeSymmetric` hashes into `h`, so an attacker that changes the byte makes the handshake fail (`suite` holds). The model has IKhfs up to its protocol name, not its KEM tokens; the client of the session models offers it, so that a change of the byte to IK is the downgrade that `suite` asks about.

### D8: a Login compares no key on its first use, for an anonymous user and for a user that the store does not keep

ADR-0023 has the Noise handshake authenticate both nodes by their static keys, and ADR-0022 (Enrollment) the static key pinned on the first login (trust on first use). The responder takes the key of any initiator, and `NodeLoginPinned` compares it with the key pinned to the user only for a password or certificate Login of a user that the configuration store keeps and that has a key pinned. The first Login of a user pins whatever key it comes with, so the holder of the password before that Login pins a key of its own (`tls443-pw-first`); a user that the store does not keep (a domain account) is never pinned; and an anonymous Login has no password and no pin. On those Logins the static key of the client authenticates nothing. FIX-8 (#407) makes a store that fails to check the key refuse the Login; the model has the key check as FIX-8 leaves it, with a failed store refusing.

### D9: the pin of the mimic path is the REALITY public key that the link holds, typed by hand

ADR-0023 pins the server certificate to the node identity, and keeps the authentication keys of the mimicry sidecar separate from the Noise key and from the TLS certificate. The mimic path has no certificate to pin: the client sidecar takes the temporary certificate of a server only when its signature is the HMAC under the auth key, which only the holder of the REALITY private key of the public key of the link computes with it (`temporaryCertificate`, `realityHandshake`, which checks no chain), so the public key of the link is the pin. The key is separate, as the ADR asks. But nothing ties it to a node: the link of a client (its address, the public key and the short id) is typed by hand into the `MimicClient` setting, and the private key of a server into its `MimicServer` setting. The Controller half, CORE-P2-7 (#424), which makes the key on the node and reports it, and SDN-94 (#423), which gives the clients of a mimic server their link, are not merged. The model has the pin as the code checks it, with the public key of the right server in the link; a link with the key of another server is the key of that server, which the model does not have. Of the other differences, D5 holds on this path too (the mimic transport sets no `Rekey`, and the TLS session of the sidecar is its own), and D6 does not (REALITY completes TLS 1.3 only); which suite the REALITY server selects from the ClientHello of a browser, and whether the TLS library of the sidecar updates its keys on a long connection, are the open points of CORE-H3 (#400), which the model, with one AEAD and no rekey, does not decide.

## What the model leaves out

- The TLS and QUIC stacks themselves: the model has an abstract TLS 1.3 handshake with the authentication of the server and an exporter, not Schannel or msquic, their record layers, their resumption (the code uses none) or their downgrade protection; the ALPN protocol of the control stream, which tells a control stream from the HTTP of the controller; the groups of the key exchange, which the model takes as one Diffie-Hellman; and a QUIC connection that carries up to 4 streams of the client, each a session with the same binding.
- The bytes: lengths, framing and parsing (the fuzz targets and the tests of the module cover them), and the AEAD nonce counters of a long session.
- Time: the keepalives, the dead-peer timeout, the rekey interval, the expiry of a binding, which the model has only as the receiver that has lost its sequence. The model sends a keepalive and a close record and reads neither.
- The decoy of the TLS server (`TlsDecoyGuard`): it reads message 1 a first time and sends a message that does not open, and the rest of its stream, to the decoy. In the model a message that does not open ends the session either way, and a prober learns what the decoy shows it, which is no query here. The decoy of the mimicry sidecar is in the mimic models.
- Of the mimic path: the clock of the proof and the time difference that the server allows (so a ClientHello sent again is taken again in the model, and within that time in the code), the version range of the proof beyond one version, the server names and the SNI, the fingerprint of the ClientHello (uTLS) and the records that the library copies from the real site after its handshake, the frames, the padding and the pacing of the stream between the sidecars, the counters and the log, the job that ends the sidecar with the node, the delay of a restart, and what a prober learns from time and from the shape of the traffic. The pipes are in the model as the private link between a sidecar and its node that their DACL and the check of the process id make them; a process of the account of the node is the node.
- `BreakBinding`, a switch of the configuration of the transports for the tests, which makes a client compute a wrong binding as a middlebox would, and `EndPointBinding` of the QUIC transport, which binds as the build before CORE-H5 did (the model of that binding is `endpoint-cert`).
- The anonymous and the certificate Login: the model has the password Login. An anonymous Login is the session of `tls443-pw-first` with a password that everybody has; a certificate Login signs a challenge from the handshake hash, which `endpoint-cert` relays as it relays a password.
- What the controller checks after the key of a node: the source prefixes, the licence and the Capabilities, which decide whether it serves a node and not who the node is.
- Of the multi-connection tunnel, the first connection (its Login and the id that its handshake gives are the session model, and the id is the attacker's here), the routing of the flows over the connections (`NoiseTunnelRoute`), the loss of a connection and its return, the refusals of a join for a halting Tunnel, a full one or a session that joined already, and the number of connections that a tunnel holds.
- Of the peer layer, the forwarding of the relay (the attacker sends any datagram from any address, which is all that the forwarding would give it), the relay check of a signal (its content is one secret value), the rate limit and the ICE connectivity checks of libjuice.
- Of a peer session, whose model is one handshake and the first record of the initiator, these gaps (finding 5 of the review of PR 429, CORE-H2-R1 #436, which this list records in place of a model of them):
  - The counter of a record and the sliding window of `PEER_WINDOW_BITS` counters that refuses a counter taken before (`PeerWindowCheck`): with one record there is nothing to replay in the model. coretest `peersession` sends a record again and sees it refused and counted.
  - Two handshakes at once, of which the node with the lower static key keeps its own and the other gives its own up and answers (`PeerSessionTakeInit`): the initiator and the responder of the model are processes of two nodes whose initiations never cross. coretest `peersession` has G and H start at once and end in one session.
  - The indices: the sender's index in an initiation, the two in a response and the receiver's in a record, and the payloads of the handshake that repeat them, so that a clear index changed on the way fails the handshake (`PeerHandshakeParse`). An index only selects the keys of a record, and a record under the keys of another session, or of none, does not open. coretest `peersession` refuses a record of A sent in the name of C, and drops as forged a response made from the clear header of an initiation, which leaves the handshake on its way.
  - The whole clear header as the associated data of a record: the code authenticates the index and the counter with the kind and the two keys (the `PEER_RECORD_HEADER` bytes), the model the kind and the two keys, so what the model proves of the binding of a record to its pair holds of the code, which binds the index and the counter beyond it. coretest `peersession` changes each byte of a record and sees every copy refused.
  - The drop of the old clear form (`PEER_MSG_DATA`, `PEER_DROP_CLEAR`): the model has no clear form, and its nodes take a payload only from a record that opens, which is what the drop leaves of the code. coretest `peersession` shows the relay and the node drop one and count it.
  - The rekey, the keys before and after it (Previous and Next), the queue and the timers, and the keys of a responder that the initiator has not confirmed yet, which stay as the keys before when the next initiation of the initiator overtakes its records on the way (CORE-H2-R1 #436), all of which coretest `peersession` checks.
- Denial of service and traffic analysis.
- Cross-protocol use of the node static key in the sessions, the control stream and the envelopes: the three prologues differ in their labels and the envelopes in their pattern, but the models do not run them together. A node that is both a client and a server with one static key is not modelled either: the Diffie-Hellman of the models is between an initiator and a responder.
- Several compromises at once beyond the scenarios: the models answer for one compromise, or two where the second is the key of the client, and for both keys of the server.

## Running it

ProVerif 2.05 builds from its source archive (`./build -nointeract` with OCaml). The models are text:

```
python .github/scripts/formal.py check
python .github/scripts/formal.py run tls443-none tls443-cert --proverif /path/to/proverif --out build/formal
```

`run` writes each variant as one `.pv` file and its log to the directory of `--out`; the file runs on its own with `proverif -in pitype build/formal/tls443-none.pv`. The result of a query is `is true`, `is false` (an attack, with its trace) or `cannot be proved`. ProVerif keeps its state for every query of one run, so `variants.tsv` can cut a variant into slices, each a run of ProVerif with consecutive queries of its own and a job of the workflow (`python .github/scripts/formal.py run noise-encrypted --slice 2/4` runs the second of four).

To add a model, write its process in a file of `session/`, `control/`, `overlay/`, `tunnel/`, `mimic/` or `noise/`, give it a line in `variants.tsv` and a line for each of its queries in `expected.tsv`, and a row for each name that it declares in the table. A variant whose name starts with `try-` is an experiment: it needs no line in `expected.tsv`, the jobs of the workflow leave it out, and `formal.py run try-name` reports what ProVerif answers for each query without judging it, with the last lines of ProVerif when it runs out of time. Run `formal.py smoke` and an experiment first when a model is new: a process that creates a name after an input, or an equation, is what makes ProVerif run for hours.
